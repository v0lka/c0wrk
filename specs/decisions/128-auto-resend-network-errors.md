# ADR-128: Task-Level Auto-Resend for Network-Class Provider Errors

## Status

Accepted

## Context

[ADR-065](065-auto-resend-retryable-errors.md) gave a failed task an automatic re-send, but scoped it tightly: the retryable class is `ErrKind` `rate_limit` / `overloaded` (HTTP 429/529) only, and the interval is a **per-provider** knob (`auto_retry_seconds`) carried per provider entry — at ADR-065's writing only by the compatible configs, with the fixed providers (`anthropic`, `chatgpt`, `kimi`) resolving 0 ([ADR-127](127-fixed-provider-auto-resend.md) later extended the *same per-provider key* to those fixed entries; that is a provider-scope change, not a class change, and it leaves the network class untouched — see commitment 3). ADR-065 recorded the resulting invariant explicitly: **network errors (`StatusCode` 0) and every non-listed status never surface a deadline.**

Two things make that scope insufficient:

1. **Connection-level failure is the dominant whole-task failure for infrastructure the user owns — and it hits fixed providers hardest.** A self-hosted gateway restarts (connection refused), a VPN or DNS resolver hiccups (`dns`), a proxy drops the socket mid-flight (`reset`), a stalled connection trips a client-side deadline (`timeout`). The engine's in-flight retry is bounded (`llm.retry`: default 3 attempts, backoff 1 s → 30 s) and routinely dies before a minutes-scale outage heals; the task then lands in the `failed`/resumable state with the manual-resume banner — exactly the babysitting ADR-065 removed for rate limits. The fixed providers are precisely where this strands the user: ADR-065's rationale ("vendor endpoints are not the user's own") bounded a per-provider *tuning knob*, not the failure class itself — a connection failure against the ChatGPT Codex backend strands a task exactly like one against LM Studio, and today neither surfaces a deadline.
2. **[ADR-071](071-adaptive-llm-request-budgets.md) changed what "timeout" means.** A request that dies of the adaptive request budget's *own* expiry surfaces as the llmbudget transport's wrapper — `adaptive request budget exhausted: … armed for … (own budget expiry, not a provider abort; the next budget escalates): %w` around a `context.DeadlineExceeded` — and self-heals in-flight: the transport latches a ×2 escalation for the model and the retry re-enters under the fresh, larger budget. That signature is technically indistinguishable from a provider-side timeout by a naive predicate (`context.DeadlineExceeded` itself satisfies `net.Error.Timeout()`), so an extended network class must carve budget-death out explicitly — otherwise a per-request deadline miscalibration would tear down and restart whole tasks that ADR-071 already cures in-flight.

The question this ADR answers: extend the task-level auto-resend to connection-level provider failures — for which error classes, under which interval, covering which providers, and with what deliberately out of scope?

## Decision

**The auto-resend extends to the connection-level (network) error class, for every provider including the fixed ones, under one global fixed-longer interval with `0 = off`; budget-death stays explicitly out of scope.** Four commitments:

1. **The class extends to connection-level (network) provider errors.** A terminal `*llm.Error` whose `StatusCode` is 0 and whose wrapped chain carries one of sp4rk's four transient connection classes — `dns`, `connect` (refused/unreachable), `reset`, `timeout` — qualifies for the auto-resend. The taxonomy is sp4rk's connection-level diagnostic set (`llm.TransportKind`, `llm/errors.go`), the same classes whose retryability sp4rk's `classifyNetError` already establishes for in-flight retry (transient errnos on Unix and the raw Winsock codes on Windows, DNS errors, net-error timeouts). The extension lands in the transient-class predicate `core.IsTransientProviderError` (`core/delegation_retry.go` — the one definition of the class, shared with the delegation launcher's auto-retry); the backend-local seam `isAutoRetryableCause` (`backend/session/manager_auto_retry.go`) consumes it and keeps only the interval resolution: a code change, not a config change, exactly like the rate-limit class before it. The remaining `TransportKind` labels stay **out**: `tls` is misconfiguration (a certificate/pin mismatch) that no re-send ever heals; `eof` is ambiguous between a transient drop and a broken stream and is already carried by the engine's in-flight retryable set; `other` is unclassifiable.
2. **Fixed providers are included.** Unlike the rate-limit knob, which is a per-provider interval (ADR-065's compatible-only scope, since extended to the fixed entries by ADR-127), the network class is not per-provider at all: it applies to every provider — `anthropic`, `chatgpt`, `kimi`, the backend-owned `embedded`, and every compatible entry. No per-provider field is added for this class; there is nothing to tune per provider (see 3).
3. **One global interval, longer than and separate from the rate-limit interval; `0` = off.** A single new top-level key `llm.network_auto_retry_seconds` (plain int, **default 90** — the middle of the 60–120 s band) governs the whole class for all providers. It never multiplexes with `auto_retry_seconds`: the classes cure on different timescales — a 429 window is server-signposted and seconds-scale, while a refused socket can be minutes-scale with no signal about when to come back — so re-sending into a healing outage on the rate-limit cadence (default 30 s) would only multiply futile attempts. Semantics follow the ADR-065 pattern: no separate enable bool — `0` is the kill-switch ("never auto-resend on network errors"), an absent value materializes the default 90 via `ApplyDefaults` (omission ≠ off, unlike the per-provider knob where omitted = disabled), and a positive value is validated against the same inclusive upper bound as the per-provider interval (`config.maxAutoRetrySeconds` = 3600, enforced by the shared `validate()` + `UpdateLLMConfig` rule). The value reaches the session manager through the same immutable atomic-snapshot seam (`SetAutoRetryResolver` / `publishAutoRetryIntervals`, extended to carry the global value) and is republished by every committed `UpdateLLMConfig` candidate — a flip applies to the next surfaced deadline, no restart. What the UI sees is unchanged in shape and lifecycle: the same `auto_retry_at` stamp in `task_failed_resumable`, the same live-only countdown, the same stop-on-any-manual-click, the same compaction strip, the same unlimited re-arm (ADR-065's contract, verbatim).
4. **Budget-death is explicitly out of scope.** A failure whose cause is the adaptive request budget's own expiry — the llmbudget transport's own-budget-expiry wrapper around a `context.DeadlineExceeded` it armed itself while the caller's context is still alive — does NOT qualify, even though it satisfies a naive timeout predicate. ADR-071's escalation ladder (×2 latch per model, bounded by `MaxEscalationFactor`, re-clamped to the class ceiling) plus the engine's in-flight retry under the escalated fresh budget is the designed and sufficient cure; a task-level re-send would restart the entire task to fix a per-request deadline miscalibration and would fight the ladder instead of letting it converge. The predicate excludes the transport's own-budget-expiry signature explicitly, in both directions (a budget death never arms a deadline; a provider-side timeout still does).

This deliberately narrows ADR-065's recorded invariant to: **non-budget connection-class failures surface a deadline under the global network knob (`dns` / `connect` / `reset` / `timeout`); `tls` / `eof` / `other` and every budget-death never do.** ADR-065 is **extended, not superseded**: its ownership split (backend classifies, UI fires), its live-only deadline, its `0 = off, no bool` pattern, its compatible-provider rate-limit knob, and its unlimited re-arm policy all stand. A dated Historical Note on ADR-065 records the extended class membership (the record itself is immutable).

## Consequences

**Positive:**

- The whole-task failure mode the engine cannot cure (an outage outliving three in-flight attempts) now self-heals for every provider kind — including the subscription transports where no per-provider knob exists and none will be added.
- Zero new frontend surface: same event payload key, same countdown hook, same banner lifecycle; the only backend delta is classification plus one global interval resolution.
- Budget deaths keep exactly one recovery path (ADR-071's escalation); the two timeout senses (own-budget vs provider-side) are disambiguated by the shared exported signature predicate (`llmbudget.IsOwnBudgetExpiry`), with tests pinning both directions.
- The snapshot seam already republishes on every config save, so the kill-switch and interval changes are live for the next surfaced deadline without a restart.

**Negative / trade-offs:**

- A deliberately stopped local server now triggers an unbounded re-send every 90 s while the banner stays mounted — the same accepted unlimited-retry trade-off as ADR-065 (bounded retries would give up during exactly the long outages this targets; Cancel is one click), now pointed at the user's own infrastructure. The `0` kill-switch is the escape hatch.
- The default flips behavior for existing installs: network failures previously never surfaced deadlines. Operators who want the old posture set `llm.network_auto_retry_seconds: 0`. Accepted — the default is the feature.
- The class taxonomy (plus the budget-death carve-out) is frozen in backend code again — the deliberate price of keeping knobs operational rather than expressive.
- Budget deaths stay out through the transport's exported signature predicate (`llmbudget.IsOwnBudgetExpiry`) rather than any message-prefix coupling: the signature is owned by the transport file alone, and both classification seams (the delegation launcher's transient class and the session auto-resend) reference the same exported predicate.

## Alternatives Considered

- **A per-provider `network_auto_retry_seconds` mirroring `auto_retry_seconds`** — rejected: the motivating case includes the fixed providers, which ADR-065's schema excluded (ADR-127 since added a per-provider key to them, but that is a per-*provider* knob, not a per-*class* one, and it would leave the network class compatible-only again); a compatible-only knob re-creates the exact gap being closed, and per-provider × per-class knobs buy nothing the timescale argument does not settle globally.
- **Reusing the per-provider rate-limit interval for the network class** — rejected: the rate-limit cadence is tuned to server-signposted windows (default 30 s); connection-level outages heal on minutes-scale with no signal, so the shorter cadence multiplies futile attempts. The separation of the two intervals is the point, not an accident.
- **Engine-level escalation (sp4rk `RouterConfig` retry budget) for network errors** — rejected for ADR-065's original layer reason: the router cannot resume an executor loop, so the "retry" would still be one request's retry inside a dead task, and the knob would leak into every provider's in-flight behavior rather than being the task-level, UI-owned re-send this ADR extends.
- **Including budget deaths in the class** — rejected: duplicates ADR-071's escalation (the budget transport already retries in-flight with ×2 and the next attempt re-enters under the fresh budget); a task restart would fight the ladder instead of letting it converge, and a full generation re-send costs far more than the escalated single attempt it would replace.
- **Including `eof` / `tls` in the class** — rejected: `tls` is misconfiguration whose re-sends loop with a certain outcome; `eof` is ambiguous (transient drop vs broken stream) and is already inside the engine's in-flight retryable set, so the bounded retries own it.
- **Bounded network retries (e.g. max N with backoff)** — rejected, same as in ADR-065: gives up precisely during the long outages the feature targets; a cap can be added later without schema changes.
