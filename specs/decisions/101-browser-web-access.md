# ADR-101: Browser Web Access — a Sidecar Mounted Sideways from desktop

## Status

Accepted → Consolidates the branch-local former web-access gate ADR (then numbered 091) (the series was collapsed before the mainline merge): the availability model — the master experimental gate — is decision 13 here; the sidecar architecture and every other decision stand unchanged

## Context

c0wrk's UI exists in exactly one place: the Wails desktop window. The React frontend is served by the Wails asset server (`//go:embed all:frontend/dist` in `main.go`), talks to the Go backend through generated bindings over the embedded `*backend.FrontendAPI`, and receives the event stream through Wails events. A user who wants to check on or drive a session from a phone, a second machine, or any browser has no path to the running app.

A browser surface needs the three transports the webview gets from Wails for free: the static frontend bundle, an RPC channel into the backend, and the event stream. Building any of that into the desktop package — or maintaining a second, headless binary — multiplies the surface that must be tested and kept in sync before the need is even proven.

The requirement that shaped this decision: **attach the web surface maximally sideways.** The existing app must carry almost no web knowledge, the feature must stay trivially removable, and the larger evolution (LAN exposure, a headless build) must not be foreclosed by stage 1. Whatever is decided has to respect the layering invariants ([architecture/layers.md](../architecture/layers.md)) and the security posture of a tool that can execute shell commands on the user's machine — a browser surface into c0wrk is, by construction, full remote control of the agent.

## Decision

1. **The web surface is an autonomous sidecar package, `internal/webaccess`, that depends on neither `desktop` nor Wails.** Every environment-specific piece is injected from the mounting point in `desktop`:
   - **Dispatch target.** webaccess receives the existing `*backend.FrontendAPI` as an opaque target and dispatches every RPC by reflection over its exported method surface — the same surface the Wails binding generator consumes. Zero edits in `backend`/`core`: methods become callable from the browser exactly when they become callable from the webview.
   - **Event tap.** `(*App).emit` in `desktop/app.go` — the single funnel through which every backend-facing event already flows — gains a generic, web-agnostic tap (the `eventTap` seam): when non-nil, it receives `(eventName, optionalData...)` alongside the normal Wails emit. This is the only seam in app core, it is 2–3 additive lines, and it knows nothing about sockets, browsers, or webaccess.
   - **Static FS and CSP middleware.** The static filesystem (the built frontend bundle — the same tree Wails embeds) and the Content-Security-Policy middleware are constructed at the mounting point and handed to webaccess; the package serves only what it is given.

2. **Loopback by default, with a credential generated once and persisted.** The sidecar binds `127.0.0.1` unless the operator pins another address, and authenticates browsers with a token minted at the first start: an empty `web_access.token` is generated (crypto/rand, 32 bytes → 64 hex) and written back to config.yaml through the same immediate config save every other settings change uses — from then on the credential is stable across restarts, which is what makes daily browser reconnection workable. The token is delivered as an `HttpOnly` `SameSite=Strict` cookie; the WebSocket upgrade additionally verifies the request `Origin`. **Accepted consequence, stated explicitly:** a browser holding the cookie has full control of the app — identical to sitting at the desktop. Loopback binding plus the token gate is the whole mitigation; no per-RPC authorization model is built.

3. **Transport security (TLS) is out of scope and gets its own future decision; the path is not closed.** The feature is shaped so that evolution is additive: bind address and credential handling arrived as mounted parameters rather than package constants (the configurable bind landed as decision 12), and TLS termination is the remaining seam. (The seam has since closed as [ADR-102](./102-web-access-tls.md).)

4. **Control RPCs live on `desktop.App`, never on `*backend.FrontendAPI`.** `GetWebAccessInfo`/`SetWebAccessEnabled` are desktop-lifecycle concerns. Because the web client dispatches over the `FrontendAPI` surface, keeping the control RPCs off it means the browser cannot control the sidecar itself — no self-disable, no credential state readback through the web surface. It also keeps the import graph acyclic: `desktop` imports `webaccess`; `backend` never imports `webaccess`; `webaccess` imports only the Go stdlib plus the WebSocket library.

5. **The removal path is: delete `internal/webaccess`, the desktop mounting lines, and — optionally — the config section and the Settings block.** No backend/core code carries web concepts. The single deliberate backend edit is additive and survives removal: the new `AttachFileContent` method (decision 7). The frontend shim in `frontend/src/api/runtime.ts` **stays** after removal: it is the transport-abstraction seam a future headless build needs, independent of whether the desktop sidecar exists.

6. **WebSocket transport is `gorilla/websocket v1.5.3`.** It is already in the module graph as an indirect dependency of Wails v2, so adopting it promotes an existing pinned version instead of adding a new dependency.

7. **Browser-native gaps are handled by feature-detect + gating; attachments are the one additive backend edit.** The web client detects desktop-only affordances (native file and directory dialogs) and gates the corresponding UI instead of reimplementing them. Where the web surface genuinely needs new backend capability — file attachments, where a browser hands over bytes rather than a local path — a new `AttachFileContent` method is added to the backend attachment surface. This is the deliberate, recorded exception to "zero backend edits".

8. **The inbound WebSocket bridge is a fixed whitelist (amendment closing the stage-1 HITL gap).** Stage 1 shipped with inbound frames discarded — HITL answers from a tab were view-only. Closing that gap does NOT reopen a generic forge path: the mount wires `Options.WSInbound` to a desktop-owned dispatcher (`desktop/webaccess_inbound.go`) that resolves exactly the seven frontend→backend HITL response events through the same `desktop/event_handlers.go` handlers the Wails event listeners use — one authorization decision, two transports. A tab holds webview trust (decision 2's cookie boundary), so resolving a pending HITL action is an authorized operation; every other frame drops at Debug (network input must not write unbounded log lines), `EmitSessionEvent` stays denylisted so arbitrary events still cannot be forged into the trusted bus, and a judge flood is self-bounded (the handler acts only on a live pending entry). Frontend code needs no change: `runtime.ts`'s `emit()` already sent the symmetric `{name,args}` frames.

9. **The web SPA boots only after the transport probe settles, and App-level gaps surface through an explicitly pinned extra adapter (amendment from field diagnosis of the first real browser session).** Two defects surfaced when a late-joining browser tab met the real sidecar. First, the boot race: the web-transport probe is an async round trip, and a tab that mounted the app before it settled fired every mount-time RPC at `getApp()` while the transport was unresolved — the shim threw, and `App.tsx`'s one-shot splash→main safety net died without a retry, stranding the tab on an empty splash forever (the desktop window was immune only because Wails injects its bindings synchronously). The fix is a boot barrier in the gate — the app mounts only into a resolved transport — with the `'wails'` path short-circuited synchronously so the window never waits; a pre-auth tab also no longer opens the event socket (the upgrade could only 401-loop; login reloads the page and the fresh probe reconnects). Second, `GetPendingActions` — the HITL reconciliation sweep a session switch fires — lives on `desktop.App`, not `FrontendAPI`, so the reflection dispatcher 404'd it. Rather than moving app state into `backend` or widening the dispatch target to the whole App (which would expose the control RPCs decision 4 isolates), the mount passes a MINIMAL desktop-owned adapter (`webaccess_extra.go`) as `Options.ExtraDispatch`, consulted only when the primary surface lacks the method; the denylist governs the union, and the adapter's method set is pinned exactly by tests in both packages. Adding to it is a conscious, test-amended security decision, never a convenience.

10. **The address is pinned through one URL-style field; the credential is generated by default and written only through dedicated token RPCs (amendment: the reconnect UX demands stable coordinates).** An auto port and a regenerated-every-launch credential mean every desktop restart invalidates the browser's URL AND login — unusable for anyone who reconnects daily. Three RPCs answer this, all on `desktop.App` (decision 4's control surface), all persisting through the same immediate config write with the toggle's failure honesty:
    - `SetWebAccessConnection(bind, port)` pins the connection. The Settings field is URL-shaped ("http://0.0.0.0:9000") — the frontend parses it locally with a strict pattern (IPv4 octets bounded in the pattern, bracketed IPv6, the exact name `localhost`, port 1–65535), adds `http://` when the operator omitted it, refuses `https://` rather than silently downgrading, and an invalid value never reaches the backend. The token is deliberately NOT an argument: the credential has its own RPCs below, so the connection pin can never race a token write. An empty bind means the `127.0.0.1` default; validation reuses `config.ValidateWebAccessBind`/`ValidateWebAccessPort` (the exact load/save messages); the no-op check compares bind and port. Failure ordering: a failed PERSIST rolls the config flip back; a failed RESTART (e.g. the pinned port is taken) rolls the pin back, persists the previous one, and brings the sidecar back up on it — the app is never left silently without a sidecar it had before the call, and the error names both halves.
    - `SetWebAccessToken(token)` persists an operator-typed credential from the Settings token field: the value is trimmed and bounds-checked by `config.ValidateWebAccessToken` (8–256 characters; the empty value is rejected — emptiness means GENERATED, and the UI reverts the draft instead of saving an empty credential over a live one), then applies exactly like the rotation below: persist + hot-restart + rollback. A request matching the stored token is a no-op. A hand-edited static token in config.yaml stays possible and is warned when shorter than 16 characters at sidecar start — the interactive bounds deliberately do NOT gate the file: tightening the rule must never lock an operator out of their own config.
    - `RegenerateWebAccessToken()` rotates the credential: it mints a fresh token, persists it immediately, and hot-restarts a running sidecar onto it — every open browser tab must sign in again with the token Settings now shows. The same rollback discipline applies (a failed persist keeps the old credential; a failed restart restores it on disk and live). The token RPCs serialize under `webAccessMu` like every other lifecycle transition, so the two writers can never interleave a persist+restart pair.
    - **Minting is part of starting:** `startWebAccessLocked` finds an empty `web_access.token` on the very first start, mints, persists, and only then mounts the sidecar; if the persist cannot land, the start aborts loudly (a credential that would silently vanish on the next restart must never serve). The pin/token/rotation UI lives only in the desktop Settings block (hidden in the web transport — a tab cannot control the sidecar).

11. **The web transport adapts the workspace to the browser instead of emulating the desktop (amendment: the parity principle cuts both ways).** One emit funnel and one RPC surface give the tab desktop parity where it matters (sessions, tools, HITL); where the browser already provides the affordance, emulating the desktop is noise, not parity: the workspace tab bar is forced off (the gate flips `uiStore.tabsEnabled` before the app mounts — the tab layer's documented single-tab special case, so every reader stays consistent without transport-aware branches), the window title mirrors into `document.title` (`runtime.setWindowTitle`), the Settings blocks that would only ever render their dead states (Web Access control, the tabs master switch) are hidden, and notification banners come from the browser Notification API: the permission is a browser-site grant requested from real user gestures (the Settings toggle-on click, the Test button), and a banner click focuses the tab and replays `notification_clicked` LOCALLY through `runtime.emitLocalEvent` — the same validation guard and `useNotificationClicks` navigation the Go callback feeds, so no second routing path exists. Without a Service Worker the banners require the tab to be alive; a push/SW stage would be its own decision. Every branch keys off `isWebTransport()` and is inert on the desktop.

12. **The bind is operator-configurable under a warn-only exposure model (amendment: the motivating use case is reaching the app from another device on the operator's own network; amendment II, security-review fix round 2026-10-25: the PLAIN-HTTP non-loopback shape is no longer warn-only — it is refused by default behind the explicit `web_access.allow_insecure_lan` opt-in, enforced fail-soft at load, fail-closed at save, at the enable/re-bind/TLS-off boundaries and at the sidecar mount; warn-only survives for the loopback and TLS-encrypted classes and for the opted-in shape's accepted-risk warning).** `web_access.bind` accepts any IP literal — loopback (`127.0.0.1`, the `127.x.y.z` range, `::1`, IPv4-mapped forms), the unspecified wildcard (`0.0.0.0`, `::`), or a specific interface address — plus the exact name `localhost`, with `127.0.0.1` unchanged as the default (`config.DefaultWebAccessBind`). The predicates live in `backend/config`: `IsValidWebAccessBind` (the validity gate) and `IsLoopbackBind` (the exposure classification over already-valid binds). **Exposure is warn-only; the gate keys on validity, never on loopback class:**
    - **Load** is fail-soft on invalid values only (unparseable bind, empty bind while enabled, out-of-range port): a visible warning is emitted and the section resets to the safe default state (sidecar off, loopback, auto port, empty token). A valid non-loopback bind loads as-is with exactly one network-exposure warning; a reset lands on defaults, so reset-warning and exposure-warning never stack.
    - **Save** is fail-closed on the same invalid values only; a valid non-loopback section persists as-is.
    - **Sidecar start** (`internal/webaccess.New`) rejects invalid binds with the same messages (fail-closed) and warns once on a valid non-loopback bind — with no transport encryption the auth token is the only protection out there; loopback binds stay silent.
    - **Settings UI** renders the network-exposure banner whenever an enabled section classifies non-loopback, in addition to the ordinary full-control reminder.

    The rationale for warn-only: whether a given network is trustworthy is knowledge the app does not have and cannot encode; refusing valid non-loopback binds does not remove the exposure, it removes the supported way to get it (and pushes operators to unobserved proxies). What the app can do — and now does at every layer where the decision becomes live (load, start, UI) — is keep the consequence visibly in front of the user who made it. **TLS is its own decision ([ADR-102](./102-web-access-tls.md)):** the transport stays plain HTTP until the `web_access.tls` subsection turns on sidecar-terminated TLS (the cookie's `Secure` rides that switch); the load-time exposure warning narrows to the plain-HTTP combination (ADR-102 decision 7), while the section banner and the sidecar start log stay transport-aware on every non-loopback bind. **Browser-facing URLs never name a wildcard host:** `webAccessBrowserURL` rewrites `0.0.0.0`/`::` to `localhost`, passes specific IPs through as-is, and brackets IPv6; the info carries `configured_bind` and `bind_is_loopback` so the UI keys its banners on the backend's own classification.

13. **The sidecar additionally mounts only behind the master experimental gate: availability is the conjunction `experimental.enabled && web_access.enabled` (consolidated from the former ADR-091).** The surface is experimental-grade by any reading: a tab holds full control of the app by design (decision 2), a non-loopback bind rides the warn-only exposure model (decision 12), and the feature was amended in the field while shipping (decisions 8–12 all landed as post-ship corrections) — exactly the profile of surface the all-or-nothing master switch exists to keep off every default machine while it stabilizes. The gate's scope has a history ([ADR-044](./044-model-profiles-out-of-experimental.md) graduated Model Profiles out and left the switch "gating only the E2S execution mode"; [ADR-056](./056-research-always-on-global-seeding.md) aged that wording further; [ADR-068](./068-embedded-llm-frontend-experimental-gate.md) added the embedded model's frontend surfaces and recorded the rule — hide the UI, never the capability, so no stored config can silently diverge from effective behavior). Web access fits neither half of that rule alone and becomes its first recorded deliberate exception:
    - **The conjunction is enforced externally to the section, at the only two points where the app decides to mount.** The startup mount (`initWebAccess` in `desktop/startup_phases.go`) requires both switches — a closed gate is a QUIET skip (Debug — an intentionally-off feature is not a failure), leaving the event tap unset and nothing listening. The section stays pure data (a doc-comment in `backend/config/web_access.go`, no code): the loader, its fail-soft/fail-closed validity gates and every `web_access` RPC are untouched, and `internal/webaccess` never hears of the master gate.
    - **Both switches live-follow mid-session; no restart anywhere.** `UpdateExperimentalFeatures` (`backend/frontend_api_config.go`) persists `experimental.enabled` FIRST, then invokes the desktop hook carried through the `FrontendAPIConfig` seam (`OnExperimentalChanged` → `applyExperimentalWebAccess`, under `webAccessMu`) synchronously on the caller's goroutine — gate opened over an enabled section → mount (idempotent on a live sidecar); gate closed → bounded stop (the same budget `SetWebAccessEnabled` uses); every other combination a no-op. The hook fires ONLY after a successful persist — a rejected disk write starts or stops nothing — and the toggle RPC returns only after the sidecar transition it caused has landed. The lock order stays one-directional (`configMu` → `webAccessMu`; desktop code never takes `configMu` under `webAccessMu`). The section's own switch (`SetWebAccessEnabled`) is unchanged — under an open gate it keeps its exact pre-gate behavior.
    - **The frontend hides the block with the same conjunction.** The Settings → General Web Access block renders only while `experimentalEnabled && !isWebTransport()` — a reactive render guard in `SettingsModal`, so flipping the master switch hides/reveals the block within the same session without a reload; in the web transport the block stays hidden for decision 4's reason (a tab cannot control the sidecar).
    - **The inner toggle is preserved as the section's own switch.** `web_access.enabled` keeps its meaning, its file location and its writer; the master gate adds a precondition, it does not replace the switch. An open gate over a disabled section mounts nothing; a closed gate never promotes — nor demotes — the section switch into a second master.
    - **Why a backend-reaching gate is safe here (the ADR-068 exception, bounded by an argument the embedded model could not make):** a frontend-only gate would hide the Settings block while `web_access.enabled: true` kept mounting a full-remote-control listener at every startup — hiding the ONLY surface that shows the feature is on, the exact failure mode the rule exists to prevent. Stopping the sidecar for real is safe because nothing persisted depends on it running: no stored config references the listener, the generated credential is written by the sidecar's own start and re-read by nothing else, a stopped sidecar invalidates no stored state — which is exactly what made a backend gate dangerous for `embedded`.
    - **Upgrade behavior is intentional:** every `config.yaml` that opted into web access before the gate keeps its `web_access.enabled: true`, but the sidecar stops mounting at the first post-upgrade launch until the operator also turns `experimental.enabled` on — the feature is opt-in twice, and one silent service shutdown is the accepted price of the compound gate.

## Consequences

Positive:

- Near-zero cost to the existing app: two or three additive lines in `desktop/app.go`, a mount block in `desktop`, one additive backend method. No `backend`/`core` edit carries web knowledge, and the layering invariants hold untouched.
- `internal/webaccess` is testable without Wails, a webkit toolchain, or a window: plain `httptest` over HTTP + WebSocket covers the whole sidecar.
- The web UI tracks the desktop UI for free — both reflection dispatch and the generic event tap consume the surfaces Wails already exposes, so new RPCs and events appear in the browser without a sync step.
- Removal is a directory delete plus a handful of mounting lines; the feature cannot rot into the app's bones because nothing outside the sidecar and its mount knows about it.
- The event tap is web-agnostic: a future transport (headless, telemetry) can consume the same seam.
- One switch governs the app's experimental surfaces (E2S, the embedded frontend, the web-access sidecar): a default machine serves no browser listener, and the sidecar can keep evolving (TLS, a push stage) without every machine discovering it. The conjunction is enforced at the only two mount decisions plus the render guard — the section, the sidecar package and the backend config layer stay gate-free code.

Negative:

- Full control from the browser is an accepted, permanent consequence. Whoever obtains the session cookie on the listener's interface can drive the agent, including shell execution; the feature deliberately builds no finer authorization.
- The generated credential is a DURABLE secret persisted in config.yaml (accepted, recorded in SECURITY.md — a config-file reader outlives a restart and holds a working browser login). The secret never leaves the sidecar/Settings surface, but the file now carries a live credential from the first start on.
- On a non-loopback bind the surface is plain HTTP: an on-path observer can sniff the token and the whole session, then impersonate the operator with full remote control. The warnings state this; they cannot prevent it. The wildcard binds (`0.0.0.0`/`::`) listen on every interface, including ones the operator forgot exist (VPNs, docker bridges, tethered interfaces).
- Reflection dispatch is untyped at compile time. Method-surface errors surface at request time, and semantics that Wails handles specially (context-aware methods, native dialogs, some value marshaling edge cases) may need per-case handling at the mount as they are discovered.
- The emit seam adds one indirection on the desktop event path, and the tap widens the blast radius of a panic in a transport consumer — the tap must be defensive by contract (never alter, never block, never propagate failures into the Wails emit).
- A second serving surface of the frontend bundle exists (sidecar static FS vs Wails asset server); CSP and any asset-side hardening must now be reasoned about twice, mitigated by both being constructed at the mounting point.
- Native browser affordances (file pickers, dialogs) degrade to feature-detected alternatives; the web client is explicitly second-class for those flows until a future ADR says otherwise.
- The availability gate (decision 13) gives the experimental toggle RPC a sidecar transition on its critical path (bounded by the stop budget; start failures are logged fail-soft and loud, never fatal), and `GetWebAccessInfo`'s `enabled` (persisted intent) vs `running` (live state) can legitimately disagree after a failed start — the gate adds no third state.
- Pre-gate opted-in configs keep `web_access.enabled: true` but lose the listener at the first post-upgrade launch until the master switch is flipped — decision 13's accepted upgrade price.

## Alternatives Considered

- **Webserver inside `desktop/`** — rejected. It couples the HTTP/WS surface to the Wails lifecycle and types, makes the sidecar untestable without a window/toolchain, blurs `desktop`'s role down to "everything that talks to a user", and turns the removal path into surgery on the app core instead of deleting a package.
- **A headless binary now** — rejected. It doubles the build, release, and compatibility matrix before the browser use-case is proven, and it forces an immediate decision about which backend wiring the headless variant carries. The sidecar plus the surviving `runtime.ts` shim keeps the headless path open without paying for it now (it gets its own ADR when pursued).
- **Migrating to Wails v3** (multi-window/web-native serving) — rejected. The project is pinned to the Wails v2 line; a framework migration is a cross-cutting risk out of all proportion to the feature, and it still would not answer the "drive the app from another device" question that motivates the sidecar.
- **Relying on `wails dev`** — rejected. It is a development server, not a product surface: no auth model, dev-server semantics, no distribution story, and it answers none of the remote-access needs.
- **Keeping a loopback-only gate and documenting an external reverse proxy for LAN reach** — rejected as the product answer: it moves exposure behind c0wrk's back (unwarned, unobserved, often without the token gate if the proxy forwards unauthenticated), while the sidecar path keeps one credential model and one warning surface. The proxy route remains available to operators who want TLS today.
- **An explicit opt-in key (e.g. `allow_non_loopback: true`) beside the bind** — rejected: two keys to express one decision, a stale-boolean drift risk (bind changed, flag not), and no added safety — the warning set must exist either way, since the flag only *restates* the bind's loopback class.
- **TLS termination in the sidecar now** — rejected for this stage: certificate provisioning (self-signed warnings, ACME, trust-store handling) is a scope of its own, and half-done TLS (untrusted self-signed) trains users through browser warning screens. Deferred as decision 3's future stage.
- **Fail-closed on wildcard binds specifically** (require a specific interface address) — rejected: the wildcard is the idiomatic "every interface" answer on DHCP machines, and the specific-address pin breaks silently when the DHCP lease changes; the same exposure warning covers both.
- **An editable token field in the Settings pin block** — rejected: a second writer racing the generator/rotation on a live secret, a typed secret that must never linger on screen, and no added capability — the credential should be generatable, not transcribable; hand-set static tokens remain possible by editing config.yaml directly (with the short-token Warn).
- **A frontend-only gate (the ADR-068 pattern)** — rejected for web access: the block would vanish while `web_access.enabled: true` kept mounting a full-remote-control listener at every startup — hiding the only surface that shows the feature is on; the embedded gate could be frontend-only because nothing persisted depended on its hidden backend, and a serving listener IS the hidden backend.
- **Next-launch application** (gate checked only at startup, no live-follow) — rejected: the experimental switch is flipped in Settings, and "restart to apply" contradicts the hot-apply contract every other gated surface already honors; it would also leave `GetWebAccessInfo.Running` disagreeing with the revealed block until a restart.
- **Removing `web_access.enabled`** (master switch as the only gate) — rejected: it collapses two meanings into one key — the section's own opt-in (persisted beside bind/port/token, read by the sidecar package) and the app-wide development gate — and turns the upgrade into a silent rewrite of every opted-in config file.
- **A dedicated per-feature opt-in key** (e.g. `web_access.acknowledge_experimental: true`) — rejected: a third switch to express "this is experimental" is one more stale boolean drifting against the other two; the master switch already carries exactly that meaning app-wide.
- **Gating at the loader** (reset the section while the gate is closed, like invalid binds) — rejected: the loader's fail-soft resets are keyed on VALIDITY — a valid, enabled section is operator intent that must survive config round-trips untouched, and the persisted credential must never be touched by anything but the token RPCs and the first-start mint; mangling the section under a closed gate would destroy the state the feature promises to preserve.
