# ADR-067: Memory-Aware Embedded LLM Provisioning

## Status

Accepted — supersedes **D6** (the hard 16 GiB RAM floor) and **D10** (the RAM-tiered context, "never `-c 0`") of [ADR-066](./066-embedded-llm-runtime.md), and the *"and whenever memory is short"* clause of its **D2** (backend-driven packing). ADR-066 itself stays `Accepted`: every other recorded decision in it — D1 (Metal not MLX), D3 (artifacts outside `tools/`), D4 (hybrid provider representation), D5 (unload = stop the process), D7 (no reasoning-effort knob of its own), D8 (profile hint only), D9 (the full Windows backend matrix), D11 (the pinned fork, no auto-update), D12 (the Web UI off) and D13 (the unconditional readiness guarantee) — stands unchanged. Per [META.md](../META.md) an accepted ADR is immutable, so the superseded decisions are named here rather than edited in place, and D2's backend→packing table remains in force with only its memory clause replaced.

## Context

ADR-066 provisioned the embedded model from a **RAM-only** view of the machine, because that was the only view c0wrk had. `Resolve`'s entire signature was `(platform, backend, ramGiB)`, and the two outputs that decide whether a launch survives contact with the hardware were both derived from that one number:

- `-ngl` was a **constant** per platform and backend (`layersFor`: 99 or 0) — never a function of how much accelerator memory existed;
- `-c` was a **five-step RAM ladder** (`contextSizeFor`: 8192 / 16384 / 32768 / 65536 / 131072) — never a function of what the KV cache would actually cost on this machine.

Neither was a memory *decision*. Three concrete failures followed, and none of them is hypothetical:

1. **A machine that could run the model was refused.** D6's blanket 16 GiB floor keyed on system RAM alone. An 8 GiB laptop with a 24 GiB accelerator holds the weights, the KV cache and the compute reserve **on the card**; system RAM only carries the un-repackable weight spill and one CPU compute buffer — measured at **598 MiB** at full offload (`| - Host | 598 = 322 + 0 + 276 |`). The floor refused it on a number that described neither pool.
2. **A machine that could not run the model was accepted.** The same floor waved through 16 GiB of RAM beside a 4 GiB iGPU, where the 6539 MiB of device-resident weights plus a 65536-token f16 cache (4096 MiB) plus the 1377 MiB compute reserve and the 849 MiB projector reserve — **13011 MiB projected** — have nowhere to go. The launch then failed inside the runtime, after a 6–8 GiB download, with a `fit.cpp` abort rather than an actionable refusal.
3. **The tier ladder is the wrong instrument entirely.** The KV cost per token is a property of the *model* (65536 bytes at f16 for this one: `size = 16384.00 MiB (262,144 cells, 16 layers)`) and the capacity is a property of the *machine*. A ladder that maps RAM → context conflates them, so it is simultaneously too generous on a small discrete card and too stingy on a big unified pool.

Two prerequisites landed after ADR-066 and make a real decision possible:

- **`topology.go`** — `ProbeDevices` asks the *installed runtime* what accelerator memory it can see (`llama-server --list-devices`), and `buildTopology` derives the two budgets a fit decision may spend, with unified memory **detected** rather than assumed so a pool is never summed with the RAM it was carved out of.
- **`memory.go`** — `ModelMemoryProfile`, a per-term measured model of the one pinned checkpoint (every constant cited to a 2026-09-25 run of the pinned fork `prism-b10735-842b188`), with `ProjectDeviceMiB` / `ProjectHostMiB` reproducing the runtime's own dry-run and loaded breakdowns **exactly** (24450 / 16782 / 12686 MiB device, 598 / 23789 MiB host).

Requirement and capacity finally exist as separate, measured quantities. What was missing was the decision layer between them and the command line — and the pinned fork has its *own* decision layer for exactly that job (`--fit`), which had to be reconciled rather than ignored.

Two measurements shaped the defaults, and both are reproduced in the delegation record:

- `-np 4` inflates the fork's own projection from **24450 MiB to 77297 MiB** (`n_streams` becomes 4 when `kv_unified` is false), and `-np` also **splits** the context across slots (`-c 8192 -np 4` → `n_ctx_slot 2048`).
- `-ngl 99` beside `--fit on` **aborts** the launch. `common/fit.cpp` throws whenever `--fit` is asked to size an argument the caller already pinned — the throw sites at `:183` and `:462`, `:466`, `:472`, `:477`, `:480`, `:483`.

Finally, the pinned model's own issue tracker reports **empty and truncated answers as its most common complaint**, with the documented workaround `-n 16384` paired with "use `-c 65536`". Any floor below that reproduces the reported failure.

## Decision

`core/embeddedllm/plan.go` adds a **pure planner** — `Plan(MemoryTopology, ModelMemoryProfile, Tuning, Backend, GPUFamily) → (MemoryPlan, error)` — and `Resolve` is refactored to take a `ResolveInput` struct and delegate to it. Ten recorded decisions; the delegation's roadmap labels are mapped at the end of this section.

**D1 — planning is pure, and purity is a checked property.** `Plan` performs no I/O, no probing, no clock read and no package-state read: every input arrives as a value. That is what keeps the whole *(topology × profile × tuning × backend × GPU family)* matrix table-testable with no runtime, no GPU and no filesystem — the same invariant `Resolve` and `buildTopology` already held, now extended to the layer that decides memory. Two tests assert it structurally and behaviourally: `TestPlanImportsNoIOPackage` bans every I/O-, clock-, process- and network-capable package from `plan.go`'s import list (a runtime sandbox is not portable, so the guarantee is made structural instead — an import that performs I/O fails the test rather than silently making the planner impure), and `TestPlanIsPure` requires byte-identical plans across 16 concurrent calls and across two different `MemoryTopology.ProbedAt` stamps, which is the only clock-derived field in the inputs.

**D2 — fit exclusivity: exactly one decider, chosen by the override vocabulary alone.** The fork's `--fit` sizes both `-ngl` and `-c`, which makes it a direct competitor with this planner; if both decide, the loser is silently ignored — and the loser is not always the runtime. The fork resolves the ambiguity by **refusing** it (see the `fit.cpp` throw sites above, confirmed empirically). So:

| Condition | `-fit` | `-ngl` | `-c` | who sizes |
| --- | --- | --- | --- | --- |
| `Offload == Auto` **and** no `Devices` **and** `SplitMode == Auto` | `on` | **omitted entirely** | `0` | the runtime sizes layers and context |
| **any** of {explicit `Offload`, `Devices`, `SplitMode`} | `off` | passed | **computed here** | the planner, from `ModelMemoryProfile` |

`MemoryPlan.Layers` is a `*int` for this reason: `nil` means *omit the flag*, which is materially different from a pointer to `0` (`-ngl 0`, a real choice). `MemoryPlan.FitArg()` renders the literal `-fit` value and `EmitsLayers()` the omission, so the rule is testable exactly as it is stated. A `FitEnabled` override never breaks exclusivity: `false` forces the second row, and `true` beside an explicit offload **loses** to the rule and is recorded in `Notes` rather than silently dropped or spawned into a `fit.cpp` throw. An exact `Context` does *not* force fit off — it is not an offload override, and `--fit` adjusts only *unset* arguments, so a pinned `-c` survives beside `--fit on`.

**D3 — adaptive KV precision (roadmap D-C).** With `KVType` unset the planner tries **f16**, and if the target context does not fit the device budget it escalates to **q8_0** and then **q4_0**, recording every escalation in `Notes`. Precision is what gets spent first because it is nearly free: the fork measures q8_0 and q4_0 within ~1 % of f16 on this model (pp 342.0 / 342.6 against 343.5, tg 31.5 / 31.3 against 31.8 — PrismML-Eng/llama.cpp#191) while cutting the cache to 53 % and 28 % of its f16 size. `q5_0` is **not** in the ladder: the same issue measures it at pp 11.4 / tg 4.0 t/s, roughly 8× slower on long-context decode, and it buys no capacity over q4_0. An explicit `KVType` is honoured and never escalated; a precision outside `memory.go`'s closed set is refused with `ErrKVTypeUnsupported` wrapped in `ErrTuningInvalid`, never coerced.

**D4 — the fit floor is 65536 tokens, not the runtime's 4096.** `-fitc` is the smallest context `--fit` may settle on, and the fork's own default is 4096. That is a *does-not-crash* floor, not an *is-usable* one: given the pinned model's most-reported failure (empty/truncated answers) and its documented `-c 65536` workaround, letting fit shrink to 4096 would reproduce exactly that failure on every machine tight enough for fit to shrink — a server that loads, answers, and returns nothing useful, which is **worse** than a refusal because nothing reports it. 65536 also equals the tier `contextSizeFor` already grants a ≤71 GiB machine, so the fit floor and the explicit ladder stop disagreeing about what "usable" means. `DefaultFitMinContext` and the retained `upstreamFitMinContext = 4096` make the divergence quotable, and `TestPlanFitMinContextIsNotUpstreamsDefault` fails if they are ever equalized.

**D5 — one slot: `-np 1`, never the runtime's `-1` (auto).** Both measurements in *Context* argue the same way. Auto/4 more than **triples** the projection fit decides against (24450 → 77297 MiB), which on a machine between the two numbers is the difference between a launch and a refusal; and `-np` divides the context, so a plan that verified a 65536-token budget while passing `-np 4` would be provisioning four 16384-token slots — the D4 failure by another route. c0wrk serves one agent loop over one loopback socket and issues one request at a time per server, so a single slot is not a restriction; it is also the shape every `memory.go` figure was measured in (`-np 1` is in its reference command line). An override is honoured, and the plan notes the per-slot context it implies.

**D6 — the measured budget replaces the RAM floor, and only when it exists.** `ResolveInput.Topology == nil` keeps ADR-066 D6's `MinRAMGiB` gate verbatim, as the **first** check, because a caller that never probed has nothing better: the RAM tier is a worse estimate than a measured budget and a better one than nothing. With a topology present, the floor does not apply at all — the gate is the projection against `DeviceBudgetMiB` / `HostBudgetMiB`, and a shape no modelled precision satisfies is refused with `ErrMemoryPlanInfeasible` **carrying the arithmetic** (context, precision, both footprints, both budgets) so the UI can show *why* instead of a bare "not enough memory". This is what makes the two acceptance topologies come out right: 8 GiB RAM + 32 GiB VRAM **plans** (`TestPlanSmallRAMWithLargeVRAMIsViable`, with the host footprint strictly below the device one — the model really is on the card), while 8 GiB RAM + no VRAM **refuses** (`TestPlanSmallRAMWithoutVRAMRefuses`), and refuses even at an explicit 4096-token context, because the 6865 MiB of host-resident weights at `-ngl 0` alone exceed the 4096 MiB host budget.

**D7 — the RAM-only path deliberately does NOT delegate to fit.** Even though `--fit` needs no topology of c0wrk's to do its job, an unprobed machine keeps the explicit RAM-tiered shape. The reason is the consumer, not the runtime: a fit-sized plan has no concrete context, and the resolved context is what the manifest records and what becomes the `llm.models` `context_window` override — deterministically, at config-read time, when the server is not running and cannot be asked. D10's *override* mechanism therefore survives; only its ladder-as-the-only-source status is superseded. The plan says so in its `Notes`.

**D8 — a `Tuning` override vocabulary in which "unset" is representable.** Every field distinguishes *unset* from *set to the default value*, because the difference is load-bearing: an unset `-ngl` lets fit size the launch, while an `-ngl` that happens to equal the value fit would have chosen turns fit **off** (D2). Fields with a natural zero sentinel use it (`KVType`, `Packing`, `SplitMode`, `Devices`, `Context`, `Offload`); the rest are pointers (`FitEnabled`, `FitTargetMiB`, `FitMinContext`, `KVOffload`, `MMProjOffload`, `Parallel`, `CacheRAMMiB`, `HostReserveGiB`). `HostReserveGiB` is a **planner-side** budget knob and not a runtime flag — the pinned fork has no `--host-reserve` — and it *replaces* the topology's derived reserve rather than stacking on it. `TestTuningZeroValueIsAllAuto` pins the whole contract.

**D9 — `Notes` explains every non-default decision.** `MemoryPlan.Notes` is human-readable and surfaced in the UI verbatim, so each entry is a sentence an operator can act on and none is a debug dump. The contract is one-way: a plan with nothing overridden has nothing to explain beyond the fit delegation itself. `TestPlanNotesEveryNonDefaultDecision` tables nineteen single-field overrides — each changing exactly one knob, so a missing note names the field that lost its explanation rather than hiding among the others.

**D10 — the GPU family prices an unmeasured split; it does not gate on it.** `memory.go` documents that everything in it was measured on **Metal**: the weight, cache, recurrent-state and compute terms are model+runtime properties and travel across backends, but the device/host **split** is a property of each backend's repack support. So the family — classified from the `--list-devices` *description*, never from the backend, by the vocabulary `compat.go` owns — deducts a **policy** margin from the device budget: `0` for Apple Silicon (the measured family), `1024 MiB` for a recognized family nobody measured, `2048 MiB` for an unrecognized part, on the reasoning that unknown means unknown in both directions (the split *and* the compute-reserve behaviour). These two constants are the only numbers in `plan.go` that are not derived from a cited measurement, and they are labelled as policy in the source. A partial layer count (`-ngl 32`) is the one shape the profile does not cover, so its expected figures are conservative **bounds** — full-offload device, CPU-only host, both erring towards refusal — and the plan says so instead of presenting an estimate as a measurement.

**Roadmap labels.** This ADR implements the delegation's D-A/D-B/D-C/D-F/D-G/D-I set. The delegation text defined **D-C** explicitly, and that is D3 above (adaptive KV). The remaining letters were not defined in the delegation and are **not** guessed at here: the six decisions the delegation did specify are recorded as D2 (fit exclusivity), D3 (adaptive KV = D-C), D4 (the 65536 fit floor), D5 (`-np 1`), D6 (the measured budget replacing the RAM floor) and D10 (the GPU-family classifier and its allowance), with D1/D7/D8/D9 covering the purity invariant, the RAM-only path, the override vocabulary and the `Notes` contract. A later reader reconciling the two numbering schemes should treat this ADR's own D1–D10 as authoritative.

Also superseded in passing, and recorded for checkability: **`Resolution` gained a `Memory MemoryPlan` field** and `Layers`/`ContextSize`/`Packing` are now projections of it. Under a fit-sized plan `Resolution.ContextSize` is `0`, so a consumer that persists it must read `Memory.Fit` and treat the plan as *"no concrete context to record"* rather than *"context 0"* — the contract the launcher wiring inherits.

## Consequences

**Easier**

- A capacity question is now answered with two measured numbers instead of one guessed tier, and the refusal names its arithmetic.
- The whole decision matrix is table-testable with no GPU, no runtime and no filesystem, because the planner is pure and its purity is a checked property.
- Operator overrides are first-class and self-documenting: a tuned launch produces the notes that explain it.
- `fit.cpp`'s throw sites become unreachable by construction, rather than being a landmine the launcher wiring has to remember.

**Harder / costs**

- **Two sources of truth for the context, by design.** A fit-sized plan has no concrete `-c`, so anything that needs one at config-read time (the `llm.models` `context_window` override, D10 of ADR-066) must either read `Memory.FitMinContext` as the floor or fall back to the RAM tier. That consumer work is deliberately **not** done here; it belongs to the launcher/manifest wiring.
- **`LaunchSpec.Validate` still refuses a non-positive context** (`1..contextTierTop`), so it cannot yet carry a fit-sized plan. Widening it is a change to `server.go`, owned by the wiring task, and must be made together with the manifest's context field.
- **The split allowance is policy, not measurement.** Until CUDA/ROCm/Vulkan residency is measured, the 1024 / 2048 MiB deductions are a conservative guess with a label on it. A per-backend `ModelMemoryProfile` is the natural follow-up and would let both constants go to zero.
- **Three entry points into resolution** (`Resolve`, `ResolveProfile`, `ResolveMachine`) instead of one. They are nested conveniences over a single `resolveWith`, not three policies, but the surface is wider than it was.

## Alternatives Considered

- **Keep the RAM ladder and add VRAM as a second tier.** Rejected: it would still conflate a model property (KV bytes per token) with a machine property, and it cannot express "weights on the card, cache in RAM" (`-nkvo`) or a partial offload at all. The measured projection subsumes every tier it could produce.
- **Let `--fit` decide everything, always.** Rejected: `-c 0` under fit leaves nothing concrete to persist, which breaks the deterministic `context_window` override ADR-066 D10 exists to provide; and it forfeits the refusal — fit *aborts* rather than reporting a budget, so an undersized machine would fail after a 6–8 GiB download instead of before it. Fit is used where it is strictly better (sizing an offload c0wrk has no opinion about) and bypassed where c0wrk needs the number.
- **Always compute layers and context locally, never use fit.** Rejected: it duplicates a sizing pass the runtime performs against the *live* device inventory, using a profile measured on one backend. On a machine c0wrk's classifier does not recognize, fit's own measurement beats this planner's allowance-based estimate.
- **Shrink the context to fit instead of escalating the KV precision.** Rejected as the *first* resort: a smaller context is the failure mode the model's own issue tracker reports most, and precision costs ~1 % throughput where context costs the task. Context reduction remains available through an explicit `Context` override, and the 65536 floor is what stops it happening silently.
- **A blanket lower RAM floor (say 8 GiB) instead of a measured gate.** Rejected: it fails both directions at once — still refusing the 8 GiB + 24 GiB machine that works, still accepting the 16 GiB + 4 GiB machine that does not. The number was never the right axis.
- **Making `Plan` take a `*MemoryTopology` so "not probed" and "no devices" collapse into one input.** Rejected: `topology.go`'s own contract is that the zero `MemoryTopology` means *unknown*, never *no memory*, and conflating them would turn a failed probe into a refusal. "Not probed" stays a `ResolveInput`-level distinction (`Topology == nil`) with its own documented path (D7).
