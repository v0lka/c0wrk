# ADR-074: ChatGPT subscription authentication (browser OAuth sign-in)

## Status

Accepted

## Context

The `chatgpt` provider has always authenticated with a static API key in `config.yaml` (`llm.chatgpt.api_key`). A ChatGPT subscription, however, is not an API credential: subscription OAuth tokens are accepted only by the ChatGPT Codex backend (`chatgpt.com/backend-api/codex`), never by the public `api.openai.com` API, and are obtained through an interactive browser sign-in with the user's ChatGPT account — there is no key to paste.

Three properties of that credential shape force the design:

- **It is a long-lived secret.** The refresh token outlives the app and unlocks a paid account. `config.yaml` is plain text, hand-edited, pasted into bug reports; logs and error strings travel even further. A refresh token in any of those places is a credential leak by definition.
- **The endpoint is stateless and streaming-only.** The Codex backend answers non-streaming requests with an error, and it stores no responses server-side — a reasoning item must be round-tripped through its encrypted payload, or the model loses its reasoning chain across ReAct iterations.
- **The host contract is synchronous.** Every sp4rk caller expects one fully assembled `ChatResponse` per call; c0wrk's router, retry, judge, and token accounting are all built on that shape.

The question this ADR settles: how a desktop app wires an interactive, browser-issued, keychain-held subscription credential into a provider stack whose entries carry a static key — without changing any `api_key` configuration's behavior, without a silent fallback between the two credential kinds, and without breaking the assembled-response contract on an endpoint that streams.

## Decision

The `chatgpt` provider gains a second authentication mode — `llm.chatgpt.auth.mode: "oauth"` (ChatGPT subscription) beside the historical `"api_key"` default — backed by `backend/providerauth` (browser OAuth + OS-keychain persistence + token lifecycle) and a two-sided seam into the router build, mirroring the embedded-LLM loader seam. The decisions:

**D1 — Two modes, one enum, fail-closed.** `llm.chatgpt.auth.mode` is exactly `api_key` (the default; `ApplyDefaults` seeds the empty value) or `oauth`. `validate()` rejects any other value at load and the `UpdateLLMConfig` trust boundary applies the same enum — a typo fails the load rather than silently keeping key auth while the operator believes the subscription runs.

**D2 — oauth pins the endpoint; api_key is byte-for-byte historical.** In oauth mode `ToBuilderConfig` marks the chatgpt entry `SubscriptionAuth` and pins its `BaseURL` to `providerauth.ChatGPT().APIBaseURL` — subscription credentials are accepted only by the Codex backend. With the marker off, neither `TokenSource` nor `RequireStreaming` is ever set on the entry, whatever the seam carries: every `api_key` configuration is built exactly as before the mode existed.

**D3 — Browser authorization-code flow, PKCE, public client.** The sign-in is an OAuth authorization-code flow with PKCE (S256) and a single-use `state`, redirected to the loopback URI registered for the client — `http://localhost:1455/auth/callback` — served by a listener bound on that port on every loopback family the host provides (IPv4 `127.0.0.1` and IPv6 `::1`; browsers may resolve `localhost` through either). The issuer matches `redirect_uri` against the OAuth client's allow-list byte-for-byte: the numeric host `127.0.0.1`, a different path, or a different port is rejected with `invalid_authorize_request` before any login page renders, so the port is NOT negotiable — when it is busy the sign-in fails with an actionable error instead of silently moving to an unregistered port (no ephemeral fallback). The authorize request carries the Codex client's expected extras (`id_token_add_organizations=true`, `codex_cli_simplified_flow=true`, `originator=c0wrk`). It uses the public Codex CLI OAuth client id (no client secret — a public PKCE client usable by third-party clients). The FRONTEND opens the system browser (`runtime.BrowserOpenURL`); the backend never launches a browser on the interactive path. The flow serves exactly one request on the listener and validates `state` on it; a `DefaultCallbackWait` (5 min) bounds the redirect wait.

**D4 — Credentials live in the OS keychain, nowhere else — and only the minimal secret does.** `KeyringSecretStore` (go-keyring, service `c0wrk`, key `providerauth:chatgpt`) persists the credential; `config.yaml` never sees a token value, and no token material ever appears in a log line, an error string, an event payload, or an RPC result — only identity fields (email, account id, expiry) cross the boundary. The stored secret is DELIBERATELY minimal (schema v2): the refresh token plus the parsed identity, never the access or ID token. OS keychain bridges cap secret sizes far below a full ChatGPT token set — go-keyring's darwin backend shells out to `security add-generic-password` with a 4096-byte command budget and its Windows backend caps the credential blob at 2560 bytes, while the access and ID JWTs alone are multi-kilobyte (persisting the full set failed on macOS with `data passed to Set was too big`). A restored sign-in therefore starts with no access token and reconstructs the live token set with one refresh round-trip on its first `Token` call — lazy, so startup still performs no network I/O; a sign-in the issuer issued no refresh token for is failed outright (it could not be restored after a restart). On Linux a Secret Service (gnome-keyring) must be reachable; every store failure carries a platform-appropriate actionable hint, and a sign-in whose keychain persist fails is failed, not half-signed-in. ID-token claims (`chatgpt_account_id`, `email`) are parsed but not cryptographically verified — the token arrived directly from the token endpoint over TLS, so its origin is already trusted.

**D5 — `TokenManager` implements sp4rk's `llm.TokenSource`.** The provider resolves credentials per request through middleware (stamping `Authorization` and the `ChatGPT-Account-Id` / `originator` headers), so every SDK-internal retry attempt carries a freshly resolved token. The manager refreshes proactively (30 s before expiry), single-flight (concurrent callers share one refresh round-trip), reuses the old refresh token when the endpoint does not rotate it, re-parses identity from a rotated ID token, and maps `invalid_grant` / `invalid_client` to `ErrReauthRequired` — the sign-in-required error, not a bare 401. A failed persist after a refresh degrades durability (Warn), not availability.

**D6 — No API-key fallback. Ever.** In oauth mode the static `llm.chatgpt.api_key` still travels on the entry (untouched in config), but the token source overrides it on the wire on every request; when no account is signed in, a stand-in `TokenSource` (`signInRequiredTokenSource`) fails every request before any bytes reach the endpoint with the actionable "sign in with ChatGPT" error. The models stay visible and selectable; the requests fail loudly. A lingering key in `config.yaml` can never silently act as a fallback — the operator always knows which credential kind is running, and a metered key is never silently billed for a subscription they believe is active.

**D7 — Buffered streaming for the streaming-only endpoint.** The subscription entry sets `RequireStreaming`; sp4rk's Responses path then sends `stream: true` on the wire, pins `store: false`, and includes `reasoning.encrypted_content` — the stateless backend keeps no stored response, so the encrypted reasoning payload (round-tripped verbatim on the next request) is the only way to preserve the reasoning chain across turns. The final `ChatResponse` is assembled from the terminal event (`response.completed` / `response.incomplete`) through the same converter the synchronous path uses, so the assembled result is identical by construction and the host contract — one fully assembled response per call — is unchanged; text and reasoning-summary deltas are forwarded to `DeltaSink` when the caller set one, and a mid-stream `error` event or a terminal `response.failed` aborts with the event's code/message instead of a degenerate empty response. This is deliberately NOT the phase-observable streaming of [ADR-071](071-adaptive-llm-request-budgets.md) D13′ — no prefill/decode labels surface to the budget engine; that stays deferred. Streaming-on-the-wire is subscription-only: no `api_key` entry ever sets `RequireStreaming`.

**D8 — The seam mirrors the embedded-LLM precedent, both halves.** The token manager is owned by the backend layer that runs the browser flow, so it enters the router build through `BuilderSubscriptionAuthConfig` — a per-build form (`BuilderConfig.SubscriptionAuth`) plus a builder-level default (`OrchestratorBuilder.SetSubscriptionTokenSource`) that covers every build whose config carries no token source of its own, most importantly the per-session routers converted deep inside the session factory where the manager is not in scope. An explicit per-build source wins; otherwise the builder default applies — the same single-resolution-point rule as `embeddedSeam`. The sign-in lifecycle mirrors the live state into the seam (signed-in manager in, zero value out on sign-out) and rebuilds the judge and router BEFORE the `chatgpt_auth:state` success event fires, so a request issued after the event already carries subscription credentials.

**D9 — The oauth model list is the subscription's own catalog, not a curated guess.** The checklist's primary source is `FetchChatGPTModels`: a live GET of the ChatGPT Codex backend's model catalog (`{APIBaseURL}/models?client_version=<pinned Codex CLI release>`, authenticated with the same bearer + account headers as a chat request). The backend's response is NOT the public API's shape (`{"models":[{"slug":…}]}`, identifier `slug`) and its picker contract is the Codex CLI's: only `visibility=="list"` entries, ascending `priority` rank (1 = the flagship). `client_version` gates the answer PER MODEL: every catalog entry carries its own `minimal_client_version`, and a client reporting a below-minimum version is answered with a 200 and an **empty** `{"models":[]}` (verified live: `0.0.1` yields exactly that, silently) — so the request pins the current Codex CLI release (`chatGPTCatalogClientVersion` in `backend/frontend_api_auth.go`) rather than c0wrk's own build version, with `TestFetchChatGPTModels_ClientVersionPin` guarding the pin against a dev-placeholder regression. Registry-known slugs render with full catalog metadata; slugs ahead of the registry render with the endpoint's `context_window` and remain usable through the router's tier-5 registry fallback — the catalog is never clipped to what the registry knows, and new backend models appear the moment the subscription serves them. The curated registry-pinned preset (`GetChatGPTModelPreset`) is demoted to the offline fallback: it answers first so the checklist is never empty, and it is all that loads while signed out. The frontend hook keeps the two lists as separate state and never installs an empty live answer, so a failed or empty live fetch leaves the fallback rendered instead of a blank checklist. This replaces the earlier static-preset-only design, which under-listed the subscription (a hardcoded allow-list cannot track an entitlement that changes server-side).

## Consequences

**Positive:**

- A ChatGPT subscription becomes usable from c0wrk with no API key at all; the sign-in is the browser flow the user already knows from the ChatGPT product.
- Credentials live in the OS keychain — the plain-text `config.yaml`, logs, events, and RPC results stay secret-free by construction, enforced by the store/error/event layers rather than by convention.
- Failures are actionable by design: signed-out requests name the one fixing action (sign in), keychain failures name the platform remedy, and a `mode` typo fails the config load instead of flipping credential kinds silently.
- Every `api_key` configuration is byte-for-byte historical (D2/D6/D7 marker discipline), so the feature's blast radius on existing users is zero.
- The assembled-response contract holds on the streaming endpoint, so the router, retry, judge, and token accounting need no changes; `backend/providerauth` is profile-shaped, so a later Kimi/Claude subscription sign-in reuses it wholesale.

**Negative:**

- A new platform dependency: the OS keychain (on Linux, a reachable Secret Service) is now required for the feature — without it the sign-in refuses with a hint rather than degrading to plaintext storage.
- The OAuth client id and endpoints are pinned constants mirroring the public Codex CLI client; OpenAI rotating or revoking that client breaks the sign-in until a c0wrk update (deliberately no remote config — the client identity is supply-chain surface, see the tool-manager/ADR-010 pinning precedent).
- The oauth-mode model checklist is the subscription backend's OWN live catalog (`FetchChatGPTModels` — `GET {APIBaseURL}/models?client_version=<pinned Codex CLI release>`, `visibility=="list"` only, ascending priority rank, the same picker contract as the Codex CLI; the per-model `minimal_client_version` gate means a too-low `client_version` returns a valid-but-empty catalog, hence the pin), with the curated registry-pinned preset demoted to the offline fallback. A slug the registry does not know no longer blocks the list: it renders with the endpoint's `context_window`, and the router's tier-5 registry fallback keeps it usable, so new backend models appear the moment the subscription serves them.
- Two credential kinds now exist for one provider; the mode switch is persisted config state, so a draft opened before a mode flip can show a stale auth panel until re-read.

**Neutral:**

- The `chatgpt_auth:state` event and the five sign-in RPCs follow the embedded-LLM surface conventions (read-only getters return no error; mutations return actionable errors; the interactive flow never blocks an RPC on the user) — see [event-catalog.md](../contracts/event-catalog.md) and [desktop-frontend.md](../contracts/desktop-frontend.md).
- Startup performs NO network I/O for auth: `InitChatGPTAuth` only loads whatever the keychain already holds and mirrors the seam when the config selects oauth mode and an account was restored.

## Alternatives Considered

- **Store tokens in `config.yaml` (or a sibling file).** Rejected: plain-text secrets in a hand-edited, pasted-around file; the env-var `${VAR}` expansion path moves the problem to shell profiles, equally plain text.
- **Split the full token set across multiple keychain items.** Rejected: N-items-per-account keychain clutter and shrink-aware rewrite bookkeeping to persist bytes that carry no durable value — the access token is derivable from the refresh token by one round-trip, so storing it buys nothing (this is why D4 persists the minimal secret instead).
- **Silent fallback to the static `api_key` while signed out.** Rejected: credential-kind confusion — the operator believes the subscription runs while a metered key is billed, and the failure mode (an expired subscription silently degrading to key auth) is invisible from the UI. The loud error is cheaper than the surprise bill.
- **Device-code flow.** Rejected: the allow-listed public client is configured for the loopback redirect; the device flow is not supported for it, and the loopback listener is bound before the authorization URL is derived, so no redirect can race the listener.
- **Embedded webview for the sign-in page.** Rejected: the system browser is the trust anchor the user recognizes (password managers, phishing heuristics, certificate errors); an embedded webview trains the user to type credentials into app chrome.
- **Verify the ID token signature locally (JWKS fetch + validation).** Rejected: the ID token arrives directly from the token endpoint over TLS — verifying the issuer's signature on a value obtained from the issuer proves nothing further, and the JWKS fetch adds a moving part and a failure mode for zero trust gain.
- **Full incremental streaming into the host pipeline.** Deferred: it changes the `Provider`/caller contract across sp4rk and c0wrk (and is the ADR-071 D13′ prerequisite). Buffered streaming delivers the subscription endpoint today without touching that contract; real delta delivery is a separate feature if it is ever wanted.
- **A dedicated provider type for the Codex backend.** Rejected: the endpoint is OpenAI Responses-shaped; a marked existing `openai`-type entry with a token source and a pinned base URL reuses the whole existing path (protocol dispatch, model registry, budget wiring) instead of forking it.
