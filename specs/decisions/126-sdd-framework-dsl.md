# ADR-126: Render a recognised SDD framework through its declarative DSL (no shipped skillset)

## Status

Accepted

## Context

The Specs surface was built as one opinionated system: [ADR-105](./105-vendor-spec-skillset.md) vendored a six-skill `spec-*` skillset plus a `specs` Subagent Profile into `core/specs/skills/` and `core/specs/agents/specs/AGENT.md` and seeded both machine-globally at every launch; [ADR-106](./106-specs-sidebar-panel.md) added the Specs sidebar panel over a hand-written parser (`core/specs.ParseSpecsRoot`) that hard-coded ONE layout (`specs/{META.md,INDEX.md,architecture,domains,contracts,decisions}`); [ADR-108](./108-specs-panel-usability-redesign.md) and [ADR-109](./109-specs-panel-simplification.md) recomposed that panel around nine hard-coded integrity checks; [ADR-115](./115-sidebar-pack-gates-reconcile-and-serialization.md) made `specs.enabled` gate BOTH the sidebar tab and the pack lifecycle (seed/unseed, gate mirror, launch reconcile); [ADR-116](./116-specs-root-follows-active-session.md) made the hard-coded `<workspace>/specs` root follow the active session.

Three facts invalidated that shape:

1. **c0wrk's tree is one SDD dialect among several.** OpenSpec (delta-driven: `openspec/specs` as the source of truth, `openspec/changes` as per-change folders) and GitHub Spec Kit (`.specify/` project state plus `specs/<feature>/` artifact sets) are equally widespread. A fixed layout with a fixed check list cannot render them, and teaching the parser each one in Go would make every new framework a code change plus a privileged "native" grammar that an operator's own framework can never match.
2. **Shipping a skillset is an opinion the operator did not ask for.** Seeding it machine-globally bought versioned packs, content-hash classification, `.seed-version` markers, unseeding, gate mirrors and a launch reconcile — a large body of code whose only product is writing files into a user's global agent directory. The workflow a workspace actually uses is decided by the framework that workspace installed, not by c0wrk.
3. **The surface needs no privilege over the tree.** Every mutating gesture was already a dispatched skill, so the panel's only real job is: decide whether a framework is installed, parse its tree, render declared views/actions/findings.

## Decision

**1. A framework is a declarative document.** `core/sdd` models an SDD framework as one `sdd-framework/v1` YAML document — `schema`, `id`, `label`, `description`, `docs_url`, `priority`; `detect` (marker files plus a skill probe: declared skill directories, `all_of`, `any_of`); `roots` (workspace-relative directories addressed by ID); `concepts` (a `match` glob with `*`/`**` and an optional `dir`, companion `files`, `extract` directives, per-instance `required` assertions); `checks` (the closed vocabulary of eight integrity kinds — `required_files`, `name_pattern`, `crossrefs`, `index_completeness`, `frontmatter_keys`, `content_regex`, `unique`, `references`); `actions` (label, dispatched `skill`, `prompt`, optional `concept`, `requires` tokens `root` / `findings` / `concept:<kind>` / `companion:<kind>` / `absent:<kind>`); `views` (ordered `tree` / `findings` / `checks` sections over concept kinds). Parsing is STRICT: an unknown YAML key, an unknown schema, an unknown check kind, an extraction directive or a parameter belonging to another check kind is a load error. The built-in frameworks are the same documents parsed by the same code, so there is no privileged in-code representation.

**2. Three built-ins, two operator files, one merge rule.** The embedded catalog is `sdd` (c0wrk's own hand-written tree), `openspec` and `spec-kit`. An operator adds a framework or overrides a built-in wholesale in `~/.c0wrk/specs.yaml` (global) and then `<checkout>/.c0wrk/specs.yaml` (project) — YAML streams of complete documents merged BY ID, earlier sets first, so a later file either adds an ID or replaces that definition in full; nothing can remove a built-in. Loading is fail-soft per document (a broken stream or an invalid document is a warning naming it while the documents around it still apply) and strictly read-only: the files are optional, never created, and an absent file is the neutral state. The merged catalog is ordered by `priority` then `id`, so detection never depends on write order.

**3. Visibility is skill detection; the tree is only the tie-break.** A framework is recognised when the skills its own `init` installs are present (`all_of` satisfied and, when declared, at least one `any_of`), matched through the `spec-` ↔ `vibespec-` alias prefixes so an upstream copy names the same skill. Installed skills are classified in three tiers — project (inside the checkout, including framework-declared directories such as `.claude/skills`), c0wrk global, user. Declared markers and roots are the TREE signal only: they never make a framework visible, they order the default selection (tree present first, then strongest skill tier, then declaration order) and feed the empty state. Zero recognised frameworks means no Specs surface at all.

**4. The active framework is the operator's selection, else detection's default.** The selection is persisted per project (`project_ui_state.active_sdd`, RPC `SetActiveSDD`); a non-empty id must be DETECTED for that project or the call fails, and an empty id clears the selection and restores the default. More than one recognised framework with no persisted choice raises the selector's `selector_needed` hint; the panel shows a selector that renders the chosen framework immediately while the re-parse it triggers is still in flight.

**5. Parsing goes through the definition and nothing else.** `sdd.ParseTree` walks the declared roots, classifies every path against the declared concepts (the most specific glob wins, so a container concept such as `changes/*` coexists with `changes/archive/*`), extracts only the metadata a concept declares, renders the declared views and runs the declared checks. A finding exists only because a DECLARED check failed, and a file no concept matches never enters the model. Every read is containment-checked against the workspace (a root or entry escaping through a symlink is excluded with a warning), bounded per document, and strictly read-only, so the same call serves every refresh.

**6. The tree follows the active session; the DSL file does not.** The tree is parsed in the workspace the ACTIVE SESSION resolves to (a session worktree when one resolves, the project checkout otherwise — ADR-116's protocol), so an agent's specifications are what the panel shows. The checkout-local operator file is read from the project CHECKOUT, never from the session tree: it is repository data that travels with the clone, not agent output. `sddWorkspace` and `sddCheckout` name the two roots so they cannot be confused.

**7. c0wrk ships no skillset.** The vendored `spec-*` skills, their `assets/`, the `specs` Subagent Profile and the whole seeding/unseeding machinery (`core/specs/skillpack.go`, `agentpack.go`, `unseed.go`, `core/specs/LICENSE.md`) are removed. c0wrk neither seeds nor unseeds agent skills for this surface: a workspace's SDD skills are ordinary agent-skill data installed by the framework's own `init`, and detection recognises them wherever they live — project, c0wrk global or user tier. Copies already seeded by an earlier c0wrk version are left untouched (deleting operator-visible files to tidy up after a feature removal is worse than leaving them). The hand-written reader (`core/specs/model.go`, `core/specs/parse.go`) survives only as the parity oracle `core/sdd/tree_test.go` compares the DSL parse against; no production code imports it. This **supersedes ADR-105 decisions 1–4** — the six-skill vendoring, the `WORKFLOW.md` stance that flowed from it, the bundled Subagent Profile, and the "seed globally, always on" invariant including its version-marker/reconcile machinery. ADR-105 decision 5 stands: `core/seedpack` remains the shared seeding core for the packs that DO ship (research, papers).

**8. `specs.enabled` becomes a pure visibility gate.** `SetSpecsEnabled` persists and announces `config:updated`, and nothing else: no seed, no unseed, no gate mirror, no launch reconcile for this surface. This **amends ADR-115**, which stated the gate's contract for BOTH sidebar surfaces symmetrically: the research half (packs, launch reconcile, `researchSeedMu` serialization) is unchanged and ADR-115 stays the authority for it, while its specs half is superseded by this decision. A disabled Specs gate hides the tab and the panel; the recognition, the DSL files, the roots and the read RPCs are untouched by the toggle.

**9. The panel renders only what the DSL declares.** View sections render in declaration order (a framework that declares no views falls back to one implicit tree over the forest's root nodes); actions become gestures only when they carry a `skill` — a framework that declares no `fix-findings` action keeps an inert findings badge, and one that declares no bootstrap action renders no empty-state CTA; a node-scoped action renders on the instances of its concept with `{path}`/`{name}` substituted; panel-level actions render in the quick-actions row with the backend's evaluated `available` flag, and an unmet requirement renders inert with a reason instead of disappearing. Every mutating gesture dispatches the declared skill into the chat through `sendMessage`'s `activeSkills` slot; the panel never writes to the tree, so no declared prompt can act without a user click and every resulting tool call passes the ordinary policy/judge/confirmation pipeline.

**10. The tab is `gate ∧ detected`, with an explicit unknown state.** The workspace tab strip answers visibility BEFORE the panel mounts (a hidden tab never mounts it), so the framework projection lives in `sddStore`, fed by the panel's own parse — one RPC, one authority, the parse stays in `specsStore` and pushes each status through. Before a project's first answer the tab stays visible (unknown is not absent, and the panel's parse is what discovers detection); after it, `present` is authoritative, and a remembered Specs tab falls back to the layout's primary tab by the same rule the indexing and research gates established.

## Consequences

- Adding a framework is a YAML document — embedded or operator-authored — never a Go change. An operator's private layout is a first-class citizen with the same primitives the built-ins use, which is also the honest limit: a framework whose invariants fit none of the eight check kinds needs a new kind (a reviewed code change), not a private extension.
- The Specs surface stops asserting which workflow a workspace should use, and c0wrk stops writing agent skills into a user's global directories. The cost is that a fresh machine has no `spec-*` skills: the built-in `sdd` framework's actions name them, so its lifecycle gestures do real work only where the operator (or a previous c0wrk version, whose copies remain) installed them; other frameworks name their own skills.
- One panel serves three dialects, so the panel lost its c0wrk-specific vocabulary: no fixed DECISIONS section or quick-action set — the tree's date column appears on any dated document the active framework parses, and labels, findings, gestures and the empty state all come from the active document. A framework that declares nothing renders an empty surface, which is a DSL bug, not a panel bug.
- `core/sdd` is now the largest pure package on this path (framework schema, detection, parser, checks) and its failure mode is data: a malformed operator file yields warnings on the panel's warning strip while every other definition still applies, and a strict parse error in an EMBEDDED document empties the built-in catalog behind one loud warning — deliberately, because a built-in that does not validate is a build defect, and `core/sdd/builtin_test.go` pins the embedded set so it fails the build first.
- Two roots are in play and they differ on purpose (session workspace for the tree, checkout for the operator file). A user who edits `.c0wrk/specs.yaml` inside a session worktree sees the checkout's copy win; that asymmetry is the point (operator data is repository data) and is named in the domain spec so it is not "fixed" later.
- The repo-provided `.c0wrk/specs.yaml` arrives with a clone, so it is semi-trusted input: it can shape what the panel probes and renders and which skills its actions dispatch, but it cannot read outside the workspace root, execute anything by itself, or run a tool without the user's click and the policy pipeline. See `specs/domains/sdd-dsl.md` (Security).

## Alternatives Considered

- **Keep the vendored pack and add per-framework branches to `core/specs`.** Rejected: it makes c0wrk's own layout the privileged grammar and turns every other framework into special-case Go code, while keeping the seeding machinery whose only purpose was delivering that one skillset. Every framework — including an operator's — should be expressible with the same primitives.
- **Keep seeding the `spec-*` pack as a default while also supporting other frameworks.** Rejected: two authorities for one surface (a shipped workflow and a detected one), and the whole pack lifecycle (version markers, unseed, gate mirror, launch reconcile) would still have to be maintained for a default the operator never asked for. The existing seeded copies remain on disk and keep working, so nothing breaks for an installed machine.
- **Detect frameworks by tree markers instead of installed skills.** Rejected: visibility would depend on the tree, so an installed framework with no tree yet (the exact state the empty state and the `init` action exist for) would be invisible, and a foreign repository's `specs/` directory would summon a panel for a framework nobody installed. Markers stay the tree signal and the default-selection tie-break.
- **Auto-install a framework's skills (or run its `init`) when a workspace is detected without them.** Rejected: c0wrk would decide the workflow and write outside its own directories; installing or initialising a framework is the operator's action, which the panel already offers through declared bootstrap actions dispatched into the chat.
- **Read the operator DSL file from the session workspace.** Rejected: `.c0wrk/specs.yaml` travels with the repository; a worktree copy would be a second, silently diverging authority for how the SAME tree is parsed, and an agent writing there would change the panel's rendering of committed data.
- **Keep the hand-coded nine checks alongside the DSL's eight kinds.** Rejected: two check vocabularies mean the panel's findings depend on which parser ran; the DSL's kinds cover every check the hard-coded set performed (root files, key-file paths, ADR name/number/duplicate/supersession, cross-refs, index completeness), and c0wrk's own tree declares them in `core/sdd/frameworks/sdd.yaml`.
