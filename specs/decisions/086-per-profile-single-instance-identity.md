# ADR-086: Per-profile single-instance identity

## Status

Accepted — amends [ADR-075](./075-single-instance-lock.md) D1 (the lock identity is no longer the macOS bundle identifier; it is derived from the agent directory) and extends D4 (a second instance is still never a supported state over ONE agent directory, but parallel agent directories are now independent lock/relay domains); D2 (focus-only relay) and D3 (the app-level advisory lock gating crash capture) are unchanged.

## Context

ADR-075 fixed the Wails `SingleInstanceLock` identity to the constant `com.wails.c0wrk-desktop` — one lock identity per machine. That makes the documented hermetic whole-app launch ([domains/testing.md](../domains/testing.md): an isolated `$HOME` exported before launch, relocating `~/.c0wrk` wholesale via `os.UserHomeDir()`) impossible to exercise while the real instance runs: the isolated-home process resolves a different agent directory, but under the fixed identity it derived the SAME `UniqueId`, found the running instance's platform lock, and relayed into it — focusing the production window and exiting instead of booting the test instance. The second-instance machinery and the isolated-second-instance workflow were mutually exclusive, so isolated test launches of a second instance could only happen when no other c0wrk was running.

Everything the lock protects, however, is already scoped to the agent directory, not to the machine or user account: the SQLite database, session/project storage, the embedded-LLM supervisor, tool manager, watchers, and the app-level advisory lock itself (`config.SingleInstanceLockPath(agentDir)` → `<agentDir>/app.lock`) all live under `~/.c0wrk` as resolved by `config.AgentDir()`. Two full instances over two DIFFERENT agent directories share none of that state — the hazard ADR-075 eliminates (two processes mutating one `~/.c0wrk`) cannot arise across directories. The crash-capture gate and the updater's first-instance-only staging sweep were already keyed on the per-directory app lock; only the Wails identity lagged behind, serialized processes that share nothing, and blocked a legitimate workflow.

## Decision

**The lock identity is always derived from the canonical agent directory** — `desktop.SingleInstanceLockIDFor(agentDir)` in `desktop/singleinstance.go`:

```
UniqueId = SingleInstanceLockID + "_" + hex(sha256(canonical agentDir))[:12]
```

`SingleInstanceLockID` (`"com.wails.c0wrk-desktop"`) is kept as the stable, greppable **prefix** only. The ADR-075 D1 alignment of `UniqueId` with the macOS bundle identifier is **deliberately severed**: nothing resolves the constant as a bundle id anymore, and the trade is safe because the Wails relay keys on the `UniqueId` alone, never on the bundle id matching (verified against the Wails v2.16 per-platform sources). Canonicalization is lexical first, filesystem second — `filepath.Clean` → `filepath.Abs` → `filepath.EvalSymlinks`, degrading softly to the Clean+Abs form on any resolution failure — and deliberately performs NO `user.Current()` lookup (see Alternatives Considered). `main.go` passes `config.AgentDir()`, so the lock identity keys on exactly the directory every other subsystem already keys on. The 12-hex-char (48-bit) suffix keeps the derived platform names compact and valid: a letter-led D-Bus bus-name element stays `[A-Za-z0-9_]`-only (Linux fail-open semantics make determinism a correctness requirement — an *invalid* bus name would kill the relay permanently), hex is a safe darwin lockfile name (`<native temp dir>/<id>.lock`, fail-closed — determinism is what keeps the fail-closed semantics honest), and hex is Win32 object-namespace-safe (session-local mutex/window names).

**Ordering invariant.** `main.go` derives the id (inside `SingleInstanceOptions`) only AFTER `AcquireSingleInstanceLock` — whose `safeio.MkdirAllReal` guarantees the agent directory exists. A first run computing the id before the directory exists would fail `EvalSymlinks` and silently pin the unresolved form while every later launch resolves it: two identities for one directory across restarts, which on darwin's fail-closed path would let a second process boot a full app over the first one's state instead of relaying.

**Per-profile relay.** Because the identity (and with it each platform's relay channel — D-Bus bus name, darwin lockfile, Windows mutex/window class) is per agent directory, parallel agent directories are independent lock domains: a second launch of profile A relays to profile A's first instance only, and never disturbs profile B. Within one agent directory the ADR-075 invariant holds verbatim — **exactly one** process ever reaches `OnStartup`.

**Isolation modes (extends ADR-075 D4).** D4's refusal of a second instance over one `~/.c0wrk` stands: there is deliberately still no `single_instance.enabled` knob and no env override for the identity itself. What the per-directory identity enables is fully isolated parallel profiles, in two documented shapes:

- **home_only** — the operator replaces `$HOME` for the launch (the testing convention: a fresh `mktemp -d` exported as `$HOME` before exec). `config.AgentDir()` then resolves the agent dir inside the substitute home, the derived `UniqueId` differs, and the process boots as the first instance of its own profile: own database, own crash-capture marker, own app-level lock.
- **full isolation** — a second OS user, container, or machine: a different home by construction, same derivation, same outcome.

**Banner-click outcomes with two instances.** macOS attributes a banner click to whatever process LaunchServices resolves for the app bundle — and a LaunchServices-spawned process never inherits the operator's terminal environment (the same Finder limitation that motivates `config.LoadShellEnvironment()` running before any other init on macOS). Therefore every GUI-spawned launch — Finder double-click, dock, stale-bundle banner-click spawn, updater relaunch — resolves the REAL home and the REAL profile's identity: with the real-profile instance running it relays into it (focused), without one it boots a real-profile first instance. The isolated-profile instance can never be a banner-click relay target and never receives click routing; its tasks are untouched either way, and its window is reachable only directly. **macOS caveat (follows): a non-default profile must be exec'd from a terminal (or another parent process) that exports the overridden `$HOME`** — no Finder/LaunchServices launch can express it, and on macOS even the self-update relaunch goes through `open -n` (LaunchServices), so the override does not survive an update restart there (on Linux/Windows `relaunchApp` passes `os.Environ()` explicitly, so the profile survives the relaunch).

**Updater note — two "first" instances.** Each profile now legitimately runs the first-instance-only startup tail: crash capture AND `updater.CleanupStaleUpdaters`, both gated behind that profile's app lock in `main.go`. Two concurrent instances therefore mean two concurrent sweeps over the shared OS-temp updater artifacts (`updaterStagingBase()` is `os.TempDir()` on every platform). This is benign by construction: the reap skips everything younger than `cleanupStaleMaxAge` (24 h, `core/updater/installer_util.go` — the review-finding-#37 liveness bound treats an in-flight download or a staged apply pending relaunch as LIVE), so one instance's sweep can never reap the other's in-flight update staging; it may only reap the other's genuinely >24 h-stale leftovers, which is the sweep's purpose. Download staging is per-profile anyway (`config.UpdateStagingDir` → `<agentDir>/update-staging`). A self-update applied by one profile with the other alive is likewise documented-benign: the two-process flow (`--self-update`) waits only for the UPDATING instance's pid, swaps the shared install tree (previous tree retained as the `.old` rollback backup), and relaunches that instance; the other profile keeps executing its current build — its running image is unaffected by the tree rename — until its own check/update/restart. Two c0wrk builds transiently running side by side, one per profile, is a supported state; two instances of one profile over one agent directory remain impossible.

**Upgrade window (one-time, mixed code generations).** The derivation is a one-way identity change with no compat shim: binaries built before this ADR carry the bare `SingleInstanceLockID` constant, binaries built with it derive `…_<hash>`, and an old binary cannot be retrofitted. While a pre-ADR instance is running over an agent directory, a post-ADR launch pointing at the SAME directory derives a different id, misses the running instance's platform lock, and boots a full second instance — the one-profile-two-instances state D4 eliminates is transiently reachable across the generation boundary, in either direction (a stale old binary launched beside a post-ADR one reopens the same window). The damage is bounded one layer below the identity: the advisory `app.lock` is keyed on the directory, not the generation, so the second process reports not-first and skips both first-instance-only startup tails — the crash-forensics install and the stale-updater sweep (D3, `main.go`) — but it still reaches `OnStartup` and shares the live database, which is the very hazard ADR-075 closes. The window self-heals: once every running process derives its id, the deterministic contract holds verbatim over the new id — it is one window per generation, reopening only if the derivation itself ever changes (the pinning tests make that a deliberate act). Realistic exposure is narrow — the updater flow waits for the running instance's pid before swapping the tree — so it amounts to a dev loop (`make build` beside a running instance) and manual launches inside the update window; the rule is to quit the pre-ADR instance before launching the post-ADR binary over the same agent directory. Relaying the post-ADR launch into the pre-ADR instance instead of starting (detecting the busy advisory lock and relaying) was considered and rejected: a durable design change to ADR-075's second-instance semantics aimed at a one-time, self-healing window.

## Consequences

**Positive**

- Isolated whole-app test launches (the [testing.md](../domains/testing.md) hermetic convention) boot for real while the production instance runs — they no longer relay into the user's real instance, and a stray second open of a test build no longer steals the production window's focus.
- The lock finally has the same scope as the state it protects: one agent directory, one lock domain. The crash-capture gate and the updater's first-instance-only sweep needed no changes — they were already per-directory via `config.SingleInstanceLockPath(agentDir)`.
- Per-user/per-session platform namespaces stay collision-free and greppable: the stable prefix keeps diagnostics searchable, the home-embedding path hash separates parallel users/sessions (darwin per-user temp dir, Windows session-local names, distinct D-Bus elements on a shared session bus).
- ADR-075's behavior is untouched for the default deployment (one instance, one agent directory): the default profile's id changed shape, not semantics.

**Negative / trade-offs**

- The cosmetic bundle-id coupling is severed: a changed bundle id no longer even nominally tracks the lock constant (harmless — documented on `SingleInstanceLockID`; the relay never depended on it).
- 48 bits of path hash are collision-resistant for realistic profile sets, not adversarially collision-proof — irrelevant in practice: an attacker who can choose the agent directory path already owns everything under it.
- A GUI launch cannot target a non-default profile (the env override does not survive Finder/LaunchServices, nor the macOS `open -n` relaunch); non-default profiles are terminal-managed by design. A launchd-level wrapper could change this and was deliberately not pursued.
- The D-Bus name, darwin lockfile, and Windows mutex names now embed a path hash — slightly less obvious in diagnostics, mitigated by the stable greppable prefix.
- A one-time upgrade window around this ADR's adoption: a pre-ADR binary and a post-ADR binary over one agent directory never meet in lock space, so a mixed-generation pair transiently runs two full instances of one profile (bounded by the directory-keyed advisory lock; self-heals once every running process derives its id — see the Decision note).

## Alternatives Considered

- **Derive the home from `user.Current()`** (passwd) instead of the agent directory path. Rejected on three counts: it is a second source of truth for the home directory that can drift from every other path helper (`config.AgentDir()` already embeds the home); under the very isolation this ADR serves (home_only swaps `$HOME`, not the passwd entry) it would resolve BOTH profiles to the same passwd home — collapsing them into one identity and reintroducing exactly the relay-steals-isolated-launch bug this ADR fixes; and a pure path hash keeps the derivation free of `/etc/passwd`/getpwuid behavior differences across build modes (the module is not globally cgo-free, but the lock path should not depend on it either).
- **Keep the fixed constant and add an env override for the `UniqueId`** (e.g. `C0WRK_INSTANCE_ID`). Rejected: a configuration surface for lock identity is exactly what ADR-075 D4 refuses — an escape hatch lets two processes share an identity while pointing at the same agent directory, silently dropping the one-instance guarantee, and moves the correctness burden onto every launcher instead of deriving it from the one thing the lock protects.
- **Derive from a runtime value** (pid, port, timestamp). Rejected: nondeterministic across restarts breaks the darwin fail-closed contract — every launch of the same profile must compute the same id or second launches boot full apps over running state.
- **Route banner-click navigation across profiles** (revisit ADR-075 D2's focus-only contract now that two instances can coexist). Rejected: orthogonal to identity — the click's routing payload still reaches only the process macOS attributes the click to, so the per-profile relay changes nothing about what that path can recover; D2 stands.
