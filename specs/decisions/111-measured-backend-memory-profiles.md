# ADR-111: Measured Backend Memory Profiles

## Status

Accepted

## Context

The memory model (`core/embeddedllm/memory.go`) was measured on exactly one tuple: Metal on Apple Silicon (2026-09-25). Every other (backend, family) pair was priced from those Metal figures as a documented estimate, and the planner charged each unmeasured tuple a policy premium for it — `splitAllowanceMiB`'s 1024 MiB (2048 for an unrecognized part) held back from the device budget because nobody knew how a foreign backend divides the model's terms between device and host. The estimate was honest but blunt in one direction: the planner's projections carried a per-context compute reserve that was a Metal SCALAR (`ComputeDeviceMiB` 1377 plus a +12 MiB quantised-cache extra), and the CUDA measurement proved that shape wrong twice over — on CUDA the reserve is an order of magnitude smaller (166–730 MiB) and it GROWS with context and KV quantisation, where Metal's shrinks.

On 2026-11-03 the CUDA side was measured end to end: the pinned fork (`prism-b10735-842b188`), the cuda-13.3 build, an RTX 5060 Ti (NVIDIA Blackwell, 15938 MiB), PQ2_0 weights, four full `llama-server` runs (32768/f16, 65536/f16, 65536/q8_0, 131072/q8_0 — logs SHA256-recorded in `core/embeddedllm/testdata/cuda-measured/`, transcribed with methodology in `docs/development/embedded-llm-cuda-measurements.md`). The measurement carries a per-term device/host split that finally makes the CUDA tuple's projection a measurement rather than an estimate — which turns three questions into decisions: where the new figures live, how a context-dependent reserve is represented, and what the newly honest budget means for the split allowance and the auto context target.

## Decision

Codify the measurement as a second **measured backend memory profile**, keyed on the (backend, family) tuple end to end:

1. **The overlay (D1).** The CUDA figures land in `memory.go` as a self-contained overlay — `cudaComputeCurves` (the four measured compute knots with their host halves), `cudaDeviceWeightsMiB` (6543, the loaded `model` column), `cudaHostWeightSpillMiB` (322) — selected by `shapeFor(backend, family)`/`cudaShape` for exactly one tuple: a CUDA backend (any pinned asset tag; the buffers belong to the fork pin and the silicon, and cuda-13.3 is the build actually measured) on `GPUFamilyNVIDIABlackwell`. Unmeasured tuples keep pricing the Metal default, which stays the documented estimate, never a hidden fallback (`TestCUDAProfileFallsBackToMetalForUnmeasuredTuples` pins ten such tuples); PTQ1_0 on CUDA refuses (`ErrMemoryNotMeasured` — only PQ2_0 was measured), and the projections' signatures carry `(backend, family)` so a plan and the packing decision can never disagree about which silicon they price.

2. **Tuple-scoped profiles and split policy (D2).** A profile is a property of the (backend, family) tuple, and the planner's split allowance reads the same tuple: the append-only `measuredSplitTuples` table in `plan.go` lists exactly the tuples the overlays cover — Metal/Apple Silicon and CUDA/Blackwell — and `splitAllowanceMiB(backend, family)` pays **0** on a table row, so a measured card's device budget is exactly the topology's own (RTX 5060 Ti: 15938 − the universal 1536 MiB margin = 14402 MiB, which is what `TestMeasuredCUDATupleBudgetAndProjections` pins together with the measured-tuple projections: 11836 MiB at 65536/f16 and 12624 at 131072/q8_0 fit; 15932 at 131072/f16 honestly does not and is never chosen — the planner's ladder starts above f16 at that context). A recognized unmeasured tuple keeps paying 1024 MiB and an unrecognized part 2048 MiB. The table and `shapeFor` must cover the same tuples — one test pins both sides — and a plan's `Notes` carry the held-back amount only for a tuple that pays something, so a measured tuple's manifest never claims a split "this project has not measured".

3. **The compute reserve is a function, not a scalar (D3).** On CUDA the device/host compute reserve is `cudaComputeAt(kv, ctx)`: linear interpolation between the measured knots of the KV precision's curve, floored like llama.cpp's own columns. Outside the measured range it clamps to the end values — below the first knot that is a safe over-count; above the last (131072/f16 was never measured — the run would have swapped) it is a documented UNDER-count, recorded in the source, that the context ladder cannot reach (131072 is a projection ceiling, not an auto target — see D4). The Metal scalar and its +12 MiB quantised extra stay Metal-only, documented as such.

4. **The auto context target does not grow with the headroom (D4).** The 1024 MiB the measured tuple stops paying buys KV precision, not context: `contextSizeFor`'s RAM tier remains the sole decider of the auto target, so the 5060 Ti machine still plans 65536 tokens, not 131072 — even though the measured q8_0 shape at 131072 (12624 MiB) now fits the measured budget. An operator who wants 131072 pins it; the planner then prices it from the measurement and serves it at q8_0. The tier ladder prices context from system RAM because the context's real cost is host-side (compaction, prompt cache, checkpoints); device headroom is the wrong axis for it.

## Consequences

- The measured CUDA tuple gains 1024 MiB of device budget (13378 → 14402 on the 5060 Ti) and its projections drop by up to ~1.2 GiB (the Metal scalar 1377+12 vs the measured 166–730): launches on measured hardware plan closer to the truth in both directions.
- The cushion between the measured budget and the loaded-pass reality on that tuple is now the 1536 MiB margin alone — the same cushion every measured Metal shape has always run against. The 2026-11-03 runs themselves demonstrate it holds: the worst measured shape (131072/q8_0, 12624 MiB projected) loaded with 1702 MiB physically free. The previous text that credited the 1024 MiB allowance with absorbing the ~2.4 GiB unaccounted CUDA term is retired with the allowance; the term is what the margin exists to cover, on every backend alike.
- The margin being the only cushion leaves a thin, operator-authored band where a pinned shape can pass the gate and still fail the load. The gate admits a full-offload shape while `self` plus the 849 MiB measured mmproj reserve fits the budget (`self ≤ 13553` on the measured card); the loaded pass's real overhead is `self` plus the measured unaccounted term (2450–2472 MiB across the four runs — CUDA context, cuBLAS/graph workspace, mmproj), which physically OOMs above `self` 13466. Landing `self` in that ≤ 87 MiB window takes an exact context in the 105200–106592 range WITH a pinned `kv_type: f16` — the precision the planner would not choose itself above the 65536 threshold — and neither auto path can get there: the 65536 target's f16 `self` is 10987, and above the threshold the KV ladder starts at q8_0, whose `self` never approaches the band on this card. The band is documented rather than priced — folding the unaccounted term into every projection would refuse the measured 131072/q8_0 rung that demonstrably loaded with 1702 MiB free, re-introducing in the opposite direction the estimate-wearing-a-measurement this decision removes. A band refusal is loud: the load's own OOM names the real cause.
- Unmeasured tuples are behaviourally unchanged (1024/2048 MiB, Metal-shaped projections), so no gate verdict moves on hardware nobody measured.
- The planner's signatures grow a `backend` parameter (`splitAllowanceMiB`, `planBudgets`, `shapeNotes`); the `MemoryPlan` wire shape does not change — the echoed `DeviceBudgetMiB` and the notes text carry the difference.
- Every future measurement is one append: an overlay row in `memory.go` plus a `measuredSplitTuples` row in `plan.go`, each citing its logs. Editing a row's figures is a re-measure; adding a tuple is never a policy change.
- `TestMeasuredCUDATupleBudgetAndProjections` (budget arithmetic, the three shape verdicts, the never-chosen f16, the notes claim) and the reworked `TestPlanSplitAllowancePricesAnUnmeasuredSplit` (tuple rows, table↔overlay agreement, 1024/2048 for the unmeasured) pin the contract.

## Alternatives Considered

- **Family-only or global overlay selection** (apply the CUDA figures to every CUDA backend, or lower the projections globally). Rejected: a CUDA build on non-Blackwell silicon, or a Blackwell card behind ROCm, would inherit a measurement it does not own — the exact "estimate wearing a measurement's confidence" the allowance existed to price. The tuple is the unit the measurement actually covers.
- **Per-term mixing** (keep the Metal split terms, take only CUDA's compute curve, or vice versa). Rejected: the terms are not independent — the CUDA reserve's level and direction are measured together with the split that shares the same runs, and a hybrid would be a third profile nobody measured. The Metal profile stays whole for the tuples it covers.
- **Keep Blackwell at 1024 MiB** until more CUDA cards are measured. Rejected: the allowance prices SPLIT uncertainty, and the split is now measured for the tuple; holding the premium would keep lying in the other direction — telling a measured machine it is less known than it is, and refusing shapes (131072/q8_0) the card demonstrably loads.
- **Auto-extend the context target to 131072 when the measured budget allows it.** Rejected in favour of D4: the RAM tier is the context's decider, the tier ladder is a host-memory contract (compaction, prompt cache, checkpoints live there), and letting device headroom silently double the context would couple two budgets the planner deliberately keeps separate. The headroom is spent where it is measured — the KV precision ladder.
- **Express the compute reserve as a second scalar pair per KV type** (no interpolation). Rejected: the four knots are two precisions at two contexts each; a scalar per (kv, ctx) cell would freeze the curve at the measured points and misprice every context between them, which is most of them.
