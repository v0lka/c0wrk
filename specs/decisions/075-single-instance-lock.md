# ADR-075: Single-instance lock — relay a second launch instead of booting a second app

## Status

Accepted

## Context

On macOS, clicking a delivered system notification banner could (re)launch the app as a **fresh instance** — visually a "Wails restart" — killing every active task of the previous instance ([issue #98](https://github.com/v0lka/c0wrk/issues/98)). The in-process click path (`desktop/notifications.go` → `showWindow` → `notification_clicked` → `useNotificationClicks`) is sound and cannot restart anything by itself; the culprit is one layer below. Notifications are attributed to the **app bundle** (default Wails template bundle id `com.wails.c0wrk-desktop`), and a banner click routes through macOS LaunchServices to whatever process it resolves for that bundle. When the running process is not the one LaunchServices resolves — a rebuilt/replaced `.app` with stale banners still delivered (dev builds), an updater-swapped install tree, a stale LaunchServices registration — macOS **spawns a second process** instead of activating the running one. `main.go` set no Wails v2 `SingleInstanceLock` option, so that second process booted a full app: a second window, a second `*sql.DB` over the same `database.db` (WAL + `busy_timeout` only — no inter-process guard), a competing embedded-LLM supervisor port walk, duplicate watchers/PTYs/pack seeding, and under write contention `SQLITE_BUSY` failures inside the first instance's task loops. The same hazard exists for any manual second open (Finder double-click while running) on every platform, and a plain second open on Linux/Windows goes through the same un-guarded path.

Two further constraints shape the fix:

1. **Crash-capture forensics are shared mutable state.** `crashlog.Install` (run before `wails.Run`, hence by any second process too) stashes the running instance's live liveness marker aside and writes its own; a second process that exits without `RemoveMarker` — exactly what the Wails single-instance relay does (`os.Exit(0)` inside `Frontend.Run`) — leaves an orphaned marker whose dead pid the next start misreports as *"previous app instance did not shut down cleanly"* (`RemoveMarker` is pid-aware and leaves foreign markers in place by design). A relay process must therefore never touch the crash-capture subsystem at all.
2. **The relay path cannot recover notification routing.** The banner's session/project context is delivered to whichever process macOS attributes the click to — on the second-launch path that is the new process, which never initializes a notification center. The best achievable outcome for this path is *focus the running window*; session navigation stays the normal click path's job.

## Decision

**D1 — Enable the Wails v2 `SingleInstanceLock`** (`options.App.SingleInstanceLock`) with `UniqueId = "com.wails.c0wrk-desktop"` (`desktop.SingleInstanceLockID` — deliberately the macOS bundle identifier, `com.wails.{{.Name}}` with `wails.json` name `c0wrk-desktop`). Platform mechanics (all inside Wails v2.16, all exiting the second process at the very start of `Frontend.Run`, **before** the window is created and before `OnStartup` opens the database): darwin locks `<native temp dir>/<UniqueId>.lock` with `flock` and relays via `NSDistributedNotificationCenter`; Linux registers a session-bus name and relays via D-Bus; Windows uses a named mutex and relays via `WM_COPYDATA`. Wiring is `desktop.SingleInstanceOptions(app)` in `main.go`.

**D2 — The first instance's reaction is focus-only.** `App.handleSecondInstanceLaunch` (the `OnSecondInstanceLaunch` callback, deliberately **unexported** — Wails binds every exported method of the bound structs to the frontend, exempting only the four lifecycle hooks, and a frontend-callable focus binding is unwanted surface) logs the relay (`args`, `working_directory`), guards `a.ctx == nil` (Wails starts the second-instance processor goroutine in `NewFrontend`, *before* `OnStartup` binds the context — a relay arriving during this instance's own startup is a logged no-op; the window is revealed by the startup phases anyway), and funnels into the same `showWindow` reveal-AND-raise every other focus path uses. No frontend event is emitted: there is no consumer for it and no routing payload to carry.

**D3 — An app-level advisory lock (`~/.c0wrk/app.lock`) gates the second process's shared-state writes.** `desktop.AcquireSingleInstanceLock(config.SingleInstanceLockPath(agentDir))` runs in `mainImpl` **before** `crashlog.Install`: exclusive non-blocking `flock` (darwin/linux) or `LockFileEx` (windows), held (fd kept open) for the process lifetime, released by the OS on every exit path including `SIGKILL`. A process that finds it held knows it is the second instance and **skips crash capture entirely** — no marker stash, no marker write, no fd redirection into the shared `stderr.log` — then proceeds into `wails.Run` so the Wails relay (D1) can hand its launch data to the first instance and exit it. Setup failures (unopenable path, IO error) **fail open** to "first instance": a wedged lock file must never brick startup, and the Wails lock still enforces single instance on its own. Only the definite "locked by another holder" signal (`EWOULDBLOCK` / `ERROR_LOCK_VIOLATION`) counts as second instance.

**D4 — No configuration surface.** There is deliberately no `single_instance.enabled` knob and no env escape hatch: every c0wrk process assumes exclusive ownership of `~/.c0wrk` (SQLite database, embedded-LLM supervisor, tool-manager, watchers), so a second full instance is never a supported state to opt into. The lock file is runtime state, not config (`config.SingleInstanceLockPath`, mirroring the `window_state.json` split).

## Consequences

**Positive**

- A banner click (or any LaunchServices/Finder second open) can no longer produce a second running instance on any platform: the second process exits before creating a window, before `OnStartup`, before the database is opened — active tasks of the first instance survive untouched.
- The user-visible behavior of the failure path becomes the *intended* behavior: the existing window is focused. When the running process is the one LaunchServices resolves (the normal case), the ordinary click path still delivers full session navigation.
- Crash forensics stay truthful: the relay process leaves the liveness marker of the running instance alone, so a stale-banner click can no longer fabricate an "unclean shutdown" warning at the next start or destroy the first instance's crash evidence.
- The lock also gives `main.go` a reliable, race-free "am I the first instance" answer for any future shared-state gate.

**Negative / trade-offs**

- Two simultaneous c0wrk processes are now impossible even for development convenience (e.g. `wails dev` in two checkouts). This is intentional: both would share `~/.c0wrk` and corrupt each other's state; the second run now exits immediately with a relay instead of failing mysteriously later.
- Known race (accepted): in a *simultaneous* cold double-launch, the Wails-internal lock is taken only inside `wails.Run`, so the Wails gate can invert which of the two racing processes wins (the loser of the app-level probe may win the Wails lock and run, while the other exits as the relay). The invariant that matters still holds — **exactly one** process ever reaches `OnStartup` — but the survivor may run without crash capture, and an even later third launch could acquire the now-free app-level lock and install crash capture while the survivor runs (marker churn, the pre-ADR status quo, in an already pathological window of milliseconds).
- The `UniqueId` and the bundle id are coupled by convention only (documented on `desktop.SingleInstanceLockID`); changing the bundle id without the constant leaves the lock identity stale — harmless (still unique per app) but confusing in diagnostics.

## Alternatives Considered

- **Own IPC relay (unix socket / named pipe) with an early exit before `wails.Run`.** Would close the simultaneous-launch race and exit the second process even earlier, at the cost of a hand-rolled cross-platform notification channel, a listener lifecycle in the first instance, and re-implementing what Wails already ships per platform. Rejected: the Wails relay is battle-tested, and the remaining race window does not threaten the one-instance invariant.
- **Re-emit the notification routing from the second-instance handler** (recover session navigation on the stale-banner path). Impossible by construction: the notification's `UserInfo` reaches only the process macOS attributes the click to; the second process never sees it. The focus-only contract (D2) is documented instead.
- **Fix the crash-capture marker churn inside `crashlog`** (e.g. pid-aware stashing, or rewriting the marker from `handleSecondInstanceLaunch`). Rejected: stash/rewrite dance cannot distinguish a live first instance's marker from a genuinely crashed previous run's marker in all orderings, and the relay process touching the crash-capture subsystem at all is the root of the problem. Skipping crash capture for the relay (D3) removes the whole class.
- **`LSMultipleInstancesProhibited` in `Info.plist` / per-platform launch flags.** Does not cover the notification-click LaunchServices resolution reliably (the documented Wails v3 behavior for URL schemes shows the second-process spawn is orthogonal to that key), and is macOS-only. The Wails lock covers all three platforms uniformly.
