# Compaction Strategies

## Role

c0wrk does not implement compaction strategies — they are **sp4rk engine** primitives (sliding window, summarization, hierarchical, tool-output pruning, regular history mutation). This spec documents only how c0wrk selects and configures them. The canonical strategy behavior is in [the sp4rk compaction spec](https://github.com/v0lka/sp4rk/blob/main/specs/domains/memory/compaction.md).

## Key Files

- `core/builder.go` — `buildContextFactory` constructs the `ContextManagerFactory`; the strategy is selected by the caller (`compactionStrategyForDomain`, see below) and passed in as an argument
- `core/orchestrator_compaction.go` — `Orchestrator.CompactConversationHistory`: manual, on-demand compaction of the session conversation history (see Manual Context Compaction below)
- `backend/session/manager_compaction.go` — `Manager.CompactSessionContext` / `CancelSessionCompaction`: the pause-wait → dialogue compaction → no-op defer → persist-marker → auto-resume flow
- `core/orchestrator.go` — `RequestResumeCompaction` / `ClearResumeCompaction` / `consumeResumeCompaction`: the mutex-guarded one-shot "compact on resume" request, consumed by the next `Resume` (see Resume-side Forced Trajectory Compaction below); `ClearResumeCompaction` (invoked by the session layer's cancel/abandon paths) drops an armed flag so it cannot fire for an unrelated later task
- `core/conductor.go` — `compactionStrategyForDomain(domain, complexity)` selects the strategy from `routing.Domain` + complexity (see [README.md](README.md) for the domain → strategy table); the context factory also applies optional per-step `PruningOverride` values from `StepConfig` (passed as variadic args); `forceCompactionStrategy` (the resume-compaction request) overrides the routing-derived strategy for a run and forces `CompactOnStart`

Engine files (`github.com/v0lka/sp4rk/memory/compaction_sliding.go`, `compaction_summary.go`, `compaction_hierarchy.go`, `compaction_conversation.go`, `context.go`) are documented in [the sp4rk compaction spec](https://github.com/v0lka/sp4rk/blob/main/specs/domains/memory/compaction.md).

## Strategy Overview (canonical in sp4rk)

| Strategy | Best for | Trade-off |
| -------- | -------- | --------- |
| sliding_window | code tasks (recent edits visible) | loses early research/context entirely |
| summarization | research tasks (preserves synthesized findings) | summary may lose details; requires LLM call |
| hierarchical | long-running complex tasks (balanced retention) | more complex logic, harder to predict retained content |

Tool-output pruning (governed by `toolOutputPruning.thresholdPercent`) and regular history mutation (per-`BuildPrompt`, replaces old tool results with `ToolResultCache` references) are engine mechanisms — see the sp4rk compaction spec.

## Manual Context Compaction

On-demand compaction of the session's cross-task conversation history (what the orchestrator injects as prior conversation into every request — NOT the per-executor step context, NOT the UI chat history). Triggered from the status bar by the compact button left of the context-fill indicator (strategy dropdown with tooltips; the button becomes a cancel affordance while a compaction is in flight).

- **sp4rk primitive**: `memory.CompactConversationHistory(ctx, msgs, strategy, cfg, deps)` — message-level strategies (`sliding_window` / `summarization` / `hierarchical`) mirroring the step strategies; unknown strategies fail closed; the last message is never removed; the input is never mutated. This API is **purely structural**: each strategy applies its configured message-count window exactly (sliding `KeepFirst+KeepLast`, summarization `KeepLast`, hierarchical ratio zones) — there is no token-budget sizing and no token trim. A history the strategy leaves unchanged (too short for its window) is returned verbatim. Canonical in the [sp4rk compaction spec](https://github.com/v0lka/sp4rk/blob/main/specs/domains/memory/compaction.md).
- **sp4rk prediction**: `memory.PredictCompaction(msgs, strategy, cfg, deps)` — a pure, no-LLM, no-mutation prediction of what a manual compaction would do. `WillCompact` is an EXACT structural verdict (non-empty summarized/omitted zone) and never depends on any forecast; `AfterTokens`/`Reclaim` are an exact dry-run for `sliding_window` and a FORECAST (from `deps.Forecast` ratios) for the LLM-backed strategies; `VerbatimTokens` is the exact verbatim token anchor for calibration. Canonical in the [sp4rk compaction spec](https://github.com/v0lka/sp4rk/blob/main/specs/domains/memory/compaction.md).
- **Orchestrator** (`core/orchestrator_compaction.go`): `CompactConversationHistory(ctx, strategy)` compacts `o.conversationHistory` in place using the session's executor compaction settings (Small-LLM context overrides applied — same values `buildContextFactory` uses), summarizes via the session's tracking caller (`coreprompts.CompactionSummarize`, `llm.CallPurposeCompaction` — tokens counted in session totals), and emits `ContextCompaction` + a refreshed `ContextFill` on the EFFECTIVE basis (window − output limit − safety margin) — the session emitter rescales those to the display window itself. The RETURNED before/after percents (persisted into the marker row and the `compaction_finished` event) use the DISPLAY basis (the advertised window) directly, because the frontend renders the marker's metadata verbatim on reload and the reloaded card must match the live one. On error the history is left untouched.
- **Structural model** (manual compaction only — the executor's threshold-triggered compactions are unaffected): manual compaction is PURELY STRUCTURAL. There is no "target fill" to compact toward — each strategy applies its configured message-count window exactly, and the result is whatever that window produces. The removed token-budget gate (`manualTargetPercent`, formerly `executor.compaction.manualTargetPercent`) previously made a history whose TOKEN count fit 30% of the effective window a no-op regardless of message count — which on large-context models (≈170–260k-token budgets) meant the compact button was effectively always disabled. The availability of the button is now decided per strategy by `PredictCompaction`'s exact `WillCompact`, which depends only on message counts, not tokens. The compression-ratio forecast (below) affects only the predicted reclaim number, never availability.
- **Compression-ratio forecast** (`core/orchestrator_compaction.go` + config `executor.compaction.forecast.*`): the LLM-backed strategies' predicted reclaim is a forecast — `summarization_ratio` (summarization + hierarchical middle, default 0.3), `hierarchical_distant_ratio` (default 0.15), `hierarchical_middle_ratio` (default 0.3) are the config seeds. The orchestrator holds an EWMA-calibrated `CompactionForecast`, refined after each successful manual compaction from the observed ratio (`(after − verbatim) / (before − verbatim)`, clamped to (0, 1]); `sliding_window` is exact and never calibrated. The calibrated forecast is persisted to `app_state` (`compaction_forecast` key) by the session layer after each compaction and restored on session load, so the calibration survives restarts; a missing/unparsable state falls back to the config seed.
- **Honest no-op** (`ErrNothingCompacted`): the strategy's `PredictCompaction` reported `WillCompact == false` — the dialogue is already under the strategy's structural window, so there is nothing to compact (the real compaction would return the history verbatim). A no-op returns the sentinel WITHOUT swapping the history or emitting core events — nothing changed, so nothing is reported as changed (the session layer wraps it as `success=true, nothing_compacted=true`, see below). An empty history is the distinct `ErrNothingToCompact`. (A defensive same-length-same-token check remains as a backstop for the nil-counter case, but the prediction is exact and catches the no-op up front.)
- **Session flow** (`backend/session/manager_compaction.go`): `Manager.CompactSessionContext` — async: emit `compaction_started`, set `session.compacting` (sends/resumes now fail with `ErrSessionCompacting`), pause a running task exactly like `PauseSession` and wait for its checkpoint (pause **ownership**: the arming records who owns the pause via `session.pauseOwner` — the auto-resume resumes only a pause the flow still owns. A user-initiated pause is never stolen, whichever side paused first: a `PauseSession` landing after the arming overwrites the owner to the user, and the arming itself leaves an already-user-owned pause to the user), compact the dialogue (`orchestrator.CompactConversationHistory`), then auto-resume the task it paused — only when the flow still owns the pause; a user-owned pause stands, and the task stays paused — and emit `compaction_finished`. Outcomes: **compacted** — a marker row (role `context_compaction`; metadata carries `strategy`, before/after percents, and the compacted `messages` snapshot) is persisted so a restart restores the compacted history, and the EWMA-calibrated forecast is persisted to `app_state`; **no-op** (`ErrNothingCompacted` — the dialogue is already under the strategy's structural window) — NOT a failure: the event reports `success=true, nothing_compacted=true` with zero percents, NO marker row is written (there is no compacted history to snapshot), and the history is untouched. When a paused unfinished task waits for this flow's auto-resume, the no-op additionally DEFERS the compaction to the resume: `orch.RequestResumeCompaction(strategy)` arms the one-shot request (surfaced as `deferred_to_resume=true`) strictly BEFORE the auto-resume, so the flag is consumed by the resumed run; if the task is instead cancelled or abandoned before resuming (user discard via `CancelUnfinishedTask`, goal-mode takeover via `abandonUnfinishedTaskForGoal`, archival), the session layer's `clearResumeCompaction` drops the armed flag so it never fires for an unrelated later task — the resumed run then force-compacts the merged trajectory (see below) and the real numbers arrive as the executor's `context_compaction` card. Note the deferral on a USER-paused session (the flow pauses only the task it finds running, so an already-paused session gets no auto-resume): the armed flag simply waits for the user's own later resume of that same task. A failed auto-resume — or the flow honouring a user-owned pause (see ownership above) — sets `paused_without_resume`: the checkpoint remains but `session_paused` was suppressed, so clients re-apply the paused state. `CancelSessionCompaction` aborts: during the pause-wait it still waits for the checkpoint (skips the compaction — deterministically, even when the cancel races the checkpoint landing — and auto-resumes); during the compaction it aborts the summarize calls with the history untouched.
- **Resume-side forced trajectory compaction** (`core/orchestrator.go` + `core/conductor.go`): `RequestResumeCompaction(strategy)` arms a mutex-guarded one-shot request; the NEXT `Resume` consumes it at entry (before the goal-loop / plain-Conductor branch is chosen, so the semantics hold for both resume paths) and threads it into the conductor run as `forceCompactionStrategy`. When non-empty, the run (a) replaces the routing-derived compaction strategy with the user-selected one for the ENTIRE run — the forced start-of-run pass AND any later threshold-triggered reactive compactions — and (b) sets `CompactOnStart`, so the engine compacts the merged trajectory (seeded checkpoint steps + the resumed run) exactly once, up front, BEFORE the first LLM call, regardless of fill thresholds. Empty (the default) preserves the normal routing-derived, threshold-driven behavior. Arming with `""` is the "not requested" sentinel (a no-op); re-arming before consumption overwrites the pending strategy. The defer happens ONLY for the no-op outcome: a successful dialogue compaction already shrank the history and persisted the marker, so force-compacting the merged trajectory at resume would duplicate the work (`CompactOnStart` ignores fill thresholds).
- **Restore**: `convertChatMessagesToLLM` treats the LAST marker's snapshot as the seed — conversational rows before it are dropped, the snapshot is expanded in place, later exchanges append. Markers without a snapshot are no-ops; a no-op manual compaction writes no marker at all. The marker row renders as the existing compaction card on reload.
- **Per-strategy availability & the compact menu** (`core/orchestrator_compaction.go` `ManualCompactionAvailability` + `backend/session` + `CompactContextButton.tsx`): a pure prediction of whether each manual-compaction strategy would actually shrink the CURRENT history — no strategy runs, nothing is swapped, no events fire. Thread-safe from any goroutine: the history is read via `historySnapshot` and the forecast via `compactionForecastSnapshot` (both mutex-guarded). Each strategy's `Available` verdict is EXACT (sp4rk `PredictCompaction.WillCompact` — a non-empty summarized/omitted zone); `ReclaimTokens` is an exact dry-run for `sliding_window` (`Exact == true`) and a forecast for the LLM-backed strategies (`Exact == false`). Delivery channels: `SessionRuntimeStatus.compaction_availability` (RPC `GetSessionRuntimeStatus` — orchestrator pointer read under `sess.mu`, prediction evaluated outside it; fail-open EMPTY when the session or its orchestrator is not in memory) reconciles the menu on session load/switch; `compaction_finished.compaction_availability` (recomputed on the POST-flow history before the emit — success/nothing_compacted → all unavailable, cancelled/error → the untouched history's own verdict) refreshes it without a refetch; the frontend refetches on terminal task events (`task_complete`/`task_cancelled`/`error`) because every terminal outcome grows the history and can flip a strategy back to available. UI precedence (`CompactContextButton`): compacting → cancel affordance; at least one strategy available → the dropdown with each strategy shown, unavailable ones DISABLED with their reason ("would not shrink the context right now") and available ones carrying a "reclaims ~N tokens (estimated)" hint; none available → the trigger is disabled with a "nothing to compact" tooltip. An absent/unknown verdict (older backend, missing key, no orchestrator) NEVER disables anything — the menu fails open and a pointless click simply reports the existing `nothing_compacted` outcome.
- **Frontend**: `chatStore.compacting[sessionId]` locks the whole input area (`chatInputLock` matrix), the activity shows "Compacting", the compact button swaps to cancel, and `session_paused` handling is suppressed while compacting. `SessionRuntimeStatus.compacting` (with `.compaction_availability` — the per-strategy menu verdict, see above) reconciles the state on session switch/restart. `compaction_finished` outcome handling (`handleCompactionFinished`): an idle no-op (`nothing_compacted` with nothing to resume — no card follows) clears the "Compacting" activity immediately; `deferred_to_resume` WITH the flow's auto-resume behaves like `resumed` — the label is left in place for the subsequent `task_resumed` ("Resuming...") — while a deferral on a USER-paused session (no auto-resume, no upcoming `task_resumed`; the session's own paused state was already applied by its unsuppressed `session_paused`) clears the label like an idle outcome instead of leaving it dangling.

## Tool-Output Pruning Config (c0wrk consumption)

c0wrk configures tool-output pruning centrally in `core/builder.go` (`buildContextFactory`) from `cfg.Executor.ToolOutputPruning`:

- `keepLastN` — how many recent tool results to keep inline before replacing older ones with a placeholder
- `protectedTools` — tool names whose outputs are never pruned regardless of `keepLastN` (default `["store_fact","search_facts"]`)
- `thresholdPercent` — fill % **below which pruning is skipped entirely** (default 50; 0 = always prune). Pruning runs on every `BuildPrompt` once fill reaches this floor — it is independent of the `CheckFill` compaction statuses

Per-step pruning overrides are supported via the `PruningOverride` variadic argument on `ContextManagerFactory`; when a step's `StepConfig` carries a positive `KeepLastN`, it replaces the global value for that step's executor.

## Trigger Thresholds (c0wrk config)

The three compaction thresholds all run the same `cw.Compact` (strategy compaction); only the `CheckFill` status differs:

```
Context fill %:
  0%──────────85%────────92%──────98%────100%
              │           │        │
              ▼           ▼        ▼
            "compact"   "warning" "emergency"  → each runs cw.Compact (strategy)
                                                      │
              >= 100% ─────────────────────────────► "reject"

Tool-output pruning is governed separately by toolOutputPruning.thresholdPercent
(default 50): it runs on every BuildPrompt once fill >= that floor, independent
of the CheckFill statuses above.
```

See [README.md](README.md) Configuration for the `config.yaml` keys.

## Invariants

- Compaction never removes the system prompt or the last message (current LLM turn)
- Tool output pruning runs BEFORE strategy compaction
- Protected tools are NEVER pruned regardless of `KeepLastN`
- Unrecognized domain → `sliding_window` fallback
- Manual compaction (structural mode): a history under a strategy's message-count window (sliding `keep_first+keep_last`, summarization `keep_last`, hierarchical empty zones) is returned verbatim; there is no token-budget gate and no target fill — the strategy's window alone decides what is compacted
- The compression-ratio forecast only affects the predicted reclaim number in the compact menu; it NEVER affects a strategy's availability (which is an exact structural verdict)
- A manual-compaction no-op changes nothing observable: the history is untouched, no marker row is written, the orchestrator emits nothing; the session layer reports it honestly as `success=true, nothing_compacted=true` with zero percents
- The compact menu's availability is fail-open: only a strategy whose prediction says it would NOT shrink the dialogue is disabled; every unknown verdict (no orchestrator in memory, absent payload, older backend) leaves every strategy enabled — a pointless click just reports the `nothing_compacted` outcome
