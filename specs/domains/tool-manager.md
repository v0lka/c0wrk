# Tool Manager

## Purpose

The tool-manager downloads, installs, and version-tracks the external CLI binaries c0wrk needs at runtime — `ripgrep` (`rg`), `uv`, and `markitdown` — into `~/.c0wrk/tools/`. It is the supply-chain boundary for runtime binary dependencies: every managed version is a compile-time pin in the registry, reconciled against a local `.versions` file on startup. It deliberately does not check upstream for newer releases or auto-update installed binaries — this is a defense against supply-chain attacks (a compromised or maliciously rotated upstream release cannot reach a user's machine without a developer explicitly raising the pin and shipping a new build).

Offline operation is a hard product requirement for the steady state, not a tradeoff: a machine with a complete install (or a complete cache) starts with zero network I/O. The startup reconciliation runs in two sequenced passes inside startup — an offline pass restricted to local disk work (probe existing binaries, install from already-cached SHA256-verified archives), followed, when tools are positively known to be missing, by a **blocking network pass under the tool-install splash** ([ADR-100](../decisions/100-blocking-first-run-tool-install.md)). Per-tool failures are isolated within a pass; a network pass that still cannot deliver the tools is fatal (native modal + quit). The single non-fatal degradation is a structural failure of the offline pass over an already-complete install — a `runtime_error` toast, no blocking.

**Scope boundary.** The tool-manager delivers the agent's *CLI tools* — binaries that are resolved **by name through `PATH`** and invoked by the model — and nothing else. The [Embedded LLM](embedded-llm.md) inference runtime and model weights are deliberately **not** managed tools: they are neither in `ManagedTools()` nor under `~/.c0wrk/tools/`, they are not reconciled at startup, and they are never placed where `PrependToPATH()` would expose them to `bash_exec`. `core/embeddedllm/` is a separate delivery subsystem that reuses this one's *posture* (compile-time pins, fail-closed SHA256, secure-bytes-before-destroy) but not its code, registry, limits or directory. See [Delivery scope](#invariants) below and [ADR-066](../decisions/066-embedded-llm-runtime.md).

## Key Files

- `core/toolmanager/registry.go` — `ManagedTools(logger *slog.Logger) ([]ToolSpec, error)` registry: per-tool pinned `Version`, per-platform download `URLs`, SHA256 `Checksums`, archive-layout metadata (`ArchiveName`, `BinPathInArchive`), `PipSpec` for Python packages, and the embedded `RequirementsLock` (fully pinned transitive tree)
- `core/toolmanager/markitdown_lock.txt` — embedded requirements lock for markitdown (exact `==` versions for the package and its entire transitive dependency tree, generated by the `uv pip compile` command recorded in the file header); `core/toolmanager/markitdown_requirements.in` is its input
- `core/toolmanager/manager.go` — `Manager.EnsureCriticalTools(ctx, EnsureOptions) ([]ToolStatus, error)` reconciliation (one invocation per pass: `AllowNetwork=false` → strictly local; `AllowNetwork=true` → network retry), per-tool failure isolation, `removeStalePythonEnv`, `PrependToPATH`, `VenvPythonPath` (pure probe for the managed venv interpreter at `<toolsDir>/python/venv`)
- `core/toolmanager/install.go` — `FSInstaller`: archive extraction (`StaticBinary`), Python bootstrap (`uv python install` → `uv venv` → `uv pip install`), wrapper-script creation, zip-bomb guard
- `core/toolmanager/download.go` — HTTP downloader with retry and post-download SHA256 verification; `DownloadMode` (`DownloadOnline` / `DownloadCacheOnly`) and the `ErrCacheUnavailable` sentinel make the offline pass a downloader-level contract (CacheOnly never performs network I/O)
- `core/toolmanager/versions.go` — `ToolVersions` map and `.versions` JSON read/write
- `core/toolmanager/platform.go` — `Platform()` / `PlatformTriple()` canonical naming
- `core/toolmanager/manager_diskcheck_unix.go` / `manager_diskcheck_windows.go` — best-effort pre-download disk-space guard
- `core/toolmanager/probe_transient_other.go` / `probe_transient_windows.go` — `isTransientSpawnError`: classifies a `--version` probe failure as the kernel's transient refusal to spawn a freshly written binary (Unix `ETXTBSY`; Windows `ERROR_ACCESS_DENIED`/`ERROR_SHARING_VIOLATION`/`ERROR_LOCK_VIOLATION` from an antivirus or other short-lived holder without `FILE_SHARE_EXECUTE`), which `probeBinaryVersion` retries (`probeTransientAttempts` 3, `probeRetryBackoff` 100 ms) before reporting a mismatch; a permanently unusable binary fails every attempt identically
- `backend/startup_phases.go` `initTools()`/`InitTools()` / `reconcileToolsWithSplash()` — wiring (Phase 2, called by the desktop phase glue, [ADR-100](../decisions/100-blocking-first-run-tool-install.md)): `NeedsInstall()` early detection → splash (`tool_manager:start`) → offline `EnsureCriticalTools(AllowNetwork: false)` → when tools remain missing, a **blocking** network `EnsureCriticalTools(AllowNetwork: true)` under the splash → `PrependToPATH()`; residual not-Ready tools or a structural network failure are fatal (`toolFatalActions`: native modal + quit, built by the desktop glue); a structural offline failure over a complete install degrades to a `runtime_error` toast; `emitToolManagerProgress` (`desktop/startup_phases.go`) forwards the Manager's progress and stamps every event with the splash denominator (`tools_total`). Test seams: `toolEnsurer` (fake in tests), `toolFatalActions` (recorders)

## Core Types

```go
type ToolType string
const (
	StaticBinary  ToolType = "static_binary" // self-contained archive (rg, uv)
	PythonPackage ToolType = "python_package" // pip-installable via uv (markitdown)
)

type ToolSpec struct {
	Name        string  // "rg", "uv", "markitdown"
	Version     string  // pinned upstream version (source of truth for reconciliation)
	Type        ToolType
	Description string
	BinName     string  // executable name after install
	// ArchiveName: on-disk cache filename, resolved from the download-URL
	// basename (so the extension matches the real bytes) unless ArchiveNameOverride wins.
	ArchiveName             string
	ArchiveNameOverride     string // replaces triple-derived name when upstream naming differs per-platform
	BinPathInArchive        string // relative path to the binary inside the archive
	BinPathInArchiveOverride string
	PipSpec                 string // pip install spec, pinned with == for determinism (PythonPackage only); the fallback when RequirementsLock is empty
	RequirementsLock        string // embedded fully pinned lock (markitdownLock); installed via `uv pip install -r`
	PythonVersion           string // Python version required (PythonPackage only)
	URLs                    map[string]string // platform key -> download URL
	// Checksums: platform key -> SHA256 hex. Fail-closed (ASI04-R2): a missing/empty
	// checksum FAILS verification rather than accepting an unverified binary.
	// Every supported platform MUST declare one.
	Checksums               map[string]string
}

type ToolVersions map[string]string  // tool name -> installed version, persisted to .versions

type EnsureOptions struct {
	AllowNetwork bool // false → strictly local reconciliation (offline startup pass)
}

type ToolStatus struct {          // per-tool outcome of one EnsureCriticalTools run
	Tool      ToolSpec
	Ready     bool  // installed and verified (static: version probe; Python: bootstrap complete) — before or during this run
	Installed bool  // newly installed or updated during this run
	Err       error // why the tool is not Ready; nil iff Ready
}

type DownloadMode int
const (
	DownloadOnline    // network allowed; cache consulted first
	DownloadCacheOnly // local disk only: verified cached archive or ErrCacheUnavailable (no network I/O)
)
```

## Flow

```
startup Phase 2: initTools()
│
├─ Manager.NeedsInstall()  [stat-based early detection]
│   └─ tool_manager:start → tool-install splash (frontend); emitted when
│       tools are missing — a NeedsInstall error counts as missing too
│
├─ PASS 1 (synchronous): EnsureCriticalTools(ctx, {AllowNetwork: false})
│   │  strictly local — no network I/O is possible
│   ├─ create ~/.c0wrk/tools/ dirs
│   ├─ checkDiskSpace(toolsDir, 200 MiB)        [best-effort; no-op on Windows]
│   ├─ ReadVersions(.versions)
│   └─ for each tool in ManagedTools() (dependency order: uv, rg, markitdown):
│         ├─ .versions matches AND binary present AND its --version probe
│         │      matches the pin (static binaries only) → skip (Ready)
│         ├─ probe mismatch → reinstall ATTEMPT; the old binary stays in
│         │      place until replacement bytes are secured
│         └─ installOne:
│              StaticBinary  → Download(DownloadCacheOnly): a SHA256-verified
│              │               cached archive satisfies the request; anything
│              │               else fails fast with ErrCacheUnavailable →
│              │               not-Ready status (picked up by pass 2).
│              │               The stale destination binary is removed only
│              │               AFTER the replacement archive is secured, then
│              │               extract + post-install probe (a probe failure
│              │               removes the fresh binary; .versions untouched)
│              PythonPackage → not-Ready status (requires network); wrapper
│                             and venv left untouched
│         └─ WriteVersions(.versions) after each successful install
│
├─ outcome of pass 1:
│   ├─ all Ready → tool_manager:done (pass-1 counts) → splash resolves;
│   │   startup continues (offline steady state: zero network I/O)
│   ├─ structural failure with NOTHING positively missing (NeedsInstall
│   │   reported a complete install) → tool_manager:done(0,0) + single
│   │   runtime_error toast (error_code "tool_install_failed"); no network
│   │   pass, no blocking — the app keeps running
│   └─ not-Ready tools remain (or structural failure while tools are
│       suspected missing) → late tool_manager:start if not emitted yet
│       (NeedsInstall missed what probing found) → pass 2
│
└─ PASS 2 (BLOCKING network retry, synchronous inside initTools — splash
       up; runs only when tools are missing after pass 1):
       EnsureCriticalTools(ctx, {AllowNetwork: true})
       ├─ StaticBinary → Download(DownloadOnline) with transient retry,
       │     then the same secure-bytes → remove-stale → extract → probe path
       ├─ PythonPackage → uv python install → uv venv → uv pip install
       │     -r <embedded requirements lock>  (a tool without a lock falls
       │     back to its floating <PipSpec>; the stale wrapper+venv are
       │     removed immediately before the bootstrap runs)
       ├─ tool_manager:done (pass-2 counts) — exactly once per launch, on
       │     the deciding pass, before any fatal modal
       ├─ structural error → FATAL: native "Tool Installation Failed"
       │     modal (error text) + quit; startup aborts
       └─ tools still not Ready → FATAL: native modal naming the failed
          tools + quit; startup aborts
```

## Invariants

**Supply-chain integrity:**

- Managed tool versions are compile-time pins in `ManagedTools()`; the reconciliation source of truth is source code, not the network.
- Installed tool versions advance only when a developer raises a pin in the registry and ships a new build. The tool-manager performs no upstream version queries and no automatic updates.
- A static-binary download is SHA256-verified against the registry checksum before extraction. Verification is **fail-closed** (ASI04-R2): a missing/empty checksum fails verification rather than accepting an unverified binary, so every supported platform MUST declare one.
- The Python package install is fully pinned: `PipSpec` carries an explicit `==<version>` pin, and the install consumes the embedded requirements lock (`ToolSpec.RequirementsLock` → `uv pip install -r`) so the entire transitive dependency tree resolves to exact, audited versions rather than floating PyPI "latest". Tools without a lock fall back to the pinned `PipSpec` alone.

**Reconciliation correctness:**

- A pinned-version change always forces a reinstall. For `StaticBinary` tools the binary-presence check triggers a re-download; for `PythonPackage` tools `removeStalePythonEnv` rebuilds the wrapper and virtual environment, because the wrapper-existence short-circuit in `InstallPythonPackage` would otherwise leave the previous package in place.
- Stale artifacts are destroyed only after the bytes that replace them are secured: the static binary is removed after the verified archive is on disk, the Python wrapper+venv immediately before the bootstrap runs. An offline failure therefore never leaves the machine with less than it had before.
- A binary that fails the post-install version probe is removed from disk; `.versions` is left untouched for the failed tool so the next run retries.
- The `.versions` file is rewritten after each successful tool install, so a partially completed bootstrap resumes on the next launch.
- The fast path probes the actual binary via `--version` whenever `.versions` claims a match for a `StaticBinary` tool; a probe mismatch triggers a reinstall attempt. When the attempt cannot secure replacement bytes (offline, no verified cached archive), the existing binary stays on disk and the tool is reported not Ready — the version file never masks an outdated binary, and the machine never loses a working tool to a failed update.

**Delivery scope (what the tool-manager does NOT deliver):**

- `ManagedTools()` is the complete inventory. The embedded-LLM runtime and weights are absent from it by design, so they are never probed, reconciled, version-tracked in `.versions`, or installed by either startup pass.
- No embedded-LLM file is ever written under `<toolsDir>/bin`. That directory is prepended to the agent's `PATH` by `PrependToPATH()`, which would make `llama-server` directly invokable from `bash_exec` — an inference runtime is a c0wrk-supervised subprocess, never an agent tool (ASI05, ADR-066 D3). The embedded roots are `<agentDir>/runtimes/llama-<tag>-<backend>/` and `<agentDir>/models/bonsai-2-27b/`, pinned outside the tools tree by `TestEmbeddedLLMDirs`.
- The embedded artifacts violate every size and time bound this subsystem is built on, so reusing its code would silently weaken one of them: `maxDownloadBytes` (1 GiB) is below a single 6.7 GiB model file, `maxExtractEntryBytes` (512 MiB) is below a CUDA runtime library in these archives, the 5-minute download client timeout is below a multi-hour transfer on a slow link, and `checkDiskSpace`'s 200 MiB floor is below the ~7.3 GiB the set needs.
- A download that must never start implicitly cannot ride the startup reconciliation: the embedded install runs only on an explicit user action, in the background, and never during startup (the startup reconciliation covers the managed-tool registry only — [ADR-032](../decisions/032-offline-first-tool-reconciliation.md)/[ADR-100](../decisions/100-blocking-first-run-tool-install.md); keeping the multi-GiB embedded downloads out of it is what preserves startup's offline steady state).
- `core/embeddedllm/download.go` is therefore a separate downloader (HTTP `Range` resume, no size ceiling, a per-artifact disk guard, ~100 ms throttled progress) and `core/embeddedllm/install.go` has its own extraction with caps sized for these archives (2 GiB per entry, 8 GiB per archive). What is shared is the pattern, not the code.

**Operational:**

- The offline pass performs local disk work only: binary probes and installs from already-cached verified archives. Network access is used exclusively by the blocking network pass, which runs inside startup and only when tools are positively known to be missing ([ADR-100](../decisions/100-blocking-first-run-tool-install.md)) — a machine with a complete install performs zero network I/O and never blocks. An offline first run is fatal by design: the app refuses to come up without its managed tools rather than presenting a UI whose core workflows are dead.
- Per-tool failures are isolated within a pass: one unavailable tool never prevents the remaining tools from being reconciled. Tools still not Ready after the blocking network pass are fatal (native modal naming them + quit); the `runtime_error` toast (`tool_install_failed`) is reserved for the structural offline failure over an already-complete install.
- A version bump whose archive was fetched while online completes fully offline on the next startup (verified cached archive → in-place upgrade with no network).
- All `exec.CommandContext("rg", ...)` call sites resolve to the managed binary transparently, because `tools/bin/` is prepended to `PATH` at startup before Phase 3 — on every non-fatal path, after the passes complete (PATH resolution happens per-exec).
- Progress reporting is terminal-explicit (payload contract: [event-catalog](../contracts/event-catalog.md), `tool_manager:progress`): every install that performs work ends its visible lifecycle with a `done` or `failed` (carrying the cause) event — `done` means installed AND verified via the post-install version probe for static binaries, and bootstrap-complete (interpreter, venv, locked packages and wrapper in place; no version probe runs — the byte-exact embedded requirements lock plus the fail-closed `uv pip install` is the verification) for Python tools — and a deferral to the network pass (`errNeedsNetwork`, or an offline-pass static-binary cache miss surfaced as `ErrCacheUnavailable`) is silent — the network pass owns the tool's terminal outcome. Every progress event carries the splash denominator (`tools_total`), because the webview-subscription race can lose `tool_manager:start` and the frontend's totals must not depend on it.
- The managed venv layout (`<toolsDir>/python/venv`) is owned by this package; `VenvPythonPath` is the canonical accessor other layers use to obtain the interpreter that can `import markitdown` (vision-assisted document conversion runs through the markitdown Python API, not the CLI). It is a pure filesystem probe — it never triggers an installation and returns `""` when the venv is absent, leaving plain CLI conversion intact.

## Configuration

The tool registry is an embedded Go struct (`core/toolmanager/registry.go`), not a `config.yaml` surface — there are no user-tunable version knobs by design (tunability would undermine the supply-chain guarantee). Fixed operational thresholds:

| Parameter | Value | Location |
| --- | --- | --- |
| Minimum free disk space before download | 200 MiB | `manager.go` `checkDiskSpace` (best-effort; no-op on Windows) |
| Max decompressed size per archive entry (zip-bomb guard) | 512 MiB | `install.go` `maxExtractEntryBytes` |
| Max download size per archive (pre-verification disk-exhaustion guard) | 1 GiB | `install.go` `maxDownloadBytes` |
| Download retry on transient failure | 1 retry | `manager.go` `installStatic` |

To remove all managed tools, delete `~/.c0wrk/tools/`.

## Extension Points

**Add a new managed tool:** append a `ToolSpec` to `ManagedTools()` in dependency order, provide per-platform `URLs` and SHA256 `Checksums` (verified against the upstream `sha256.sum` asset), set `BinPathInArchive` from `PlatformTriple()`, and add `archiveNameForPlatform`/override handling if upstream naming differs. Static binaries are then resolvable by name with no call-site changes (PATH prepend).

**Raise a pinned version (security/maintenance bump):** update `Version`, the version segment in every `URLs` entry, all five platform `Checksums`, and — for `PythonPackage` tools — regenerate the embedded requirements lock with the `uv pip compile` command recorded in its header and update the `==<version>` segment of `PipSpec`. The reconciliation loop forces the upgrade automatically for existing installs.

**CVE review before any bump (required):** raising a pin is the only mechanism that introduces new external code onto users' machines. Before bumping, query the current and target versions against a vulnerability database (e.g. OSV.dev / GHSA) for the exact affected ranges, and record the decision. Bumping to fix a CVE is safe; bumping to "latest" without review reopens the supply-chain surface the no-auto-update invariant exists to close.
