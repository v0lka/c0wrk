# Workspace

## Purpose

Manages the project workspace: file tree loading, filesystem watching for changes, git status integration, and vector index for semantic code search.

## Behavior

### File Tree

- Loaded lazily on frontend request (not preloaded)
- Depth-limited to avoid scanning huge directories
- Excludes files/dirs matching `.gitignore` or `.aiignore` rules (root and nested, resolved by an `ignore.Resolver` over the workspace) plus any hidden entry (leading-dot name); no hardcoded directory/extension list remains. See [ADR-016](../decisions/016-aiignore.md).
- Returns `FileNode` list: name, path, isDir, hidden, gitStatus, gitIgnored (flat list, no children). The `gitIgnored` flag is set for paths excluded by `.gitignore` **or** `.aiignore`, not strictly git-ignored paths.

### Per-Root Ignore Resolver Cache

Each workspace root's `ignore.Resolver` (backend session manager) builds asynchronously on first use (`startIgnoreBuild`): a `LoadOrStore` sentinel dedups concurrent walks, and the goroutine is manager-tracked and derived from `shutdownCtx`, so `Shutdown` aborts the walk before joining it (a multi-minute walk over a huge root — a module cache, a vendor tree — can never burn the stop timeout on quit). Invalidation is delete-only: watcher ignore-file changes (`.gitignore`/`.aiignore`/`.ignore`) evict affected roots (`InvalidateIgnoreCache` matches via `pathutil.IsWithinPath` against symlink-resolved keys) and the next `injectIgnoreChecker` rebuilds lazily — at worst one message runs without ignore filtering, never a synchronous multi-minute walk on the send path.

### Filesystem Watcher

```
core/workspace.NewWatcher(root string, onChange ChangeHandler, loggers ...*slog.Logger)  // wired in backend/frontend_api_project.go
  → fsnotify watches root + .git (not recursive; recursion is opt-in via Watcher.WatchTree)
  → Event filters before debounce (keep the read-only-git refresh loop from
    self-sustaining): pure-Chmod events (kqueue NOTE_ATTRIB on .git/index reads)
    and Write-only events on watched directories (NTFS/kqueue directory-mtime
    churn — on Windows its delivery can lag the child events by seconds) are
    dropped; every real change arrives as its own event on the child path
      ├─ Debounce (batch rapid changes)
      ├─ Emit global event: workspace:tree_changed
      └─ Frontend: fileTreeStore refreshes affected subtree
```

The watcher root FOLLOWS the active session in both modes. For No Project
(CHAT mode) it is the active session's workspace directory
(`__no_project__/<sessionID>/workspace/`); when no session exists yet, any
previous watcher is torn down and creation is deferred until the first
session activates (there is no project-base-directory fallback). For CODE
mode the root is the active session's workspace — its managed worktree when
the session is bound to one, the project checkout otherwise — resolved at
switch time through the READ-ONLY session lookup, and re-scoped on every
session switch by the panel's `WatchDirectory` call, whose renderer-supplied
path is containment-validated first (inside the active workspace, or one of
its managed worktrees; a foreign path is rejected and changes nothing). A
re-scope additionally re-checks the active-session authority at execution
time (`scopeRootMatchesActiveSessionLocked`, under the watcher lock —
[ADR-099](../decisions/099-research-root-follows-active-session.md)):
binding calls race, so a late request for an older tree is skipped instead
of parking the watcher — and the tracked research emit roots with it — on
the wrong tree; the frontend orders the call after the selection persist
(`selectionPersisted`), and a skipped re-scope self-heals on the next panel
mount or session switch. The
per-root consumers the callback feeds — git status/ignore caches and the
vector `NotifyFileChange` — route at the WATCHED root (per-root registry,
[ADR-081](../decisions/081-vector-per-root-registry.md)), so a managed
tree's churn refreshes that tree's Git-panel state and wakes only that
tree's index manager, never the checkout's. Recursive research-tree watches
([ADR-099](../decisions/099-research-root-follows-active-session.md): the
checkout's `research` plus the watched root's own when it differs,
admitted via `AllowRoot` when they live outside the root) are re-registered
on every re-scope and create nothing on disk (Issue 52). Git operations and
vector indexing remain skipped for No Project.

### Git Integration

- `GetGitStatus(dirPath)` returns whole-repository per-file status (modified, added, deleted, untracked) computed over the Git-panel focus root (the focused worktree, or the project checkout by default — see [session-worktrees.md](session-worktrees.md#git-panel-focus-model)); `dirPath` is used only for containment validation against the project root (the focus root additionally, for an external-tree focus)
- **Per-root result caches for git RPCs** (`backend/frontend_api_gitcache.go`): `GetGitStatus` and `GitIgnoredPaths` results are memoized per repo root (10 s status / 30 s ignored TTL, ≤100 roots, earliest-expiry eviction) behind a canonical symlink-resolved key (`gitCacheKey` → `canonicalWorktreeRoot`): population and invalidation sites hand in different path forms (raw stored project path vs resolved focus root), and a plain string key would strand an entry invalidation can never reach. Invalidation is event-first: every mutating git RPC funnels through `emitGitStatusChanged` → `invalidateGitCaches`; the workspace-watcher debounce always drops the status snapshot and drops the ignored set only on ignore-rule file changes (`.gitignore`/`.aiignore`/`.ignore`); a project switch clears both caches AND the Git-panel focus, so no pathless git RPC can resolve into the previous project's repository during the window before the frontend re-applies focus
- `GetFileDiff(path)` returns unified diff for modified files; for paths outside the active project root (or a non-git path) it returns `("", nil)` — no baseline to diff against, so the frontend does not render a diff panel. The diff runs in the repository that OWNS the file: `ResolveWorkTreeRoot` walks up from the file to the nearest `.git` (a linked worktree's `.git` pointer included), so checkout files keep the checkout baseline while a file inside a session's managed worktree diffs against that worktree's own baseline
- Status integrated into file tree nodes (icon indicators in UI)
- `.gitignore` filtering in directory listings uses `git ls-files --others --ignored --exclude-standard --directory -z`. In a git repo `.aiignore` is layered on top of that git-derived set via an `ignore.Resolver` (only `IgnoredByAIIgnore` is OR-merged, so the resolver's negation-less matching cannot override a git `!pattern` un-ignore). In a non-git workspace (including No Project) the resolver is the sole authority for both files. A resolver-construction failure is non-fatal; the listing returns with whatever flags were already computed.
- `vectorindex.CurrentBranch(ctx, repoPath)` detects the active branch via `git symbolic-ref --short HEAD` (falls back to `git rev-parse --short=12 HEAD` for detached HEAD)
- All git processes are spawned through the hardened choke points — `sysproc.GitCmd` (global baseline overrides) and `GitCmdInRepo` for repo-scoped work (fresh per-repo scan + neutralization, fail-closed); stdout/stderr capture and error propagation are unchanged (errors are never swallowed)
- Non-repository paths are distinguished from failures by matching `"not a git repository"` in stderr; a legitimate non-repo returns an empty result, any other error is returned to the caller. A repo whose `.git/config` cannot be scanned safely reports as non-repo in the boolean predicates (fail closed); the non-repo fallbacks are degraded rather than silently git-free — every git invocation, `--no-index` diff included, spawns through the same fresh scan (a `--no-index` run inside a repository still consults repo config), so the scan failure resurfaces as an error instead of producing output — git never runs un-neutralized (review [53])
- The `git` binary is required for CODE mode. Its absence is detected on project switch in `backend/frontend_api_project.go` via `exec.LookPath`, emitting a `runtime_error` event (dismissable toast) and rejecting the switch. CHAT mode (No Project) never invokes git.
- No Project: `isGitRepo()` returns false (no git operations), `GetGitStatus` returns empty map, `GetFileDiff` returns empty string

### Git Subprocess Hardening

Repositories are untrusted input: a workspace can arrive as files with a hostile `.git/config`, and the config can be planted mid-session. Git executes config-driven programs (hooks, filters, merge drivers, textconv, fsmonitor, signing binaries, editors) on routine operations — including read-only ones — so c0wrk hardens every git process it spawns (full rationale and canary evidence: [ADR-033](../decisions/033-git-subprocess-hardening.md), trust/harden opt-out: [ADR-034](../decisions/034-git-trust-opt-out.md), semantic trust binding: [ADR-070](../decisions/070-git-semantic-trust.md), commit gate: [ADR-059](../decisions/059-commit-hooks-signing-gate.md), control-model view: [../architecture/security-model.md](../architecture/security-model.md#git-subprocess-hardening)):

- **Baseline (every git process):** `sysproc.GitCmd` prepends `-c core.fsmonitor=false`, `-c core.hooksPath=<empty safe dir under ~/.c0wrk/git>`, `-c commit.gpgsign=false`, and sets `GIT_EDITOR=true`. `-c` wins over repo config; the repository is never modified.
- **`GIT_OPTIONAL_LOCKS=0` pin (every repo-scoped spawn):** trusted raw spawns included — this is c0wrk's own watcher-loop prevention, not config neutralization. Without the pin every read-only status/diff refresh opportunistically rewrites `.git/index` (observed as REMOVE+CREATE under fsnotify); the workspace watcher reports `workspace:tree_changed` and the UI answers with more git calls — a self-sustaining refresh loop (~3 events/s). The variable only skips OPTIONAL locks: commands that genuinely require the index (add/commit/stash) still take real locks, and `pinGitEnv` strips inherited values first, so a user export cannot re-enable it.
- **Per-repo neutralization (every repo-scoped call):** `GitCmdInRepo` scans the config of the repository git itself would discover for the path (the `.git` chain is walked up from the given root, covering workspaces rooted at a subdirectory of a repository) fresh on every invocation (no cache) via `ScanGitConfig` and prepends the scanner's `NeutralizingArgv()` (`-c filter.<n>.process=` + `clean=cat`/`smudge=cat`, `-c merge.<n>.driver=false %O %A %B`, `-c diff.<n>.textconv=cat`, `-c diff.external=`/`-c diff.<n>.command=` for the external diff drivers plain `git diff` executes by default, `-c core.sshCommand=ssh`/`-c core.askPass=`/`-c credential.helper=` (+ a per-URL `credential.<url>.helper=` pin) for the transport keys the Git panel's remote operations reach, `-c protocol.git.allow=never` for `core.gitProxy` (no value of the key neutralizes it — git:// operations fail closed instead of executing the repository's proxy), a finding-gated `GIT_WORK_TREE` environment pin for `core.worktree` (no `-c` form beats the key; checkout/reset writes stay confined to the discovered repository root), and — narrowed per review [56] — `-c attr.tree=<empty-tree>` only when include directives exist: the one case per-name pins cannot cover, since an included file may hide a driver definition routed from the in-tree `.gitattributes` (the empty-tree hash matches the repository's object format, SHA-1 or SHA-256). Include-bearing configs additionally derive the name-independent pins `core.sshCommand=ssh`/`core.askPass=`/`credential.helper=`/`diff.external=` for command-bearing keys an included file may arm invisibly, and fail closed outright when the resolved git version is < 2.45 or unresolvable — older git silently ignores `attr.tree` (the version is probed once per process through the hardened chokepoint). Visible drivers no longer derive the blanket kill — their per-name pins cover every routing source, in-tree included — so benign eol/text attributes keep working and a CRLF-normalized repository does not show falsely-modified files or whole-file numstat diffs; while the kill IS active (includes, or a repo-set `attr.tree`) its collateral — normalization off, text files may report modified though unchanged — is disclosed in the intake warning (`(attributes disabled)` finding). Every patch-producing porcelain `git diff` call site additionally passes `--no-ext-diff` so its output stays usable on armed repositories; the `--numstat` call sites (`GetDiffStat`, `GetDiffStats`) need no flag (`git diff --numstat` never runs the external driver), and the other patch producer — plumbing `diff-tree -p` — executes no external drivers absent an explicit `--ext-diff` (verified on git 2.50.1). Linked worktrees scan the common config (resolved through the worktree gitdir's `commondir`) plus the `config.worktree` overlay when `extensions.worktreeConfig` is enabled, merged last-wins like git. The attribute routing sources `attr.tree` does not cover — `.git/info/attributes` and the file named by `core.attributesFile` — are scanned too: every routed driver name gets the same `-c` name pins, and `core.attributesFile=` (empty) disables that source; an attribute source that exists but cannot be scanned fails the whole scan closed (no kill-switch exists for the mechanism). Unscannable config (unreadable, oversized, non-regular file, malformed pointer) → error, no git execution. All repo-scoped call sites in this domain (`git.go`, `vectorindex/git.go`) and the backend git-panel wrappers route through it.
- **Intake warning:** when a project is switched to or an auxiliary work directory is added, `notifyGitConfigRisk` (`backend/frontend_api_gitconfig_risk.go`) scans the config and emits the global `project:git_config_risk` event when it is not provably clean (dangerous keys, include directives — deliberately not followed — malformed or unreadable config). Findings now include the baseline-covered `signing` kind (`commit.gpgsign` truthy-gated; `gpg.format`, `gpg.program`, `user.signingkey` emitted but marked **inert** unless `commit.gpgsign` is armed — dead configuration cannot execute, so inert-only signing configs stay warning-free) — reported so the intake picture is complete and the trust decision is reachable for signing-armed repositories at intake ([ADR-059](../decisions/059-commit-hooks-signing-gate.md)); hook *files* are not config and produce no intake finding — the commit gate below is what surfaces them. A clean repo emits nothing. Detection-only: neutralization in the spawn layers holds regardless of the UI. A trusted repo is rechecked against its stored **semantic** fingerprint on open — inert branch/alias churn silently refreshes the stored snapshot (no event), while a semantic change (or a now-unreadable config) evicts the trust and re-warns with `reason` + a semantic `diff` ([ADR-070](../decisions/070-git-semantic-trust.md)).
- **Trust opt-out & harden:** *Trust this repo* stores the root plus two content-addressed identities of the scanned config (common config, `config.worktree` overlay, `.git/info/attributes`, `core.attributesFile`, include targets): the raw `fingerprint` — the exact bytes the user reviewed — and the `semantic_fingerprint` — the SHA-256 of the canonical serialization of only the DANGEROUS records (a closed inert allowlist of exactly `branch.*`/`alias.*`; attribute-routing and include sources embedded verbatim) — and mirrors the root into the process-wide `core/gittrust` registry, so the spawn layer runs raw git (`sysproc.GitCmdRaw`) for it — its own hooks, filters and signing apply (see [ADR-034](../decisions/034-git-trust-opt-out.md), [ADR-070](../decisions/070-git-semantic-trust.md)). The trust lifecycle keys on the semantic fingerprint and is rechecked on every open: both fingerprints matching stays silent; a semantic match with a raw mismatch is provably-inert churn — the stored raw snapshot is silently refreshed (no event); a semantic change (or an unscannable config) evicts the trust back to hardening with a semantic diff (fail-closed), and a failing snapshot write at trust time refuses the trust outright. *Harden this repo* (`security.harden_git_repos`) is the inverse — always hardened, mutually exclusive with trust. Entries predating the semantic layer are migrated from their stored raw snapshot on the next open; a record whose snapshot is missing, corrupted, or uninterpretable loses its trust (fail-closed) and re-warns with a `(trust unverifiable)` finding.
- **Trust path probing:** a trust decision is honored across every path form a repository root can be spelled under: the backend trust list (`trustedGitRepoEntryFor`) and the `core/gittrust` spawn registry (`GitCmdInRepo`) probe, via `workspace.TrustProbePaths`, the cleaned path, its canonical spelling, the `ResolveGitTrustRoot` and `ResolveWorkTreeRoot` roots and their canonical spellings — deduped, first occurrence first — so a trust recorded under any one form honors every other; every candidate is the same repository's root or the probed path itself, so no prefix/subtree matching ever crosses a repository boundary.
- **Agent-side write gate (sp4rk):** mutating file tools refuse-to-execute-silently on any target inside a workspace `.git` tree — a hard `git_internal_path` judge reason forces the confirmation funnel under any group policy, so the agent cannot be steered into planting hooks/filters for later execution outside c0wrk.
- **Commit gate (withhold-and-decide):** the Git panel's Commit RPC (`backend/frontend_api_git_commit.go`, [ADR-059](../decisions/059-commit-hooks-signing-gate.md)) runs exec-free `DetectCommitSuppression` (`core/workspace/gitcommitsuppress.go`) on every attempt in an untrusted repository: commit-family hooks (`pre-commit`, `prepare-commit-msg`, `commit-msg`, `post-commit`; executable-bit required, `*.sample` ignored, `commondir`-resolved so linked worktrees are covered; a `core.hooksPath` finding yields a single marker without listing the redirected directory) or an *armed* (truthy) `commit.gpgsign` — repo config or the user's global config — is "armed". Armed + not forced → the commit is **withheld**: nothing spawns, no commit is created, and the result carries a non-nil `Suppressed{Hooks, SigningRepo, SigningGlobal}` with a nil error (a decision request, not a failure — the frontend renders it as a notice plus an explicit *Commit hardened (skip hooks)* button, i.e. re-commit with `force=true`; hooks/signing stay neutralized on the forced path). A detection error fails the commit closed. A trusted repository skips the gate and commits raw (hooks/signing execute — that is what trust means). Clean untrusted repositories commit as before with no new friction. Detection inherits the scanner's include posture: `include`/`includeIf` directives are recorded but never followed (ADR-033), so a commit-surface setting defined only inside an included file — armed signing above all — stays invisible and the gate does not fire (accepted; see ADR-059 "Known blind spot", and the intake warning marks every directive). The commit spawn (hardened or trusted, forced or not) gets its own budget — `timeouts.gitCommitTimeout` (default 300 s; quick probes like `rev-parse` keep 30 s) — combined stdout+stderr capture bounded at 64 KiB with a truncation marker (`Output` shows hook/signing output for trusted repos), and `cmd.WaitDelay = 1 s` so orphaned hook children cannot hold the pipes open past the timeout. `git:status_changed` is emitted only when a commit actually landed.
- **Trade-off:** in an untrusted repository, repository-defined hooks and filters — including legitimate ones like git-lfs — do not run inside c0wrk; hooks are stripped and the strip is announced in the warning notice (never silent), and since [ADR-059](../decisions/059-commit-hooks-signing-gate.md) a commit that would silently skip armed commit hooks or signing is withheld outright for an explicit decision instead of landing stripped. A trusted repository opts out — its own hooks/filters/signing run — but the opt-out is bound to the config's semantic content and fails closed back to hardening on any semantic drift; inert branch/alias churn refreshes the stored snapshot silently ([ADR-070](../decisions/070-git-semantic-trust.md)).

### Vector Index

- Dual-indexed: chromem-go vector store (cosine similarity on ONNX embeddings) and bleve BM25 lexical store with a custom `c0wrk_code` analyzer (camelCase splitter → lowercase → stop-en). Both indices share a deterministic document ID (`sha256(path)[:8hex]:{chunkIndex}`); lexical hits enrich their content via `chromem.Collection.GetByID`. Since [ADR-104](../decisions/104-content-addressed-vector-store.md) the ID's path is the file's **root-RELATIVE occurrence coordinate** (slash-separated, `relPathFromAbs`), stored alongside the legacy absolute `file_path` as the `rel_path` commit-metadata key: the same repository layout checked out under any workspace root yields the same IDs, identical bytes at two paths keep TWO occurrences (never collapsed), and read paths resolve `rel_path` against the REQUESTING root for content hydration and result paths (per-request hydration — a chunk indexed under one tree never reports another tree's absolute path; `sourcePath`)
- Embeddings computed via ONNX Runtime (local, no API calls)
- Model: quantized embedding model downloaded by `make fetch-embedding-model` (Unix) or the Makefile-routed `scripts/fetch-embedding-model.ps1` (Windows); the Makefile is the single source of truth — version/URL/dir values are passed from Makefile variables to the PowerShell recipe
- ONNX Runtime shared library: fetched by `make fetch-onnx` (Unix) or the Makefile-routed `scripts/fetch-onnx.ps1` (Windows); the Makefile pins `ONNX_VERSION` plus per-platform SHA256 digests of both the release archive and the extracted shared library, and is the single source of truth. The GPU flavor (cuda13) is a separate opt-in fetched by `make fetch-onnx-gpu`; both targets verify digests fail-closed and keep disjoint version stamps (see the flavor-stamp policy in [ADR-045](../decisions/045-gpu-embedding-provider.md))
- Build-time artifact verification is fail-closed: downloaded, extracted, and cached copies are each SHA256-verified against the pinned digest; a mismatch removes the bad file and aborts with a non-zero exit. An empty digest is an error, never a skip (the no-Intel-macOS-asset case fails closed with a clear message). Installed embedding-model/tokenizer copies are digest-verified too (byte-identical copies); the installed ONNX Runtime library is a byte-identical copy of the verified cache and is never rewritten in place — modifying the signed dylib after signing invalidates its embedded code signature, which macOS enforces with a `CODESIGNING` Invalid Page SIGKILL at `dlopen`. It is additionally guarded by a version stamp (`build/bin/.onnxruntime-version`, mirrored by `scripts/fetch-onnx.ps1`), so an `ONNX_VERSION` bump replaces a stale installed library rather than skipping on the installed-copy short-circuit
- Digest provenance: onnxruntime releases attach no checksum files, so archive digests are pinned trust-on-first-use from fresh downloads of official release URLs and cross-verified against the server-computed `digest` (sha256) field GitHub publishes for release assets in its REST API; the model digest is the official Hugging Face LFS oid from the repository pointer file; the tokenizer digest is trust-on-first-use (a plain git blob there). Every digest is recomputed on any `ONNX_VERSION`/URL bump
- Collections are partitioned per git branch; switching branches selects a different collection pair (`branches/<collectionName(branch)>/` and `lexical/<branch>/`). **Only the active branch is loaded**: each branch has its own stable chromem DB root `<project>/vector_index/branches/<collectionName(branch)>/`, and `Service.SwitchBranch` opens only the target branch's root — so `chromem.NewPersistentDB` enumerates exactly that one collection and never gob-decodes the others (see [ADR-064](../decisions/064-branch-scoped-lazy-vector-index-open.md))
- Storage location: `~/.c0wrk/projects/<projectID>/vector_index/` (per-project, co-located with session data); the per-branch chromem DB roots live under `…/vector_index/branches/<collectionName(branch)>/`, with `lexical/`, `embedding_cache/`, `file_hashes_<collectionName>.json`, and `contentless_<collectionName>.done` staying at the `vector_index/` root (chromem never opens that root, so they are never parsed as collections)
- **Branch generation manifests ([ADR-104](../decisions/104-content-addressed-vector-store.md) §2):** each branch root carries `manifest.json` — `{format: 2, coords: rel-v1, embedding_fp, dims, chunker_fp, ignore_fp}` — pinning the coordinate scheme and the embedding era every document under it was produced with. Generations are SEQUENTIAL: on open, a manifest that is missing or belongs to another era (unknown format, other coordinate scheme, other embedding fingerprint/dimension) resets the branch — the chromem root, the branch's sidecar, its content-less marker and its lexical directory are discarded together, a fresh manifest is published (atomic write, before any document), and nothing of the old coordinates is ever served beside the new ones. The embedding-keyed re-index cost is bounded by the content-addressed embedding cache, which survives generations. The per-branch staging lives inside the ADR-064 layout; the store-level `store/generations/<n>` tree (ADR-104 §3) is the store's canonical durable form (see the §3 chunk-record store bullet below) — the commit-keyed corpora (`branches/branch_snap_<oid16>/`) remain the v1 read-path fallback beneath it
- **§3 chunk-record store + §5 disk ledger + §6 hygiene ([ADR-104](../decisions/104-content-addressed-vector-store.md) §3/§5/§6 completion):** the store's canonical durable tree lives at `store/generations/<n>/` under the storage root — `{format:2, embedding_fp, dims}` manifest, the atomic-rename `CURRENT` pointer (exactly one live generation; an era advance creates an EMPTY successor and advances the pointer — NOTHING under snapshots/ is carried across the boundary, because chunk vectors AND the tables referencing them are era-bound; each snapshot's tables return through the next attach's ordinary build pass, embedding-cache-spared, while refs/ lives outside the generations tree and survives; an UNKNOWN manifest format reads the whole tree as absent — forward compatibility refused), content-addressed chunk records `chunks/<aa>/<C>.chunk` (the normalized-chunk-text sha256 → dims×f32-LE vector, NO text — ADR-049's content-less contract at the store level; identical bytes at any paths/branches/roots cost one record), per-snapshot `snapshots/<oid16>/{occurrences.tab, table.json, lexical/}` (the sorted TSV occurrence rows `path → blobHash, [(C,index,start,end,lang)]` — the chunk index carried explicitly across poison-drop gaps — and the header whose presence is the snapshot's completion marker), and per-root `roots/<fp>/{overlay.tab, overlay-lexical/, sidecar.json, view.json}`. Write ordering everywhere: chunk records land BEFORE any table referencing them; tables land by temp-file + atomic rename. The rename is process-crash-atomic — the crash model ADR-104 §6 enumerates — while the POWER-loss window (a table durable over a record whose bytes never landed) is closed at BOTH ends: every §3 table publication verifies each referenced record by reading its payload back before anything lands (`verifyChunkRecord` — the same read the §3 open performs), and PROVEN damage is repaired in the same pass through the repair hook (`ensureChunkRecord` re-derives, re-embeds and re-verifies the record; a transient I/O fault defers the publish untouched), while the reader that proves a referenced chunk absent or torn unpublishes the snapshot so the next attach rebuilds it cache-spared. The read path opens a published snapshot with ZERO chromem decode (the tables and chunk records ARE the corpus; pseudo-documents are re-derived per read with the metadata the search paths consume), with the v1 corpus store as the fallback (an absent §3 publication or repairable §3-open failure falls back to the v1 decode; other read errors propagate without fallback; BOTH open tracks — the §3 open and the v1 fallback — resolve the snapshot's corpus lexical leg through the same two-legged resolve (`openCorpusLexicalReadOnly`: the snapshot directory's native `lexical/` first, the legacy per-key path second) and the publication gate (`publishedCompatible`) accepts either leg as servable, so a snapshot whose bleve state lives at either location opens from either track; a torn §3 publication unpublishes itself and the next attach rebuilds cache-spared; migrated snapshots keep their bleve state at the legacy per-key lexical path until a rebuild lands it inside the snapshot directory). The §5 disk ledger is walk-computed truth cached by the hygiene pass and surfaced in `GetVectorIndexStatus.store` — unique chunk bytes counted ONCE regardless of reference count, per-snapshot table+lexical bytes, per-root overlay bytes, whole superseded generations — and `vector_index.store_disk_budget_mb` (default off) evicts LRU owner-unpinned snapshot directories under pressure (an evicted snapshot is re-derived by the next attach's corpus pass). The §6 hygiene sweep is silent, switch-riding and single-flighted (the same `sweepMu` as the store migration; Debug-only logs): it removes superseded generations as atomic units (guarded by the generation directories open handles were decoded from), reclaims unreachable §3 snapshots leg-together with their v1 stores (the stage-5 reachability keep set), collects orphan chunk records the current generation's published tables no longer reference (an mtime grace window protects an in-flight writer's deferred table flush), enforces the disk budget, and reaps migrated snapshots' v1 chromem legs PER SNAPSHOT — each snapshot's rollback window closes at its own `table.json` (once the §3 table is the certified complete form, the v1 store is derived state), and the store-wide `store_chunk_records.done` marker is completion telemetry only, never a reap gate; the lexical leg deliberately stays until a rebuild lands it inside the snapshot directory. The v1→v2 chunk-record migration COMPLETES the upgrade with zero inferences: each published v1 corpus converts per-snapshot under the corpus manifest's blob-hash and chunker-fingerprint gates — every legacy document's vector MOVES from `DocumentID(path, i)` to the chunk record keyed by the re-chunked text's `C` (a live root's tree supplies the source bytes; a missing or hash-mismatched source defers the WHOLE snapshot, the all-or-nothing strengthening that keeps a §3 table from ever covering fewer files than the v1 corpus served) — with the snapshot's `table.json` as the per-branch completion marker (replay gate) and the project marker landing only after every published corpus settled
- **Root-local facts are never shared between trees ([ADR-104](../decisions/104-content-addressed-vector-store.md) L4):** the file-hash sidecar is written in the **v6 root-scoped envelope** (`{"version":6,"root":"<rootFingerprint>","entries":{…}}`; the entry grammar is unchanged v5) — a sidecar whose recorded root fingerprint does not match the loading service's bound workspace root is discarded and reconciled from disk, because size/mtime stat facts are properties of a TREE, not of content; bare pre-v6 maps keep parsing as legacy entries. The bound root (`Service.SetWorkspaceRoot`, set by the Manager per project and re-anchored by every indexing pass) also scopes `ValidateCollection`'s relative-key comparison and the deletion path's ID re-derivation, while ignore/eligibility stays per-root by construction: every pass re-walks with the CURRENT resolver and the walk's verdict evicts stored entries a stricter policy excludes (the stored corpus never bypasses policy)
- **Shared corpus + per-root overlays ([ADR-104](../decisions/104-content-addressed-vector-store.md) stage 2, owner/view):** every workspace root of a project shares ONE physical store. Snapshot corpora live at `branches/branch_snap_<oid16>/` (the commit OID is the identity — every branch and worktree at one commit share it), are built once under a single-flight lease through the ordinary full pass, and are published by an atomic `corpus.json` (`{format, coords, embedding_fp, dims, chunker_fp, ignore_fp, collection, files: {rel_path → content_hash}}`); after publication a corpus is IMMUTABLE and is opened read-only — the chromem decode is cached once per process and shared, and the corpus lexical index is opened bleve-read-only (no persister/merger; concurrent readers take a shared bolt lock, so no RW handle may outlive the build lease). Each root keeps a private overlay at `branches/branch_root_<fingerprint>/` as its working store — the whole existing write machinery (indexer, sidecar, debounce, monitor) operates on the overlay, so each physical store has exactly one writer. A root's view = corpus entries whose hash still matches the root's OWN sidecar row, plus its overlay; the visibility filter is applied BEFORE the final top-K trim and the RRF fusion, so a diverged, renamed-away, deleted or policy-excluded file is never served from the corpus. A clean second root attaches by bounded reconciliation only — walk + hash + sidecar adoption, zero embed/chunk/commit. A legacy branch store with a compatible generation manifest is promoted by RENAME (no copy, no re-embed) with the honest `migration-rebuild` status. Attach is fail-closed: an unpublished or foreign-era corpus errors (`ErrCorpusNotPublished` / `ErrCorpusEraMismatch`) and NEVER serves another snapshot's or root's data. The status stream adds `preparing`/`preparation` (view-attach window) and `migration-rebuild` phases; a failed attach surfaces `unavailable`. **A publication is only a publication when every leg an open reads is present**: the v1 `corpus.json` gate therefore also requires the corpus lexical index directory (the v1 open reads it fail-closed), so a corpus whose lexical leg is gone is treated as UNPUBLISHED — the next `EnsureCorpus` finds the target occupied, resets exactly that snapshot's legs (store, lexical, sidecar, content-less marker) and rebuilds the corpus from source, cache-spared. That is the same "proven damage un-publishes, a transient fault leaves the publication intact" rule the §3 path already applies to torn snapshot tables, extended to the v1 leg whose absence used to wedge the snapshot permanently behind a successful-looking publication record. Managed worktrees route onto the project's shared store and shared embedding cache — no per-tree vector storage or seeded cache copies (`WorktreeVectorIndexPath` is cleanup-only)
- **Vector store metadata I/O:** snapshot `occurrences.tab` and root `overlay.tab` use `occurrenceTabMaxBytes` (256 MiB); corpus manifests and file-hash sidecars use `corpusManifestMaxBytes` and `fileHashSidecarMaxBytes` (64 MiB each). These serialized-byte allocation guards allow exactly the bound and are independent of repository size. Reads use `safeio.ReadFileLimited`, retaining regular-file protections; small control records keep the default 10 MiB cap. Occurrence-table writers enforce the same bound before replacement, so an oversized snapshot table gains no completion marker from that attempt. `loadSnapshotTable` preserves read errors with the affected path and marks malformed headers/rows as `ErrCorpusNotPublished`; `openV2Corpus` treats missing table files as absent publication. Other nonrepairable errors stop native open without legacy fallback. Native snapshot read and occurrence-table write size refusals preserve `safeio.ErrTooLarge` through attach-stage wrappers: `Repairable` returns false and `QuarantineScopeOf` returns `QuarantineNoStore`, preserving publication and chunk/cache data and reporting the path and byte limit. A rebuild cannot remove a reader limit. The error remains distinct from OS transients. `readSnapshotTable` keeps its conservative hygiene interface: unreadable published tables make references unknowable and suppress chunk reclamation. Existing sidecar and legacy-manifest probes retain their conservative absence/unknown semantics.
- **Self-healing attach ([ADR-104](../decisions/104-content-addressed-vector-store.md) stage 2, repair):** an attach that fails with a PROVEN store defect (`Repairable`) quarantines exactly the store its failing STAGE names and retries EXACTLY ONCE — a missing lexical leg, a torn record or an undecodable store root heals with no user involvement, while a transient fault (`EACCES`/`ENOSPC`/`EMFILE`/`ENFILE`/`EIO`/cancellation) quarantines nothing. The scope is read off the stage, never guessed from a message: `AttachView` tags its corpus-open and overlay-open stages with `ErrCorpusUnopenable` / `ErrOverlayUnopenable`, and `QuarantineScopeOf` (repairable-only, transient faults yielding no store) maps them onto `Service.QuarantineStoreView`. The CORPUS scope runs under the corpus build lease (one writer per store, so a repair never races a build) and revokes the §3 publication first (`table.json`, whose removal IS the unpublish) before removing that snapshot's occurrence table and lexical leg, its v1 chromem root (`corpus.json` included), the per-key lexical index, the file-hash sidecar and the content-less marker; the OVERLAY scope removes only the named root's private store — branch root, lexical index, sidecar, content-less marker and the §3 `roots/<fp>` state directory. Neither scope ever touches `chunks/` or `embedding_cache/`: chunk records are content-addressed and shared by every snapshot and overlay, and the embedding cache is re-derivable inference work, so neither can be one store's private damage. A transient fault leaves the publication byte-identical and reports `unavailable` with the cause (`ClassifyInitError` → `transient`). A defect the repair cannot clear ends after that one retry with a reported failure that binds NOTHING — no other snapshot's corpus, no foreign-era data — and a cancelled operation destroys nothing.
- **Repair ladder — one automatic step, then fail closed ([ADR-120](../decisions/120-vector-store-repair-ladder.md)):** every failure runs the same bounded ladder. A TRANSIENT fault is the zero-repair rung: the publication stays byte-identical and the status reports `unavailable` with kind `transient`; retrying is a later attempt, not a repair. A PROVEN defect takes exactly one self-heal (the attach quarantine + single retry above). The explicit user rung is `ReindexVectorIndex`: the ordinary path cancels the in-flight pass and reconciles incrementally (a full build only for a legacy mode empty collection), while a view-model index with NO live collection re-attaches the snapshot view — the publication predicate treats the unopenable corpus as unpublished, resets exactly that snapshot's legs and rebuilds from source, cache-spared. Legacy (corpus-disabled) mode keeps the logged no-op because there is no shared store to rebuild. The ladder ends there: no third attempt exists, no branch switch or project reopen is substituted (a cached manager re-runs neither, and a durable corpus defect survives both), and an unrepairable failure is reported with its cause instead of being retried.
- **Incremental-failure backoff and circuit breaker ([ADR-124](../decisions/124-vector-incremental-failure-backoff.md)):** the debounce-armed incremental pass is the background heartbeat, and a broken embedder/runtime turned every file change into a failed inference attempt at full speed. Now the pass outcome is recorded: after the first failure subsequent arms carry an exponential backoff (5 s doubled per consecutive failure, capped at 10 minutes — constants, not config), computed at arm time from the streak through the same `afterFunc` seam, so every timing behavior tests on virtual time. At 5 consecutive failed passes the circuit breaker trips: `NotifyFileChange` stops arming (a timer armed before the trip runs no pass if it fires late), and the status reports `unavailable` with the SEPARATE `suspended` `error_kind` and a reason naming the failure count and the last cause — deliberately NOT routed through `notifyInitFailure`: the verdict is about the embedder/runtime pipeline, not the store, so the ADR-120 repair ladder stays untouched and nothing is quarantined. The trip is pushed onto the focused root's `vector_index:status` stream (superseding the failing pass's own terminal `ready` report in place — with no push the UI's freshest event would stay that ready until the next pull), and the verdict rides EVERY stream push while it stands — including a terminal `ready` report from a failing branch-switch pass, which would otherwise wipe the pair from the UI's event stream and repaint the silent suspension as a bare, healthy ready (the stream counterpart of the stored-status gate). The panel renders the reason and the Resume action from the pair alone, so the suspension stays explained in that corner too. A cancelled pass counts as neither success nor failure. Reset paths: a successful pass (a debounce-armed or branch-switch pass), a manual Reindex, and manager-lifecycle rebuilds — `SwitchProject` carries the reset on both arms as the lifecycle-boundary rule (a new lifecycle must not inherit a suspension it never earned), and since the per-root registry's only production `SwitchProject` is a manager's creation, the rebuilds a user reaches are the `vector_index.enabled` toggle (disable tears the manager down, enable builds a fresh one), the LRU eviction beyond the four-root cap, and an app restart. A Git-panel FOCUS switch is deliberately not a reset: `ApplyFocus` keeps live managers running, so switching away and back returns the same suspended manager — its `suspended` status re-surfaced by the focus snapshot — until one of the resets above runs. The reindex repair pass and branch-switch failures are not breaker inputs; the search panel's repair kind gate SUPPORTS `suspended` — the manager-level Reindex behind the action is the breaker's own reset path (it re-opens file-change arming and relaunches the pass, which fails honestly again if the embedder is still dead), unlike `fatal`, where the registry deterministically rejects the RPC because the embedder never came up
- **Walk skip semantics and published emptiness ([ADR-120](../decisions/120-vector-store-repair-ladder.md)):** any walk error BELOW the root (a subtree deleted or unreadable mid-walk) is recorded as a gap and the walk continues; only an unreadable root fails the pass. `IndexFull` stores the per-pass gap report on the service (only while the working store is still the one the pass belongs to) and logs exactly ONE aggregated WARN naming the skipped count, the first path and the cause; a clean walk replaces the report. Publication reads that report: an empty hash column from a clean walk is `ErrCorpusNoIndexableFiles` with the actionable `no indexable files — check exclude patterns and ignore files`, while gaps make it `ErrCorpusWalkIncomplete` naming them, and NEITHER writes the §3 table or the manifest. The gap cause renders as text (never `%w`), so a missing path is not reclassified as store damage; both degenerate-workspace sentinels map to no-store repair because rebuilding cannot change what the tree contains.
- **Hygiene never reaps under a live build ([ADR-120](../decisions/120-vector-store-repair-ladder.md)):** the §6 orphan-chunk sweep and the count-zero half of the disk-budget eviction are suppressed while any corpus build lease is live — the lease set is sampled before the sweep and re-sampled before eviction, because a build may start during the earlier passes. `StoreLedger.ChunkReapSkipped` reports the skip honestly and `ChunkOrphans` stays zero for that pass. Budget eviction still evicts owner-unpinned snapshot directories (derived state, re-derived by the next attach) but leaves count-zero chunk records on disk with their bytes accounted, so the ledger stays walk-honest and the next pass performs the real reclamation.
- **Shared-store reachability GC ([ADR-104](../decisions/104-content-addressed-vector-store.md) stage 5):** the shared artifacts — snapshot corpora (`branches/branch_snap_*`, `lexical/snap_*`, their sidecar pair) and per-root overlays (`branches/branch_root_*`, `lexical/root_*`) — are NEVER keyed by branch names, so neither the switch sweep nor the delete-triggered purge decides their lifetime from `refs/heads`. Their ownership is recorded on disk under `refs/` as pointer records (atomic rewrite, schema-versioned envelope): a ROOT marker `refs/root_<fingerprint>.ref` (`{root: workspace path, snapshot}` — written by every view attach BEFORE the corpus build, an intent pin that makes a mid-attach corpus unreachable-for-reclamation) and a BRANCH reference `refs/bref_<sha256-of-name>.ref` (hash-keyed so distinct branch spellings never fold onto one marker; pre-hash sanitized markers are honored on read and removed on the next write; `{snapshot}` — written when a root's HEAD is the branch tip at attach, and by the unified migration for every branch whose legacy store it promotes; the branch is a REF pointing at a commit, never a storage key). A root marker is LIVE while its recorded tree path exists; a branch reference lives until its branch's explicit detach. The switch sweep (`Service.PruneMissingBranchData`, both the Service and the manager-free FS form) assembles the keep set from these records — live markers' overlay keys and snapshots, surviving branch references' snapshots — plus the process registry's protection (`CorpusRegistry.ProtectedKeys`: every held corpus handle — a live reader's decode — and every in-flight build lease, so a sweep can never reclaim under a reader or builder; `ReclaimKeys` additionally closes the RESIDENCY LRU's retained zero-ref handles of doomed corpora first, the Windows handle-close ordering). Dead records are removed by the sweep itself (a tree or branch that vanished while the app was not running): the owner detached, its reference goes; the data is reclaimed only when NO other record reaches it. A storage root WITHOUT a `refs/` directory never recorded an owner and keeps every corpus/overlay artifact — the conservative upgrade posture; the first attach's marker opts the store into GC. Unknown files under `refs/` (and every unknown directory shape anywhere in the sweep's scope) are never removed by this mechanism; the legacy `branches/_orphan` root stays keep-forever. The delete-triggered paths detach exactly their own records: `DeleteBranchData` removes the branch's artifacts AND its `bref_` reference (the hash key is injective, so the keep set's both-spellings fold is strictly a conservative over-keep: a surviving branch keeps the shared reference even when only the other spelling matches); `DeleteRootOverlay` (worktree release) removes the root's overlay artifacts — store, lexical, sidecar, content-less marker — and its `root_` marker, never the corpus another owner still reaches. The session-release cleanup carries a resurrection guard (`cleanupReleasedTreeVectorData`): a released tree whose path exists again (a racing adoption's Recreate) keeps everything — its manager, overlay and marker belong to the live tree now — and the same in-window guard re-checks liveness between the registry release and the overlay removal inside `deleteWorktreeVectorIndex`.
- **Unified legacy-layout store migration ([ADR-104](../decisions/104-content-addressed-vector-store.md) stage 3, background, replay-safe):** after every successful view attach a Manager kicks ONE background sweep per physical store (`CorpusRegistry.RunStoreMigration`, `core/vectorindex/layout.go`; single-flighted per store, joined by Shutdown bounded, cancelled by project switch and replayed by the next attach). The sweep drains every legacy layout directly into the corpus+overlay shape: pre-ADR-064 root-level collection directories (re-homed into per-branch stores first — the same shared helper `SetProject` runs synchronously), ADR-064 per-branch stores in the shared root, and every legacy ADR-081 per-worktree store under `worktrees/<name>/`, each with its file-hash sidecar (both grammars — v6 envelope and bare map — feed the corpus hash column), lexical directory and content-less marker as move legs. A promotable store — compatible generation manifest, usable sidecar hash map, content-less marker present, and the lexical index leg present (the publication it would write is unopenable without it) — is promoted by RENAME under its branch's resolved commit OID with ZERO embeddings (`corpus.json` publishes last); every other outcome is a recorded reason in the versioned state file `store_migration.json` (schema 1: per-unit `completed` ids, terminal `skipped` records, atomic rewrite per unit): foreign/absent era, no sidecar hash map, marker absent (pre-049 fat documents are never served from a read-only shared decode — cache-spared rebuild instead), branch absent from the clone, or an existing-but-unpublished target collision (never overwritten; the source stays). A store whose snapshot corpus is ALREADY PUBLISHED is a validated duplicate — its legs are removed and the unit completed. The `done` status is written only after the full recognized volume settled; unknown entries (unrecognized directory shapes, `branches/_orphan`, worktree containers without branch stores) are excluded from the volume, reported as skip records and left in place — a hostile or corrupted recovered name still parks under `_orphan`, never into a traversal path. Crashes, cancellations and transient failures (git facts unavailable, rename I/O, a concurrent corpus build lease — the sweep waits only ~30 s and defers) leave `status=running` with the settled prefix recorded: no document is lost, no false marker, and the next sweep resumes at the first unsettled unit. The sweep holds no Service/registry lock across its run; each promotion takes only the target snapshot key's single-flight build lease, which is the serialization point with corpus builds, while live working stores' sidecar backfill and content-less passes own their stores exclusively by construction. A state file from a newer binary is refused, not rewritten.
- **Storage roots are real directories only:** the vector-index storage roots (`~/.c0wrk/projects/<id>/vector_index` and its `branches/`, `lexical/`, `embedding_cache/` subtrees) are created only through `ensureRealDir` → `safeio.MkdirAllReal`, which follows no symlinks: a dangling link, a non-directory component, or a link swapped into a component being created fails closed (final component included); a pre-existing operator-symlinked tree resolves as intent. A planted link must not redirect the index outside `~/.c0wrk`

- **Indexing walk policy** (`vector_index.*`, edited from the Settings → Search "Indexing" section and applied live — see the `UpdateIndexingSettings` lifecycle bullet in Invariants): the walk honours `.gitignore` and `.aiignore` with each channel individually toggleable (`respect_gitignore` / `respect_aiignore`, pointer bools, default true; a failed checker build falls open to a no-op checker), layers subtractive `exclude_patterns` (doublestar globs matched against workspace-RELATIVE slash paths — they exclude more, never un-ignore a file the ignore files skip) on top, and prunes nested-repo directories (checked-out submodules — `.git` is a regular gitdir-pointer file) unless `index_submodules` (default false) explicitly opts in; the walk root itself is exempt from the nested-repo prune (a linked-worktree root carries the same pointer shape), the pointer `.git` file stays hidden-name-excluded, and hidden-dot entries plus the hard size/chunk limits always apply regardless of every toggle. The resolved policy reaches EVERY walk identically — `IndexFull`'s walk, `ValidateCollection`'s duplicate walk (which turns "no longer walked" into "deleted"), and the watcher's indexability ancestor check — so a policy flip evicts previously indexed files through the next incremental pass instead of leaving them queryable
- **Session-workspace routing (managed worktrees, [ADR-080](../decisions/080-session-worktrees.md), [ADR-081](../decisions/081-vector-per-root-registry.md)):** the vector index is ONE `vectorindex.Manager` PER WORKSPACE ROOT, owned by the backend registry (`backend/vector_roots.go`) — never a re-pointed singleton. **Agent-side routing is context-borne:** the session manager stamps the task context with the session's workspace root (`sdktools.WithWorkspacePathNoProbe`), and the shared search closures (the `semantic_search` tool + RAG-hint injection) resolve THAT root, so a session always searches its own tree (branch detected from the root; since ADR-104 stage 2 a worktree root routes onto the PROJECT's shared store — one snapshot corpus per commit plus the tree's per-root overlay as its working store, see the "Shared corpus + per-root overlays" bullet above) at any moment, regardless of which session is active, visible, or focused — concurrent sessions on different trees get simultaneously live managers (isolation via each tree's per-root overlay over the project's shared store). **User-side routing is focus-borne:** the Search sidebar (`SearchVectorStore`), `GetVectorIndexStatus`, and `ReindexVectorIndex` resolve the Git-panel focus root — the user searches what the panel displays. The focus moves both explicitly (`SetGitPanelFocus`: the worktree switcher) and automatically (`useGitFocusSync` — mounted once at the App root — re-applies the active session's execution workspace on every project AND session switch), and every accepted move re-points the REGISTRY focus too (`focusVectorRoots` → `ApplyFocus`, fail-soft — an unfocusable root logs Warn and never fails the git RPC; the empty reset targets the checkout, not `LeaveFocus`). Because the `vector_index:status` stream carries only the focused root's manager, the status-bar pill reflects the focused tree: after a session starts, its tree's indexing progress is what the pill shows. Manager creation is single-flight per root (two managers never open one chromem storage); the registry keeps a small LRU of live managers (focus pinned, capacity 4) and evicted roots reopen transparently from their persisted gob state. A project switch moves the FOCUS to the project's effective target (saved session's tree, else the checkout) without tearing other roots down; a worktree root's embeddings come from the PROJECT's shared content-addressed embedding cache (`ProjectEmbeddingCachePath` at the project store's `embedding_cache/` root — `Service.SetProject` enables the cache at the project store, and cache roots are never nested because the accounting walk is recursive; the checkout and every worktree share one cache; `WorktreeEmbeddingCachePath` survives only as a legacy cleanup target). Cleanup: releasing a session's tree releases its registry manager first (open chromem handles dropped, Windows-safe removal), then removes the tree's per-root overlay and `refs/` ownership marker from the project's shared store — plus its LEGACY per-tree storage roots and caches (`WorktreeVectorIndexPath`/`WorktreeEmbeddingCachePath`, cleanup-only); project deletion releases every root of the project. No send ever re-points shared index state (the old send-time re-scope is deleted).
- **Stale-branch index cleanup (silent, on project switch):** every branch a repository ever had leaves per-branch artifacts — the chromem DB root under `branches/`, the bleve lexical directory under `lexical/`, plus the branch's `file_hashes_<collectionName>.json` and `contentless_<collectionName>.done` — in the checkout's storage root AND in every managed-worktree storage root that ever indexed it, and nothing ever re-opens them once the branch is gone from the local clone (merged and deleted remotely, dropped by hand, worktree pruned). On every REAL project switch (the same fire-and-forget seam the auto-fetch funnel rides — the already-active early return skips it, app-startup restore rides along) a detached goroutine lists the repository's existing local branches ONCE (`git for-each-ref refs/heads` via the hardened git spawn — the ref set all worktrees share, so branches checked out in managed trees are covered) and sweeps every storage root of the project with `Service.PruneMissingBranchData` (`core/vectorindex/prune.go`), deleting BOTH indexes of every absent branch plus its sidecar and marker. Keeping is decided on the sanitized identities, not recovered names: a stored directory is removed only when NO surviving branch maps to it (a lossy-sanitizer collision between a deleted and an existing branch keeps the shared directory), and three identities are never pruned — the synthetic `default` (`DefaultBranch`, which a real branch literally named `default` also maps to), the legacy-migration `branches/_orphan` root, and the live state's active branch (defensive, even if the caller's list missed it); parked states of pruned branches leave the park LRU with their handles released so a later return never revives a state whose directories are gone. The content-addressed embedding cache is branch-independent and untouched. The sweep is single-flighted per app instance (`pruneStaleBranchesInFlight` — rapid toggles skip, the running sweep reads fresh git state anyway) and silent by the auto-fetch quiet-failure contract: Debug-only logs, no events, no toasts, never a step that can fail or delay the switch; a skipped sweep (No Project, non-git workspace, embedder still loading or unavailable — no manager to sweep through) just leaves the stale data for the next switch, and per-entry removal failures (a concurrent open handle on Windows) are skipped and retried by the next sweep. For the SHARED store's corpora and overlays none of the branch rules apply — the sweep decides those by the ownership records of the reachability GC bullet above, and a `refs/`-less store keeps them all.
- **Deleted-branch and deleted-worktree index cleanup (silent, on Git-panel deletion):** deleting a branch through the Git panel (`DeleteBranch`) fires a detached purge (`purgeBranchIndexData`) right after the successful `git branch -d/-D` and the `git:status_changed` emission: it re-lists the repository's surviving local branches AFTER the deletion (the list drives the lossy-sanitizer collision guard; a listing failure skips the whole purge with a Debug log — the next switch sweep catches the branch up, the purge never guesses) and removes the deleted branch's BOTH indexes plus its sidecar pair from the checkout's and every managed-worktree storage root through `Service.DeleteBranchData`. The purge is deliberately NOT single-flighted — unlike the switch sweep it must run even while a sweep is in flight (that sweep may have listed the refs before the deletion and would otherwise keep the branch's data until the next switch); it is surgical and idempotent (already-absent artifacts remove nothing and count nothing), and it is silent by the same quiet-failure contract (Debug-only logs, no events, no toasts, never a failure path of the RPC). Removing a managed worktree through `DeleteWorktree` drops the tree's whole worktree-scoped storage root — BOTH indexes of every branch the tree ever indexed plus the per-tree embedding cache — synchronously with the RPC via `deleteWorktreeVectorIndex` (the registry release happens first, so open chromem handles cannot keep the directory alive on Windows); an external linked tree never had c0wrk-provisioned storage, so only its live manager is released. Deleting a REMOTE branch touches no local artifacts: the local branch survives, so its stored data stays valid — the local refs set is what both cleanups key on. Since ADR-104 stage 2/5 the same RPCs also detach the deleted branch's OWN reference to its snapshot corpus (`refs/bref_<sha256-of-name>.ref` — hash-keyed, so the detach can never take a colliding surviving branch's marker with it; the collection/lexical artifacts keep the lossy-sanitizer collision guard) and a released tree's cleanup (`deleteWorktreeVectorIndex` via `cleanupReleasedTreeVectorData`) removes exactly the tree's overlay delta and ownership marker from the PROJECT's shared store — the corpora other roots or surviving branches still reach are never touched, and a resurrected tree (its path exists again after release) keeps everything.
- A `GitMonitor` watches the git directory that owns HEAD via fsnotify — `.git` itself for a checkout, or the private git directory a linked worktree's `.git` pointer file names (`resolveGitDir`) — and triggers re-partitioning on branch change; in a linked worktree a branch switch (and a detached-HEAD commit, which rewrites HEAD itself) lands in that private gitdir, never in the pointer file, so pointer resolution is what keeps monitoring alive there. The checkout monitor's watch never covers a worktree's private gitdir (per-directory watches, not recursive), so worktree-internal churn stays invisible to the checkout's index.
- **Readiness generation:** every `SetReady(false)`/`MarkNotReady` bumps `readyGen`; an indexing pass that owns the readiness cycle captures the gen at start (`MarkNotReady`, one lock acquisition) and `RestoreReady` re-arms readiness only if the gen still matches — so a stale pass from an outgoing project, whose defer runs late after cancellation, can never mark a freshly-switched or closed project ready. Ownership is conditional since ADR-125 (the staged-acquisition bullet below): a pass that entered already-ready over a queryable collection keeps readiness up and touches neither the readiness state nor `readyGen` — it never calls `MarkNotReady`, so it defers no `RestoreReady` at all and searches keep answering between its windows.
- **Staged indexing lock acquisition ([ADR-125](../decisions/125-indexing-lock-model.md)):** a full/incremental pass no longer holds the service write lock (`s.mu`) for its duration — search, status, `Close`, a branch switch and the No Project reset are never frozen behind a pass. The pass holds a dedicated PASS LEASE (`passLease` on the service, taken before `s.mu`, never the reverse; `Close`/`SwitchBranch`/`SetProject`/the reset applier never touch it) that restores the pass-vs-pass exclusion the whole-pass hold used to provide (the manager's debounce guard explicitly does not serialize passes), and it commits each mutating step — one accumulator commit window (§3 chunk records + chromem commit + per-file sidecar publishes land together), a poison-drop sidecar publish, one legacy `AddDocuments` batch, the incremental delete phase (enumeration + chromem/lexical deletion + sidecar drop atomically), the corpus-adoption reconciliation, the final file count — inside a short identity-checked WRITE WINDOW in the per-batch discipline `RebuildLexical`'s flush windows established: under the lock the pass re-validates the working-store identity it captured at start (state + collection + lexical pointers), so a switch/reset/close that displaced the store between windows aborts the pass with `ErrWorkingStoreDisplaced` instead of committing into a store it no longer owns; within a held window no displacement can occur (every displacer takes the same lock), so the publication ordering — chunks before the commit, the commit before the file's sidecar row, deletions before re-indexing — is exactly what the whole-pass hold serialized. Preparation (walk, read, hash, chunk) stays lock-free, and INFERENCE runs outside every window through the embedding cache captured with the identity: the cache is internally synchronized and never torn down by state teardown, so a displacement wastes inference, never corrupts. Readiness is conditional: a pass entered ALREADY-READY over a queryable collection keeps readiness up and serves the committed-so-far state between windows (the watcher-driven mid-session pass — the `semantic_search` tool answers during a slowed pass), while a pass entered NOT-ready (fresh project, post-switch reconciliation, corpus build) keeps the historical `MarkNotReady`→`RestoreReady` cycle. A displaced pass classifies as no-store under the repair ladder: no quarantine, the publication stays byte-identical, and the next trigger (watcher, reindex, replayed attach) reconciles from source. The corpus build path's ladder is now `build lease → passLease → s.mu`; nothing acquires `s.mu` and then the lease, so no cycle exists
- **Init publication protocol:** all `initProject` publications (indexer, `workspacePath`, `indexCtx`, `gitMonitor`) re-check ctx under `m.mu`; `SwitchProject` cancels `initCancel` while holding `m.mu`, so check-then-publish is atomic with the cancellation point and an orphaned init cannot install state over the newer project's teardown. `SwitchProject` never drains `initWG` — cancellation + per-step ctx checks + `s.mu` serialize; only `Shutdown` waits (bounded)
- **Indexing-work seal:** a positive `sync.WaitGroup.Add` concurrent with `Wait` is a fatal panic. Every late work registration (`Reindex`, a debounce-fired pass, a git-monitor branch switch) goes through `addIndexingWork`, and `SwitchProject`'s async init launch goes through the same-seal `addInitWork` — both refused once `Shutdown` has sealed the manager (`wgClosed` under `wgMu`), so an `Add` either happens-before `Shutdown`'s drain (or the zombie closer waiting behind it) or never happens. A switch arriving on a sealed manager fails fast with `ErrManagerShutdown` (checked before the No Project reset too), and the `initProject` pass's internal indexing `Add` needs no guard because the init goroutine is joined via `initWG` first
- **Bounded shutdown drain + zombie closer:** `Shutdown` waits each goroutine group (init first, then indexing) for a bounded grace (`shutdownIndexGracePeriod`; test-overridable via `shutdownGrace`); a goroutine stuck in non-interruptible work (chromem gob-decode, `os.ReadFile`, synchronous ONNX inference) cannot be interrupted, so on timeout the blocking `service.Close()`/`closeFn()` are skipped and `Shutdown` returns by the grace either way. The expiry is logged as evidence: one WARN carrying the skipped closes BY NAME (`service.Close`/`closeFn`) plus a capped (512 KiB) all-goroutine `runtime.Stack` dump (with a `dump_truncated` flag) whose holder stack names the exact blocking call on an unreachable user machine, and — when the embedder-wedged probe fires — the explicit ONNX-thread diagnosis. The probe is the AUTHORITATIVE wedged status, and sp4rk is its source: `embedding.Embedder.Wedged(bound)` reads a per-job heartbeat the ORT runner worker stamps itself at job start/end (`embedding/runner.go`), so it can tell a thread stuck INSIDE a C inference call (a heartbeat that ages past any bound) from merely slow inference — something a caller whose embed call timed out or was cancelled can never do. Consumers consult this query for the diagnosis instead of inferring a wedge from a streak of consecutive timeouts; the timeout bound (the drain grace) stays solely the backstop that bounds the wait and is deliberately NOT the probe's bound — the supervisor applies the embed-call deadline (the healthy-inference envelope, 90 s) as `Wedged`'s bound, because healthy inference can legitimately run tens of seconds past the short drain grace and a grace-bounded probe would fabricate wedge verdicts for every shutdown that races a normal slow batch. Idle (between jobs), a CPU-provider embedder (no dedicated runner thread exists to wedge) and a non-positive bound are never wedged; the worker's own evidence log trails every job at Debug (start/finish with sequence and duration) and WARNs one line per job whose duration reaches the near-wedge threshold (`slowJobEvidenceThreshold`, 30 s). The skipped close is never lost: the ZOMBIE CLOSER, a goroutine that waits for the stuck pass(es) to return and then runs the same `closeResources` sequence as the clean path, releases the handles eventually — which matters whenever the shutdown was an LRU eviction or a Disable rather than a process exit. Reopening while a zombie lives is legal: the fresh manager opens the persisted storage from disk (derived state rebuilds; damage from a foreign open handle is what the attach quarantine treats), and the registry's eviction wait stays bounded (`vectorRootsEvictWait`, 25 s — it bounds Shutdown's RETURN, never the zombie's deferred close). The whole expiry contract is covered by virtual-time (`testing/synctest`) tests over a hung-pass seam: grace return with zero wall time, evidence attrs, close strictly after the pass returns, and the sealed-manager reopen refusal
- **File-change trigger set:** `PostExecuteHook` notifies the vector-index manager after every tool in `FileMutatingTools` (`write_file`, `edit_file`, `bash_exec`, `posh_exec`); the 1s debounce coalesces bursts, but every isolated shell call triggers a full incremental sweep — `ValidateCollection` reads and hashes every indexable file (O(files) even with no changes). Accepted tradeoff: search freshness after shell-driven changes beats hot-path cost; revisit if profiling shows indexer pressure during heavy coding sessions
- Hybrid search fuses the two ranked lists via Reciprocal Rank Fusion (`score = Σ 1/(k+rank)`, `k=60` by default). Per-side fanout is `max(topK × fanout_multiplier, fanout_min)` (defaults 4 / 100); `FilePattern` (doublestar glob) and `MustMatch` post-filters are applied **before** fusion so rank spaces are comparable. Pre-fusion **score thresholds** discard noise-tail hits before fusion: vector hits below `hybrid_vector_score_floor` (absolute) or `hybrid_vector_score_ratio × top similarity` (relative, default 0.25) are dropped; lexical hits below `hybrid_lexical_score_ratio × top BM25` (relative, default 0.1) are dropped. This prevents weakly semantic chunks that merely contain a query term from earning a double RRF contribution and jumping above one-sided relevant hits. Thresholds apply only in the hybrid path; vector-only and lexical-only modes return raw top-K without score gating. See ADR-013.
- **File-pattern matching parity:** hybrid-search `FilePattern` matching (`matchFilePathPattern`) mirrors the frontend `pathFilter` logic (picomatch with `contains:true` plus basename testing; the Go side tries a direct doublestar match, then a `**/`-prefixed relative pattern, then a basename match) so the sidebar search filter and the file-tree filter accept the same patterns. The parity is a FE↔Go contract; a strategy change on either side must update both.

- **The pre-open state is announced honestly, and the open is branch-scoped.** Both paths that perform a branch-scoped open publish a distinct `{state: "loading", phase: "open"}` (the manager's own status AND an `OnProgress` emission) *before* the open: `initProject` before `Service.SetProject` + `SwitchBranch`, and `Indexer.HandleBranchSwitch` before the `SwitchBranch` a `GitMonitor`-detected branch change triggers (there the announcement guard is the exact negation of `SwitchBranch`'s own early-return condition — `branch == currentBranch && collection != nil` — so it fires for precisely the calls that really open and never flickers the pill on a same-branch no-op, while still covering a retry after a failed open, which leaves `currentBranch` naming a branch whose collection is gone). The branch-scoped open (see [ADR-064](../decisions/064-branch-scoped-lazy-vector-index-open.md)) still gob-decodes the active branch's collection and can take seconds. This state carries **no progress fraction** and is rendered as a plain "Preparing index…" — never the `indexing`/`Vector: building` shape — so the status bar does not claim to be indexing while it is only opening. Real `indexing`/`reindexing` progress (with `phase` + `files_indexed`/`total_files`) begins only once a pass actually starts. A **failed** branch-switch open emits the terminal `unavailable` immediately after the failed `SwitchBranch`, mirroring the deferred terminal emissions of `IndexFull`/`IndexIncremental` (a pass that fails with NO collection emits the same terminal `unavailable` instead of `ready` — previous data is not queryable when nothing exists to query — and the debounced watcher pass is skipped outright while the collection is missing). Leaving the announcement in place instead parked the status bar on "Preparing index…" until the next branch change or project switch — the whole session for a user who does not switch, with the search panel claiming results will "appear automatically when ready". `IndexingStatus` renders `unavailable` honestly (idle dots, an "Index unavailable" label, no progress bar — the same dishonesty rule that removed the fake 0% bar for `loading`), and its hover carries the backend's `last_error` and `error_kind` ([ADR-120](../decisions/120-vector-store-repair-ladder.md)). The reindex action stays ENABLED under it WITHOUT the busy spinner — nothing is running, and the backend escalates the request into a re-attach/rebuild of the unopenable corpus; neither a branch change nor a project reopen is a remedy (a cached manager re-runs neither, and a durable corpus defect survives both). An init-fatal failure on the project-open path reaches the same `unavailable` through `OnFailure` (`notifyInitFailure`). Until the pre-open state lands the frontend otherwise has no status at all: the status bar renders nothing (`IndexingStatus` hides itself on the store's `idle` default) and the vector search panel claims "Select a project to search" while a project IS selected.
- **The No Project (CHAT) reset never blocks the project switch.** `Service.ResetForNoProject` tries the service write lock and, when a holder has it — the branch-scoped open (`Service.SwitchBranch`, [ADR-064](../decisions/064-branch-scoped-lazy-vector-index-open.md)), an indexing pass, `AddDocuments`, `ValidateCollection`, a Browse — *queues* the reset instead of waiting. The queued request is stamped with the current open generation and delivered by exactly one of two appliers: a `SetProject` still in flight applies it as its own final act under the lock (the request carries that open's generation); otherwise the background goroutine `kickNoProjectResetApplier` — which, unlike the caller, is free to block — waits until every in-flight open has drained, then takes the lock and applies the still-current request. Since ADR-064 the *long* holder is `SwitchBranch`, which is **not** a generation applier, so a reset queued behind a branch-scoped open lands through the background applier the moment that open releases. A `SetProject` started after the request supersedes it (it bumps the generation), so a queued reset can never wipe a freshly opened project. Waiting inline used to hold the backend's `switchMu` for the entire open, so every CHAT/CODE toggle died on its bounded acquire (`switchLockTimeout`, 5 s) and the frontend swallows the toggle's rejected promise (`switchProjectWithState`) — an apparently dead button for minutes. The bounded-acquire failure now also emits `runtime_error` (`error_code: "project_switch_busy"`) so the failure reaches the user; readiness is dropped before the reset so a search issued in the interim never serves the outgoing project's collection.
- **The switch critical section carries ONE deadline, and a busy lock dumps goroutines.** Every store round-trip inside `SwitchProject` is individually bounded (`storeOpTimeout`/`sessionStoreOpTimeout`/`restoreDBReadTimeout`, 15 s; `terminalPathLookupTimeout`, 10 s), but the section performs a SEQUENCE of soft-failing ops (best-effort persistence warns and continues), so on a saturated machine — a worktree full reindex saturating disk I/O while every op queues behind the shared SQLite pool — the holds STACK: each op burns its full budget and the sum parks `switchMu` for minutes, reproducing the "Another project switch is still finishing" loop even though no single step is unbounded (observed in the wild on a Linux user machine; a ~38 s partial stack is in the local 2026-09-17 log). The switch therefore derives every store read/write from ONE ctx carrying `switchSectionTimeout` (30 s, `frontend_api.go`): `GetProjectCtx`/`ListProjectsCtx` (backend/project) and `ListSessionsByProjectCtx` (backend/session) are the caller-deadline variants, `switchStoreOpCtx` derives per-op budgets from the section ctx, and the vector leg's root resolution (`switchProjectSetupVector` → `ApplyFocus` → `ManagerForRoot` → `resolveRootPlan`) runs its projects listing on `ListProjectsCtx` under the same section ctx. Two known waits inside the section are deliberately NOT derived from it: `createSessionForProject` pre-checks the spent budget and then runs the deadline-less full orchestrator build (a build that started with budget left still runs to completion), and `ManagerForRoot` can wait out an in-flight LRU-eviction drain for up to `vectorRootsEvictWait` (25 s, time-bounded). A hold ≥ `switchHeldWarnThreshold` (3 s) logs a WARN with the total — the observable backstop for exactly those waits. The bounded-acquire failure additionally calls `dumpBusySwitchHolders` — a capped (`maxBusySwitchDumpBytes`, 512 KiB) all-goroutine `runtime.Stack` dump at WARN next to the timeout line — so the next occurrence on ANY machine (the reporting one may be an unreachable user box) names the exact stuck line in the log without live debugging. The deadline degrades best-effort steps (they skip and warn); pre-activation failures still abort the switch cleanly before `switchProjectActivate` commits.
- **The frontend seeds its index status from the getter**, not only from push events: `useVectorIndexStatus` calls `GetVectorIndexStatus` on mount, on every active-project change, and on `backend:ready`, because for an already-built index the backend emits no status event at startup — which left the store on its `idle` default (empty status-bar pill + "Select a project to search"). Focus moves need no re-poll: `ApplyFocus` publishes a re-sync snapshot onto `vector_index:status` synchronously with the focus move, so the pill follows the Git-panel focus — after a session starts, the status bar reflects that session's tree indexing.
- Oversized files are skipped before full reads during project walk and collection validation, with `processFile` repeating the size check as the universal incremental-index backstop. Files whose structure-aware split exceeds `max_chunks_per_file` are skipped as one unit; the remaining index pass continues.
- ONNX inference uses the configured embedding batch capacity and carries the unfinished tail across file boundaries and 200-document commit windows; only the final inference of an indexing pass may be underfilled. Already-embedded documents are committed to chromem in windows of at most 200, preserving bounded memory/cancellation latency. A file's hash sidecar entry is published only after every one of its chunks has committed (or has been deliberately dropped by poisoned-text fallback), so a partial large-file commit is never classified as complete.
- Embedding inference policy is a cross-repo contract (see [ADR-036](../decisions/036-vector-index-embedding-optimization-policy.md)): generic ONNX logic — persistent fixed-shape sessions (eager batch-1 query session, lazy `[BatchSize, MaxSeqLength]` batch session), opt-in length buckets, opt-in tokenization/inference pipeline — lives in sp4rk's `embedding` package, while embedding persistence (content-addressed cache, commit windows, fingerprints) lives here in `core/vectorindex`, which never imports the ONNX runtime directly. c0wrk consumes the sp4rk defaults (automatic mode) and deliberately exposes no inference-strategy knobs: length buckets, the batch pipeline, and parallel sessions stay behind their benchmark gates (fixed-512 serial single-session remains the production path), and flipping any of those defaults requires a new checked-in benchmark decision, not a host flag.
- Non-UTF-8 file content (legacy single-byte encodings, corrupted bytes passing the NUL-header sniff) is sanitized in `processFile` before chunking — undecodable sequences become U+FFFD, matching the lossy conversion sp4rk's `Tokenizer.Encode` applies — because sugarme/tokenizer panics on invalid UTF-8. The recorded `content_hash` still covers the RAW on-disk bytes so `ValidateCollection` unchanged-file detection keeps matching.
- Content-triggered embedding failures are isolated, not pass-fatal: when an embedding chunk fails as a unit, each text is retried individually and only texts that also fail alone are dropped (WARN-logged) from BOTH the chromem commit and the lexical upsert, so the indexes never diverge; the file-hash sidecar still records the file (a deterministic content failure must not burn embedding work on every pass). If EVERY text in a chunk fails individually, the embedder itself is broken and the pass aborts with an error.

Memory program (see [ADR-049](../decisions/049-vector-index-memory-reduction.md)):

- **Content-less storage contract**: on the batch path chromem stores only `ID` + `Embedding` + the four chunk-position metadata fields (`file_path`, `start_line`, `end_line`, `language`); chunk `Content` and per-file bookkeeping (hash/size/mtime) are NOT resident — per-file facts live in the file-hash sidecar row. Search reconstructs content best-effort from the source file (`contentResolver`: bounded read ≤ `max_file_size`, `lines[start-1:end]`, per-call path→lines cache); a missing/unreadable file yields the placeholder `[content unavailable: source file missing or unreadable: <path>]`, never an error, and `must_match` filters on reconstructed text so deleted files drop out. Hydration fills only the final top-K; legacy-stored content stays authoritative where present.
- **Sidecar entry format v5** (`content_hash|size|mtime_unix_nano|chunker_fingerprint|chunk_set`, `|`-separated; 3/4-field legacy entries keep parsing): the 5th field (`idxset`) records the file's committed chunk-index set — contiguous `0..N-1` as the bare count `"N"` (empty → `"0"`), gapped sets (poison-drop survivors) as `"L:0,1,3"`. Parse is strict and capped (`1<<20` entries): malformed/oversized values downgrade the entry to legacy. An older binary's 3-or-4-field parser treats a 5-field entry as a legacy bare hash — slower but correct. Since ADR-104 the per-file keys are the root-relative occurrence coordinates (under a bound workspace root) and the on-disk file is the v6 root-scoped envelope (see the storage bullets); the per-entry grammar is unchanged
- **Enumeration without materialization**: with a known chunk set, document IDs are pure arithmetic on the deterministic `DocumentID(path, i)`; `collectDocumentIDs`, `RebuildLexical` v2, migration probing, and `ValidateCollection` stats never issue the materializing full-collection `Query(" ", N)`. Unknown set → all-or-nothing fallback to the legacy space-query. Enumeration uses a first-axis unit query vector (`QueryEmbedding`) when the embedding dimension is known, so Browse costs no ONNX inference. `RebuildLexical` v2 walks the sidecar (known fingerprint + chunk set → re-chunk → same IDs; zero ONNX) with a fallback to the collection-query path for empty/ineligible sidecars.
- **One-time content-less migration**: each collection is migrated in the background to the stripped shape exactly once, tracked by the marker `contentless_<collectionName>.done` next to the branch sidecar. The migration waits for the file-hash backfill, probes documents without the service lock, re-commits them in ≤200-doc windows with the same IDs/vectors and stripped content (chromem rewrites each per-doc gob in place), writes the marker only on full success, then frees OS memory. Cancellation (project switch, park/eviction, close, branch switch, rebuild) leaves every document individually consistent (legacy or stripped, never half) without the marker — the next open replays to completion. `IndexIncremental` waits for the migration before deleting/re-indexing.
- **File-hash sidecar trust protocol:** an empty sidecar is trusted only when the content-less marker certifies the collection stripped (its backfill could never recover hashes); with the marker absent, an empty sidecar is an in-flight placeholder or a failed backfill (`fileHashMigrationFailed`) — never trusted, never persisted by park/eviction, never used to certify the collection; it is re-settled on every load (`loadFileHashes`)
- **`ValidateCollection` stat fast-path backstop:** unchanged detection trusts size+mtime as a content proxy; a rewrite preserving both (archive extraction, some file-sync tools) escapes until every `fullHashRevalidationEvery`-th pass (20) skips the fast path and re-reads+re-hashes every file — amortized ~5% of a pass, detection window ≤20 incremental passes
- **Park budget in bytes**: parked state footprint is estimated as `documents × (embedding_dims × 4 B + 1 KiB)`; right after parking, the oldest parked states are evicted (sidecar flushed, then `freeOSMemory` outside the lock) while the sum exceeds `park_budget_mb` (default 1024 MiB; negative disables the byte budget; explicit 0 is rejected at load as ambiguous). The effective parked-RAM bound is `min(park_capacity, park_budget_mb)`; `park_capacity: 0` disables parking entirely regardless of the budget.
- **Corpus residency (ADR-104 §5)**: the shared corpus owner (`CorpusRegistry`, process-level) may RETAIN zero-reference corpus handles in an LRU bounded by `corpus_residency_capacity` (count) and `corpus_residency_budget_mb` (summed `estimateCorpusHandleBytes` = `docs × (dims × 4 B + 1 KiB)` per handle, charged once however many roots view it) — default 0/0 = retention OFF (a released corpus closes at once; A→B→A re-decodes, the pre-residency behavior). With retention on, A→B→A re-attaches the SAME handle — no chromem re-decode, no lexical reopen. Parking releases a state's corpus reference into this LRU (the park estimate keeps sizing the OVERLAY only — no double counting); an LRU-evicted root manager likewise leaves its corpora to this budget. Attached handles are pinned by the refcount (the read lease) and never evicted; eviction is oldest-eligible, enforced at the overflowing release or policy re-apply (a retained handle too big for the byte budget alone is evicted; an attached oversized one never is — the bounds govern retention, not admission, and are NOT a hard RSS cap). Every actual eviction schedules `freeOSMemory` off the store lock. The knobs have no sentinels: 0 is documented, negatives are rejected at load. `DeleteProjectData` drops the storage root's whole residency; `ShutdownAll` closes the registry after the manager drain; a `Disable()` keeps retained corpora (the enable cycle reuses them); No-Project creates no corpus store at all.
- **GC memory hygiene**: `runtime.memory_soft_limit_mb` (0/unset = AUTO = clamp(50% physical RAM, 2 GiB..8 GiB); >0 = explicit MiB; -1 = off; < -1 fails load) is resolved once at startup — precedence: off → explicit config (beats a `GOMEMLIMIT` env var, logged) → `GOMEMLIMIT` env (beats AUTO) → AUTO — and applied via `debug.SetMemoryLimit` before background indexing. `debug.FreeOSMemory` runs after every full indexing pass, after park evictions, and after the migration; incremental passes do not scavenge.
- **RSS observability**: the `GetProcessMemory` RPC feeds the StatusBar's live `RSS NNNN MB` indicator (5 s polling, exact-bytes tooltip); failures hide the indicator silently.
- **×branches multiplier closed ([ADR-064](../decisions/064-branch-scoped-lazy-vector-index-open.md))**: ADR-049's program bounds the per-collection resident constant, but one multiplier sat outside its option list — the eager whole-project open used to gob-decode **every** branch's collection at `SetProject`, so resident memory scaled with the number of ever-indexed branches. Per-branch DB roots close that multiplier: only the active branch's root is opened (at `SwitchBranch`), and a parked/resident project state now holds **one** branch's DB instead of all of them — `estimateStateBytes`, eviction, and sidecar-flush semantics are otherwise unchanged (they were already sized off a single collection).
- Used for:
  - `semantic_search` tool (agent searches code by meaning; accepts `mode`, `must_match`, `file_pattern`, `top_k`)
  - File Viewer **Find Similar**: when text is selected, the context-menu action runs vector search with that selection and opens the standard vector-results panel
  - RAG hint injection before routing/planning (top-5 relevant files)

Manual forced reindex: the search panel's mode-selector reindex action (`VectorSearchFilters` via `useVectorReindex`) calls `ReindexVectorIndex`. The manager cancels any in-flight pass, then reconciles the current index against the workspace (`IndexIncremental`), falling back to a full build (`IndexFull`) in legacy (corpus-disabled) mode when no index exists yet (empty collection). A MISSING collection (a failed open/attach — the `unavailable` state the pre-open paragraph above covers) is NOT skipped: in the corpus (view) model the manager re-attaches the snapshot view, which drives `EnsureCorpus` again, so an unopenable corpus (an absent lexical leg, a foreign era, a torn §3 table) is discarded and rebuilt from source, cache-spared. Nothing destructive touches the per-root overlay or the embedding cache — only the snapshot corpus legs are reset. Legacy (corpus-disabled) mode keeps the logged no-op, since there is no shared store to rebuild. It is rejected for No Project (CHAT) mode, where vector indexing is disabled — the action is hidden entirely there rather than rendered disabled — and reports progress through the same `vector_index:status` events. The pass targets the workspace stored alongside the indexer (read under the manager lock), so it can never be pointed at a different project than the one the indexer belongs to. The button is disabled (and shown spinning) while the index is already busy — a pass in flight, the branch-scoped chromem DB still opening (`loading`, [ADR-064](../decisions/064-branch-scoped-lazy-vector-index-open.md)), or the ADR-104 stage-2 pre-work (`preparing` / `migration-rebuild`); its tooltip names the real reason, so the open is never labelled a reindex. At the terminal `unavailable` it stays ENABLED and labels itself `Rebuild index — recreate the broken index from source`: the user's repair path, with no branch switch or project reopen required (neither re-runs the attach for a cached manager, and both hit the same durable corpus defect). The ADR-124 `suspended` kind is the labeled exception — the collection is live and the same manager-level Reindex runs a validation-based reconcile that RESUMES indexing and re-arms file changes (the breaker's own reset path, which fails honestly again if the embedder is still dead), so the action reads `Resume indexing — rerun the pass and re-arm file changes` instead of promising a rebuild it does not perform. Only the master-switch `disabled` state disables it, with its own tooltip. Via an optimistic latch the action is additionally inert during the brief window between the click and the first `vector_index:status` event, so a fast double-click cannot fire a duplicate RPC; the latch is released once the store reflects the busy state, when the project becomes unavailable, when the index enters the terminal `unavailable` (a repair that produced no collection — the action stays available for another attempt), or when the RPC rejects. The escalation is one rung of the bounded repair ladder ([ADR-120](../decisions/120-vector-store-repair-ladder.md)): the request either re-attaches/rebuilds once or reports the failure — it never loops.

**Startup preload / first-`SwitchProject` idempotency:** the startup early projects/sessions emit (`preloadProjectsAndSessions`) must NOT set `activeProjectID` — it would trip `SwitchProject`'s idempotency guard on the frontend's first post-`backend:ready` call and skip vector index initialization; `activeProjectID` is set properly by that `SwitchProject` call (the emit itself: `backend/startup_phases.go` `preloadProjectsAndSessions`).

#### Pass Liveness

Every full and incremental indexing pass is liveness-bounded by four cooperating mechanisms plus a user-visible sub-status; none of them interrupts a healthy pass, and every bound is a deliberate constant, not config.

- **Pass-stall watchdog** (`core/vectorindex/stall_watchdog.go`): a pass that emits no progress point — no processed file, no stage transition, no embed or commit batch — for the fixed `passStallTimeout` (5 minutes) is treated as evidence of a wedged pass, not a deadline: the watchdog never interrupts the pass. It fires exactly once per stall window, logging ONE Warn carrying the bounded pipeline stage (`TelemetryStage`), the last file path the pass prepared (an explicit user-approved decision for this diagnostic log; stage telemetry stays content-free) and a capped all-goroutine stack dump (512 KiB cap, `dump_truncated` flag — the same `goroutineDump` helper the shutdown evidence path uses). A generation counter silences a fire racing a heartbeat, so a spurious or repeated dump is impossible, and `watchContext(ctx)` releases the watchdog the moment the pass context cancels — a cancelled pass unwinding out of an uninterruptible read can never trip it. IndexFull, IndexIncremental and RebuildLexical (its collection-fallback included) start the watchdog before the walk/validation and stop it via defer; the timer factory (`stallAfterFunc`) is a test seam. The walk stages are NOT boundary-only: both workspace walks — IndexFull's own and ValidateCollection's — feed the watchdog per VISITED directory entry (every entry counts, ignored and hidden ones included, throttled to one heartbeat per `walkHeartbeatEvery`, 30 s, via `walkHeartbeater`), so a legitimately slow traversal on network or cloud-placeholder storage — the population the storage-liveness advisory below names — never reads as stalled, while a single hung stat (no further entries arriving) still fires on schedule. Three waits run with the watchdog SUSPENDED instead (`suspend`/`resume`: the generation is bumped so a fire racing the suspension stays silent, and `resume` arms a fresh window) — the pass-lease acquisition in IndexFull and IndexIncremental (the queue wait is unbounded — one pass runs at a time, and a healthy pass queued behind a legitimately long predecessor must not read as stalled; the queue-holding pass's own watchdog owns the wedge evidence) and the one-time sidecar migration waits — IndexIncremental's file-hash/content-less pair (`waitSidecarMigrations`) and RebuildLexical's file-hash wait — which block on background backfill work the pass does not own, so however long they last is not silence of this pass.
- **Stalled sub-status** (`Manager.IndexStatus.Stall`, `recordStall`): every watchdog transition reaches the Manager under `statusMu` — a fired snapshot records `{Stalled, Stage, LastFile, SilentFor, Watch}`, and the per-watchdog `Watch` identity makes a resolve from a DIFFERENT watchdog (two overlapping passes) unable to clear a live stall. Any progress callback or status reset clears the stall — progress is the liveness proof — and `GetIndexStatus` recomputes `SilentFor` live on every read; callbacks run outside every manager lock. The backend answers each transition by re-reading a FULL status snapshot and streaming it over the focus root's `vector_index:status` channel, so the push stream and `GetVectorIndexStatus` agree: `stalled` / `stalled_stage` / `stalled_seconds` (all `omitempty`) are visible exactly while the window is open, on the same 5-minute threshold.
- **Per-file read watchdog + read-skip budget** (`core/vectorindex/readwatchdog.go`): both read stages of every file — the binary-header pre-read and the full read — run under a 30-second deadline (`fileReadWatchdogTimeout`) via injectable seams (`readFileFn` / `binaryHeaderFn`); a stage timeout skips the file ("read timeout") under the pass's ordinary warn-and-skip accounting and strands at most one reader goroutine per file (a read stuck in the kernel cannot be interrupted; the buffered result channel guarantees the abandoned sender never blocks). One pass may take at most 50 such skips (`fileReadTimeoutSkipBudget`); a spent budget refuses BEFORE the next read is attempted — `ErrReadSkipBudgetExhausted` travels as a fatal unit, aborts the pass, and the worker-pool cancel drops already-fed paths without reads, so abandoned reader goroutines cannot accumulate.
- **Lexical lock gate** (`core/vectorindex/lexical/lockgate.go`): a bleve open otherwise blocks on bbolt's own file lock with no timeout, so every lexical open first locks a sentinel file `.lockgate` INSIDE the index directory (flock on Unix, `LockFileEx` on Windows, non-blocking probes every 20 ms; exclusive for read-write opens, shared for read-only readers) and holds it until `Close`. A gate held longer than `DefaultGateWait` (5 s) by a stuck or foreign holder refuses the open with `ErrLockBusy` — a bounded replica of the bbolt lock, deliberately not a wrapper of `context.DeadlineExceeded`. `ErrLockBusy` is classified `Repairable`: the ADR-120 attach rung quarantines the lexical leg and rebuilds it on a fresh inode while the holder keeps the orphaned old one — the sentinel dies with its directory, so the rebuilt index locks freely.
- **Embedder supervisor** (`backend/vector_embedder_supervisor.go`): every batch embed call routed through the supervisor is bounded by `embedCallDeadline` (90 s) — a detached goroutine + timer select, deliberately NOT a ctx deadline (a wedged ONNX inference ignores ctx and holds the instance's inference mutex forever). An expiry returns a TRANSIENT error; the authoritative sp4rk worker-heartbeat verdict `Embedder.Wedged` then decides whether the ONNX thread is genuinely wedged — no "K timeouts" heuristic, and a nil probe degrades the whole mechanism to plain timeout semantics. A confirmed wedge restarts the embedder EXACTLY ONCE per wedge on a fresh instance (new instance = new inference mutex, so new calls never queue behind the wedged one; the supervisor's lock is never held across the embed wait or the build), and after `embedCPUFallbackAfterRestarts` (2) consecutive failed restarts the next restart uses the CPU provider — the counters reset on the next success. The swap hook refreshes the ADR-045 requested/effective facts and re-derives the per-instance probe verdicts (`CUDAVerified`/`OVDevice` are dropped with the retired instance and re-probed on the fresh one when it runs a hardware provider), so a mid-session CPU fallback stays observable and never advertises a stale `cuda_verified=true`, and queries plus the shutdown-drain diagnosis resolve the LIVE instance. Supervisor close closes a healthy live instance, but never lets teardown hang on a stuck one: a wedged live instance (the authoritative verdict) is skipped — its `Close` would park forever behind the wedged inference thread — and the remaining call races the embed deadline, so a wedge younger than the verdict bound cannot freeze `ShutdownAll` either; wedged and timed-out instances alike die with the process.
- **On-demand diagnostics dump** (`DumpVectorIndexDiagnostics`, `backend/frontend_api_vector.go`): the user-visible "Collect diagnostics" action writes `vector-index-<UTC-nanosecond-stamp>.txt` (0600) under `<agentDir>/diagnostics/` (`config.DiagnosticsDir`, directory created lazily 0755) — a human header (the stall verdict in words, the truncated flag), the full status snapshot as JSON, and the capped all-goroutine dump (`vectorindex.GoroutineDump`, the same evidence the stall Warn carries). Routing mirrors `ReindexVectorIndex`: No Project and focus-routing failures reject with the carried cause and write nothing. The RPC is the only writer — nothing here is automatic. The status-bar overlay that hosts the action is specified in [frontend/loading-states.md](frontend/loading-states.md).

### Embedding Execution Provider (GPU)

The embedding inference backend is selectable per configuration: `auto` (default), CPU, CUDA on an NVIDIA GPU, or OpenVINO on Intel hardware. Full rationale — including the per-thread VRAM blowup and the silent-CPU-slide failure mode — is recorded in [ADR-045](../decisions/045-gpu-embedding-provider.md) (CUDA), the Intel extension — the plugin EP route, wheel-harvested packaging, device-level verification — in [ADR-089](../decisions/089-openvino-embedding-flavor.md); the research backing ADR-045 is in `docs/development/cuda-embedding-research.md`. The ADR's original "no UI yet" consequence has since been addressed: the settings surface below consumes exactly the observability contract the ADR preserved (status payload fields, config keys) — the ADR text itself is immutable per the spec update protocol, the domain spec documents the current surface.

- Configuration: `vector_index.execution_provider` (`auto` | `cpu` | `cuda` | `openvino`, default `auto`) and `vector_index.device_id` (GPU index, default `0`). `auto` walks the hardware ladder — CUDA when the GPU build of ONNX Runtime is present (the CUDA provider shared libraries sit next to the binary), then the OpenVINO provider when its plugin sits next to it, falling back to CPU when neither hardware provider is usable; `cpu` forces the CPU provider; `cuda` requests the NVIDIA GPU and, on a CUDA failure, the startup layer retries the embedder on CPU (WARN + `runtime_error` toast `error_code: vector_cuda_fallback` + mismatch recorded in status; at the sp4rk layer an explicit `cuda` stays a hard error); `openvino` requests Intel hardware and carries the same loud-fallback contract (`error_code: vector_openvino_fallback`). The PoC-era environment knobs `C0WRK_ONNX_EP`/`C0WRK_ONNX_DEVICE` were removed when the knobs moved into config.
- GPU init path (`auto`): probe whether the CUDA provider is loadable in this build (a CPU-only ONNX Runtime library errors loudly on `AppendExecutionProviderCUDA` — clean early detection); on success create the CUDA session (validating `device_id` against visible devices); on failure the ladder moves to the OpenVINO rung (present only when the plugin library sits next to the binary) before falling to CPU, each skipped rung logged.
- **Fallback is never silent**: the user decision is that a CPU fallback after a hardware-provider attempt (CUDA or OpenVINO) is tracked and warned about loudly — a previous attempt showed the ORT CUDA library can silently slide to CPU and this is invisible from inside the code. The `auto` fallback is detected and WARN-logged at the sp4rk embedding level (where session creation happens); the explicit-`cuda`/`openvino` fallback lives in c0wrk's startup glue and additionally emits the unmissable toast. c0wrk's half of the contract is observability — the effective provider (the one actually running inference) is surfaced through the vector-index status payload (`execution_provider` + `requested_execution_provider` + `provider_fallback_reason`, plus `cuda_verified` when the effective provider is `cuda` and `ov_device` when it is `openvino`), so requested vs. effective is always observable for every provider value — before, during, and after a runtime degradation (bullet below).
- **Runtime degradation keeps the pair honest (sp4rk ADR-011)**: an `auto` embedder already serving inference from a hardware provider degrades to the CPU AT RUNTIME after consecutive inference failures (the threshold is a compile-time constant inside sp4rk, `auto` only, once per embedder, WARN + the `OnProviderDegrade` callback; explicit providers never degrade at runtime — their fallback stays the init-time arm above). The callback is wired in `backend/vector_launcher.go` (`onProviderDegrade`): it flips the recorded embedder facts in place (`ApplyVectorProviderDegrade` — effective provider becomes the slide target, the runtime cause replaces `provider_fallback_reason`, and the hardware-path verification verdicts are dropped, because a stale `cuda_verified: true` beside `execution_provider: "cpu"` would lie) and emits exactly one `runtime_error` toast (`error_code: vector_runtime_degrade` — "came up and died", kept distinct from the init-time codes so "never came up" stays distinguishable; the remedy is a restart or an indexing toggle, the only paths that re-create the embedder). No dedicated status re-emission exists: every status producer reads the mutated facts (`applyEmbedderInfo`), so the next natural payload — the failing pass's own report or a `GetVectorIndexStatus` poll — already carries the slide. Two windows are guarded: a superseded (stale-epoch) launch's callback mutates nothing — the newer owner keeps the facts — and a slide during the init-time warmup probes lands before any facts exist, so the handler skips and the init path itself records the slid provider (it re-reads `ExecutionProvider()` after the probes). With a live collection a failed pass deliberately keeps the status "ready" (search still answers from the existing index); the unavailable/suspended verdicts belong to the ADR-124 breaker trip and the repair ladder, not to the slide itself.
- **Startup GPU verification (effective provider `cuda`)**: after the embedder initializes, the startup layer runs one warmup inference (the CUDA context is created lazily — probing right after session creation sees a process the driver does not know yet) and then asks the driver via `nvidia-smi` whether this PID is a CUDA compute app. PID found → INFO "CUDA verified via nvidia-smi"; PID absent → WARN "possible silent CPU fallback" and `cuda_verified: false` in the status. Diagnostics only — the probe (bounded to 2s inside sp4rk) never blocks or fails startup; probe errors are "unverified", never "on CPU".
- **The OpenVINO flavor (effective provider `openvino`)** rides the plugin-EP route ([ADR-089](../decisions/089-openvino-embedding-flavor.md), device resolution amended by [ADR-090](../decisions/090-openvino-device-resolution.md)): the stock CPU ONNX Runtime stays byte-identical and sp4rk registers `libonnxruntime_providers_openvino_plugin.so` into it at run time (decoupled execution-provider API, once per process — a duplicate registration is an error); device selection goes through the V2 `OrtEpDevice` surface, and `device_id` is pinned to `0` — the only value the plugin surface accepts. `0` means "the rung resolves the device": the plugin uses only the first of the appended devices, so sp4rk tries the plugin's devices in enumeration order at session creation and keeps the first that can compile the model (an Intel NPU — enumerated first on Core Ultra hosts — rejects the encoder's dynamic shapes, the integrated GPU runs it), caching the winner process-wide for every later session. Only the settings UI enforces that pin: it normalizes a non-zero id to 0 on a switch to `openvino` and pins the picker control to the single `0` entry. Load validation and the settings RPC check `device_id >= 0` for every provider — a hand-edited config or raw RPC can persist `openvino` with a non-zero id; that pair passes validation and fails at embedder creation, into the loud CPU fallback below (the contract `config.example.yaml` documents). **Device verification is device-level, not per-PID**: `xpu-smi` on these iGPUs exposes no compute-process list, so the nvidia-smi PID rule has no Intel counterpart; after init the startup layer drives sustained inference — no separate warmup pass: the loop's first call materializes the lazily-created OpenVINO context — while sampling `xpu-smi stats --device 0 -j`, parsing the compute-engine-utilization leaves out of the JSON payload (≤ 12 bounded samples, and deliberately no sleep between samples: the spawn is the cadence; the only deadline is one whole-probe 30 s budget — there is no per-invocation timeout). A sample that fails before the budget expires aborts the whole probe into the unverified verdict; a wedged invocation burns the remaining budget to the same end — it is never a skipped sample. The highest readable utilization decides: ≥ 25% → `ov_device: "gpu"` (INFO); a concluded window whose samples all stayed below the threshold → `"cpu"` plus a WARN naming the CPU-device outcome — an unreadable payload is not a failure shape: a sample without a recognizable compute-utilization field reads as 0, so an xpu-smi whose schema the parser does not recognize idles through the whole window and concludes `"cpu"` (the badge can thus assert a CPU device over a probe that never read a usable sample); missing tool, a sample or probe error, an expired budget, or failed sustained inference → `""` unverified — those failure shapes are never reported as "cpu". Diagnostics only — the probe never blocks or fails startup. Measured payoff (reference Arrow Lake-P iGPU): 3.9×–8.2× over the native CPU provider; the first session-create pays a one-time 0.4–1.35 s OpenVINO kernel JIT.
- **Provider changes require an app restart** — except through the wedged-restart ladder: the embedder (with its ONNX session) is created once during the background vector init and `execution_provider`/`device_id` are read at creation time only, so a configuration change still takes effect at the next embedder creation. The ONE exception is the embedder supervisor's restart-on-wedge ([Pass Liveness](#pass-liveness)): a confirmed-wedged ONNX thread is re-created on a fresh instance, and after repeated failed restarts that instance comes up on the CPU provider — a mid-session effective-provider change the swap hook records, so requested vs. effective stays honest. No other path re-creates the embedder.
- **GPU usage verification is external**: `onnxruntime_go` exposes no provider introspection (no `GetAvailableProviders`), so tests asserting GPU execution must verify externally via `nvidia-smi --query-compute-apps=pid,used_gpu_memory` — the process's own PID must appear in the compute-apps list. "Calls succeeded" is not evidence of GPU execution.
- **All ORT touches under a GPU provider go through the single locked thread**: the CUDA execution provider keeps a per-OS-thread state (a cuBLAS handle with its own workspace, ~1 GiB VRAM each); Go's scheduler migrates goroutines across threads, so an unguarded call pattern exhausts VRAM within seconds of indexing (`CUBLAS failure 3`). sp4rk's `ortRunner` (`runtime.LockOSThread`, never unlocked) executes every ONNX Runtime touch — environment init, session-options build, session creation, fast-path and batch inference, teardown — on one pinned thread. With a CPU provider the runner is nil and calls run inline (the CPU path is unchanged).
- Packaging: GPU ONNX Runtime libraries are a separate opt-in — `make fetch-onnx-gpu` installs the **cuda13** flavor only; `make build` / `make fetch-onnx` keep installing the CPU library and never overwrite a GPU install. The GPU flavor is also published as a release archive (`c0wrk-desktop-linux-amd64-cuda13.tar.gz`, linux/amd64 only), and the in-app updater always selects the asset matching the running install's flavor — a cuda13 tree updates only from the cuda13 archive; switching flavors is a manual reinstall (see [ADR-046](../decisions/046-cuda-release-artifact.md)). The GPU flavor needs the system CUDA 13 runtime (`libcudart.so.13`, cuBLAS, cuRAND) — a cuda12-flavor library would fail to load on a CUDA 13 machine and vice versa, hence pinning one flavor. The version stamp records the flavor (e.g. `1.28.1-gpu-cuda13`) and each fetch target compares against its own expected stamp value, so `make build` cannot silently reinstall the CPU library over a GPU install (see ADR-045, stamp policy).
- Packaging (OpenVINO): the plugin stack is a **second opt-in** — `make fetch-onnx-openvino` (Linux x86_64 only, fails closed elsewhere) harvests it from the digest-pinned official PyPI wheel `onnxruntime_ep_openvino` (whole-wheel SHA256 + post-extraction plugin-library SHA256, both fail-closed; unzip CRC guards extraction) and lays the shared libraries flat into the app bundle — no system OpenVINO, no Python, no `LD_LIBRARY_PATH` (the wheel's `RUNPATH=$ORIGIN` resolves everything from its own directory). Unlike the CUDA flavor the install is **additive**: the stock CPU `libonnxruntime.so` is not replaced (the CPU base is ensured by delegating to `make fetch-onnx`, the CPU stamp stays untouched, `make build` keeps working over an OpenVINO install) and the bundle carries both stamps — `.onnxruntime-version` = `1.28.1` plus `.onnxruntime-openvino-version` = `1.28.1-openvino-ep1.8.0`. The flavor is mutually exclusive with CUDA in both directions (each fetch target refuses to run over the other's marker/stamp — the plugin stack requires the CPU base, the GPU library would replace it) and ships as a third linux/amd64 release archive (`c0wrk-desktop-linux-amd64-openvino.tar.gz`) under the same-flavor update rule (see [ADR-089](../decisions/089-openvino-embedding-flavor.md), [ADR-046](../decisions/046-cuda-release-artifact.md)).
- **Settings UI** — the embedder half of the "Indexing" section in the Settings modal's **Search** tab (the tab's first block, above Web Search Provider; composed by `frontend/src/components/settings/IndexingSettings.tsx`, which embeds `VectorIndexSettings.tsx` and hides it wholesale while the indexing master switch is off), `frontend/src/components/settings/VectorIndexSettings.tsx`: an execution-provider Combobox (`auto` / `cpu` / `cuda` / `openvino` with a per-option description line) and the GPU-device control. **The controls are Linux-host-only**: `showControls = isLinuxHost()` (`frontend/src/lib/platform.ts`) gates the provider Combobox block, the device picker, the restart hint, and the save-error line. Rationale: the CUDA flavor these controls configure is linux/amd64 only ([ADR-046](../decisions/046-cuda-release-artifact.md)); Windows/macOS hardware acceleration is a separate future implementation, so off Linux there is nothing to select and the controls would be misleading rather than merely inert. Off Linux the section also skips both mount-time RPCs — `GetConfig` (the loading state resolves immediately) and `ListVectorIndexGPUs` (no probe at all) — and renders a muted note explaining that provider selection is Linux-only and that win/mac acceleration is a separate future implementation. The read-only diagnostics block (`VectorIndexDiagnostics.tsx`) is **cross-platform and always rendered** — it describes whatever embedder is actually running, which exists on every platform. Saves are debounced (500 ms) and flushed on unmount — Radix Tabs unmount inactive tab content, so a pending edit must survive a tab switch mid-debounce. Device ids are validated client-side (whole number ≥ 0); an invalid id is buffered and flagged, never persisted — the backend rejects the whole update, so one bad field must not lose the other. The diagnostics block renders requested → effective provider **classified by outcome**, not by raw inequality — an "auto" request always diverges (it is resolved to a winner at embedder creation), so `requested !== effective` alone cannot mean "fallback": explicit `cuda`/`openvino` landing on `cpu` is the one true fallback (warning color + the fallback-reason callout; the backend fills `provider_fallback_reason` on exactly this path); `auto → cuda` and `auto → openvino` are Auto's hardware rungs (success color, no callout); `auto → cpu` is Auto's expected degradation (info color + an info note naming it as expected behavior and pointing to the startup WARN in the app logs for the concrete cause — at init time that cause is not part of the status payload; after a runtime degradation it is, in `provider_fallback_reason`); any honored request renders in success color. Plus the `cuda_verified` badge (only when effective provider is `cuda` and the startup probe ran), the `ov_device` badge (only when effective provider is `openvino`: `"gpu"` renders success "Intel GPU verified", `"cpu"` renders a warning that inference landed on the plugin's CPU device, absent renders no badge — unverified is never rendered as a CPU outcome) and the running device id; it is fed reactively from `vectorIndexStore.status` (`vector_index:status` events) — the section issues no status RPC of its own. Absent `execution_provider` degrades the block to a muted "embedder is not running" note.
- **GPU device picker** (`VectorIndexDevicePicker.tsx`): a named dropdown (`"{index} — {name}"`) when the driver reports GPUs; a validating numeric input (≥ 0) when it does not — there is no nvidia-smi requirement for the control to exist. A muted "Detecting GPUs..." placeholder covers the in-flight probe (bounded 2 s) so the control does not flash between shapes; a probe *failure* (driver present but broken → RPC reject path) is surfaced as a distinct warning line next to the numeric fallback. Disabled when the provider is `cpu` (the device applies only when a hardware provider is selected). Under `openvino` the control is pinned to the single `0` entry with an explanatory note — the plugin surface accepts device 0 only — and switching to `openvino` normalizes a non-zero `device_id` to 0 before the debounced save, so the RPC never receives a pair the embedder would refuse; option values are provider-scoped (`cuda:0` / `openvino:0`) and decoded to the bare ordinal on selection, so same-index entries from the two probe sources stay distinct React keys.
- **Settings RPCs**: `UpdateVectorIndexSettings` (`backend/frontend_api_config.go`) validates (`execution_provider` ∈ {`auto`, `cpu`, `cuda`, `openvino`}; `device_id` ≥ 0 — error text mirrors the load-time `validate()` wording so the settings UI shows the same guidance as a bad YAML), mutates, and persists under `configMu`; it deliberately has **no hot application** — it never touches the vector manager or the running embedder, so a rejected request leaves both the in-memory config and the YAML untouched and a restart cannot brick on a bad value. `ListVectorIndexGPUs` (`backend/frontend_api_vector.go`) is the lazy, on-demand counterpart to the startup GPU probe: it delegates to `embedding.ListGPUDevices`, which merges two external probe sources under the same bounded probe budget (2 s each) — NVIDIA GPUs via nvidia-smi (provider `cuda`) and the Intel GPU via `vulkaninfo --summary` (provider `openvino`, always index 0) — and returns plain `GPUDeviceResponse` DTOs. nvidia-smi absent from PATH → empty non-nil slice contribution, nil error (absence of the NVIDIA userspace means "no NVIDIA GPUs to offer", not a failure); probe failure (driver down, non-zero exit, timeout) → nil slice + wrapped error, so the UI distinguishes "no hardware" from "hardware present, probe failed". The list reflects what the driver reports right now, independent of the running embedder (whose creation-time facts travel in `VectorIndexStatus`).
- **Restart semantics**: the embedder is created once per process, so a changed provider/device takes effect only after an app restart — the UI makes that contract visible instead of letting edits look ignored. A restart hint is shown whenever the saved config diverges from the running embedder's creation-time facts: `status.requested_execution_provider` ≠ saved provider **or** `status.device_id` (absent ⇒ 0) ≠ saved device; it is hidden when they match or no embedder has ever reported (the provider fields carry the populated/not-populated signal; `device_id` participates in the check for non-zero values only, and a UI treating 0 as the default reads absence as 0). The comparison is against the *requested* provider, not the effective one — a fallback (requested `cuda`, effective `cpu`) is surfaced by the diagnostics block, not by the restart hint.

### Workspace storage liveness advisory

Opening a project whose directory does not behave like local storage — a network volume, a cloud placeholder tree (OneDrive Files On-Demand), or a c0wrk data directory behind a sync engine — is a liveness hazard for everything this domain runs on that path: the file watcher, the vector index's store and sidecars, and any tool that reads workspace files can stall or lag for reasons invisible to the app. The storage-liveness advisory surfaces that fact once, as a note, without changing anything.

- `backend/storageprobe/` probes a path's storage class behind the `statfsProbe` seam: **darwin** — `statfs` flags lacking `MNT_LOCAL` mean a network (or otherwise non-local) mount, and a config-directory check additionally resolves the path and asks whether it lands under a cloud-sync provider root (`~/Library/Mobile Documents`, `~/Library/CloudStorage`) using `pathutil.IsWithinPathFold`; **windows** — `GetDriveTypeW` `DRIVE_REMOTE` on the volume root plus `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` on the path itself (placeholder files); **other platforms** — the neutral fallback reports nothing (no reliable mount-class API without shelling out, which can hang on exactly the wedged mounts the probe looks for).
- `ProbeWorkspace(path)` runs the volume-class read for a project workspace; `ProbeConfigDir(path)` adds the sync-root containment for the c0wrk data directory (`agentDir`), whose databases, caches and sidecars stall behind a sync engine in ways no single project's probe would surface.
- The wiring (`backend/frontend_api_storageprobe.go`) fires `probeStorageAdvisories` fire-and-forget from `SwitchProject`'s REAL-switch path only (the already-active re-selection path skips it), alongside the auto-fetch and stale-branch sweeps. No Project and empty workspace paths never probe.
- A finding becomes ONE `slog.Warn` (kinds + cause details as attributes) plus ONE `runtime_error` toast note (`error_code: workspace_storage_advisory`) with an operator-facing sentence per finding — then the project is marked notified for the rest of the session (`FrontendAPI.storageAdvisoryNotified`): at most one note per project per app run. The config-directory note is once per session (the directory is global). The guard is taken only when a finding actually fires, so a clean or failed probe never marks the project — a later switch re-probes instead of inheriting a stale verdict.
- The probe is advisory BY CONSTRUCTION: a failed statfs/drive-type read produces no findings and no error, an empty result produces nothing at all, and nothing in the switch path, the watcher, the vector index or any tool behavior keys off the verdict (detection only — no policy).

## Invariants

- Workspace-scoped viewer writes, directory listing, embedded-image reads and diff validation admit the active checkout or a validated managed-tree descendant belonging to that repository; containment remains symlink-aware. A managed tree's diff runs from its own Git root. Unmarked foreign roots remain outside workspace scope.
- Project app-data cleanup refuses while its default worktree container has entries other than the repository marker, before runtime/session/vector teardown; explicit worktree removal retains the dirty/lock confirmation protocol.
- File tree is always relative to active project's workspace path
- The watcher root follows the ACTIVE SESSION, so it emits events only for the session's workspace: a bound managed worktree when the active session has one, the project checkout otherwise (No Project keeps the deferred-creation rule); the session-switch `WatchDirectory` call re-scopes the watcher after containment-validating its renderer-supplied path
- The storage-liveness advisory is detection-only: its verdict (network volume, cloud placeholder files, synced config dir) never alters any behavior — no probe failure becomes an error, a clean probe never emits anything, and each project (and the config directory) is noted at most once per session via the `workspace_storage_advisory` `runtime_error` code (see [Workspace storage liveness advisory](#workspace-storage-liveness-advisory))
- Git processes spawned in this domain always carry the sysproc baseline overrides; repo-scoped invocations re-scan the discovered repository's config fresh per call (walking up the `.git` chain like git's own discovery) and fail closed on unscannable configs — repository-defined hooks, fsmonitor daemons, filters, merge drivers, and textconv never execute (see [ADR-033](../decisions/033-git-subprocess-hardening.md))
- A repository whose `.git/config` cannot be scanned safely is reported as not-a-repo by the boolean predicates, so callers take their non-repo paths — which the same scan failure then errors out of (fail-closed, review [53]) rather than producing degraded git output: git never runs un-neutralized
- Worktree primitives (`core/workspace/worktrees.go`) serialize every mutating operation per repository and validate inside the serialized section: concurrent same-branch (or same-path) creates cannot both succeed — exactly one wins and every loser gets an explicit typed error
- `git worktree list --porcelain` output that violates the documented format fails the whole listing with `ErrWorktreeMalformed` — a partially parsed list would silently hide trees from the branch-occupancy and ownership checks (fail-closed, never truncated)
- Worktree creation never overwrites foreign directories: an existing target, a symlinked ancestor, the managed container itself, `.git` interiors and other linked worktrees' interiors are refused before git runs, and `--force` is never passed to `worktree add`
- The legacy checkout-local container is hidden from the main checkout by appending `/.worktrees/` to the common dir's `info/exclude` (idempotently and atomically); new managed containers live outside the checkout. No `.gitignore` is modified.
- No worktree primitive deletes a branch (`worktree remove`/`prune` only); branch lifetime belongs to git and the user, so releasing a session's tree — including on session deletion — can never destroy unmerged work
- Nested `.worktrees` containers are excluded from vector-index walks: the hidden-dot segment guard covers the container at any depth for repo-rooted walks, while a managed session's own index (rooted at the tree itself) indexes its files normally — only segments relative to the walk root are inspected
- Nested-repo directories under the walk root (a checked-out submodule — `.git` is a regular gitdir-pointer file) are pruned from every indexing walk unless `vector_index.index_submodules` opts in: the walk root itself carries the same pointer shape (a linked worktree) and stays exempt, and because the policy reaches the validation walk too, a toggle flip evicts the submodule's already-indexed documents on the next incremental pass
- Vector index collection is partitioned by git branch and rebuilt when the branch changes
- Stored artifacts of branches absent from the local clone are pruned in the background on the next real project switch — both indexes (chromem root + lexical directory) plus the sidecar/marker pair, across the checkout's and every managed-worktree's storage root — while every sanitized identity a surviving branch maps to, the synthetic `default`, and `branches/_orphan` are never removed; the sweep never blocks, fails, or signals the switch (Debug logs only); a Git-panel branch deletion purges that branch's artifacts immediately by the same rules (deliberately not single-flight-skipped), and removing a managed worktree drops its whole storage root synchronously with the RPC
- Chromem is the source of truth; lexical is a best-effort mirror reconciled via `RebuildLexical`
- Batch-path documents are stored content-less — ID + embedding + the four chunk-position metadata fields only; content is reconstructed best-effort from source files, and a missing/unreadable source yields a placeholder result (never an error) that `must_match` excludes (see [ADR-049](../decisions/049-vector-index-memory-reduction.md))
- A file-hash sidecar entry's chunk set is authoritative for its document IDs (deterministic `DocumentID(path, i)`): when the set is known, enumeration paths use ID arithmetic and never materialize the full collection
- The content-less migration marker is written only after every document of the collection is stripped; a cancelled migration writes no marker and replays on the next open — every document is always individually complete (fully legacy or fully stripped)
- The store-migration state file (`store_migration.json`) writes its `done` marker only after every recognized legacy unit settled (promoted, superseded by a published corpus, or skipped with a recorded reason); an interrupted sweep replays from its recorded units, unknown directories are excluded from the recognized volume and left in place, and no unit's source is destroyed before its replacement is validated (renames move the only copy atomically; an unpublished target collision consumes nothing)
- The effective parked-RAM bound is `min(park_capacity, park_budget_mb)`; every eviction flushes the sidecar before dropping state and frees OS memory outside the lock
- The GC soft-limit resolution order is fixed — off → explicit config → `GOMEMLIMIT` env → AUTO — and every branch is logged at startup
- Per-side filters (FilePattern, MustMatch) are applied BEFORE RRF fusion so vector and lexical rank spaces remain comparable
- Pre-fusion score thresholds discard noise-tail hits (low cosine similarity or low BM25) before RRF fusion so they cannot earn a double RRF contribution; thresholds apply only in the hybrid path, not vector-only or lexical-only modes
- A single `ready atomic.Bool` on `Service`; hybrid auto-falls-back to vector-only when `lexical.Count() == 0`
- The indexer rejects binary files via a bounded 512-byte header pre-read (null-byte presence, `binaryHeaderSize`) before loading the file into memory; the frontend file viewer detects binary content via null bytes in the first 8KB
- Every index path applies `max_file_size` before a full file read, and every chunked file stays at or below `max_chunks_per_file`; oversized/pathological files are skipped without aborting the pass
- A deterministic content filter (`vector_index.content_filter`, `core/vectorindex/content_filter.go`) rejects generated (canonical "DO NOT EDIT" header marker within the first 2 KiB), minified (≥16 KiB file with a >10 KiB line and ≤8% whitespace), and pathological (≥32 KiB file with a single >24 KiB unbroken token) files BEFORE chunking — no chunks, no embeddings, no inference. Every heuristic and threshold is individually toggleable; `.aiignore` remains the exact path-level channel. The policy participates in the chunker fingerprint: a policy change invalidates affected sidecar entries, newly excluded files have their documents removed on the next incremental pass, and unchanged re-chunks are served by the embedding cache rather than ONNX. The filter layers ON TOP of the ignore rules and hard limits — it never relaxes them
- Every non-final ONNX inference batch in an indexing pass is filled to the configured capacity; the final tail is bounded by that capacity. Chromem commits contain at most 200 already-embedded documents, cancellation is observed between bounded operations, and all manager-launched indexing goroutines are drained before teardown
- Optional index telemetry uses a fixed stage enum and numeric aggregates only; it never records source text, absolute paths, project IDs, branch names, or caller-defined labels
- Document embeddings are cached under each project's `vector_index/embedding_cache/`, outside branch collections. Keys include cache-format version, SHA256 fingerprints of model/tokenizer bytes, max sequence length, vector dimension, normalization algorithm ID, and SHA256 of normalized chunk content; paths and branch names are excluded so rename/move/branch changes reuse identical chunks
- Equal normalized chunks in one commit window are embedded once and fanned out to every document. A cache hit never calls the batch embedder/ONNX path
- Cache entries are atomically installed (temporary file + rename), carry dimension and SHA256 checksum, and reject truncated, non-finite, wrong-dimension, or checksum-invalid vectors. Corruption is a fail-open miss: the entry is removed best-effort and rebuilt without aborting indexing
- Cache pruning runs after a resolved embedding batch but walks the cache directory only when a tracked-bytes counter crosses 95% of `embedding_cache_max_bytes` or every 4096 puts (an accounting-drift backstop; project switch always walks once to seed the counter). A walked prune evicts oldest entries down to a 90% low-water mark, so a cache running near the cap does not evict on every batch. Cache I/O/pruning failures never disable indexing
- Embedding fallback is never silent: when `execution_provider` is `auto` and CUDA init fails, the embedding layer (sp4rk) logs a WARN and continues down the ladder; when `execution_provider` is `cuda` or `openvino` and that provider's init fails, the vector launcher (`backend/vector_launcher.go`) retries the embedder on the CPU provider so vector search stays available — loudly: WARN log + `runtime_error` toast (`error_code: vector_cuda_fallback` / `vector_openvino_fallback`) + the requested-vs-effective mismatch recorded in every vector-index status. A hardware provider that DIES MID-FLIGHT is the third, runtime outcome (sp4rk ADR-011): the `auto` embedder degrades to the CPU once, after consecutive inference failures, and the launcher's `OnProviderDegrade` callback keeps the pair honest — the recorded facts slide (`ApplyVectorProviderDegrade`), one `vector_runtime_degrade` toast fires, and the hardware-path verification verdicts are dropped. In every case the effective provider is always reflected in the vector-index status (requested and effective, plus the nvidia-smi `cuda_verified` verdict when the effective provider is `cuda` and the xpu-smi `ov_device` verdict when it is `openvino`); the fallback is never a silent CPU slide
- The effective embedding execution provider is always observable (status payload/getter); requested (`auto`/`cpu`/`cuda`/`openvino`) and effective provider are both surfaced, because ORT's CUDA library can silently slide to CPU and the OpenVINO plugin picks its concrete device (GPU or CPU) in a way in-process code cannot observe — both states are invisible without the status payload and the external probes
- An OpenVINO device probe that fails always leaves `ov_device` empty: a missing xpu-smi tool, a sample or probe error, an expired 30 s budget, or failed sustained inference produce an unverified verdict, and an unverified verdict is never reported as `"cpu"` — only a concluded sampling window that never crossed the utilization threshold earns the `"cpu"` outcome (an unreadable payload is not a failure shape: it reads as 0 and can conclude `"cpu"`)
- Every OpenVINO provider session runs on device 0: the plugin surface accepts only device 0, and `0` delegates the actual device choice to sp4rk's empirical resolution (the plugin uses just the first appended `OrtEpDevice`, so the rung walks the plugin's devices at session creation and keeps the first that can compile the model — skipping an Intel NPU, which rejects the encoder's dynamic shapes; the winner is cached process-wide). Only the settings UI enforces the pin — it normalizes a non-zero `device_id` to 0 on a switch to `openvino` and pins the picker control; config validation and the settings RPC check `device_id >= 0` for every provider, so a hand-edited config or raw RPC can persist a non-zero id under `openvino` — the pair passes validation and fails at embedder creation, into the loud CPU fallback (`vector_openvino_fallback`)
- `UpdateVectorIndexSettings` validates before it mutates: a rejected request leaves both the in-memory config and the persisted YAML untouched, and the RPC never touches the vector manager — provider/device changes take effect only at the next embedder creation (app restart), which the settings UI discloses via a restart hint whenever the saved config diverges from the running embedder's creation-time facts
- **The indexing master gate is total**: while `vector_index.enabled` resolves false, the `semantic_search` tool is unregistered (live sessions included — every per-session registry clone shares the embedded sp4rk registry), no RAG hints inject, no index pass runs (initial, incremental, or manual reindex), the ONNX embedder is never loaded, and every routing path fails fast with `errVectorDisabled` — a disabled subsystem is ABSENT, never broken
- **The indexing policy is live-applied by `UpdateIndexingSettings`** (`backend/frontend_api_config.go`; the master switch's rationale — absent-not-broken, the teardown ordering, the restartable launcher — is [ADR-103](../decisions/103-vector-index-master-switch.md)): validate (the same `config.ValidateVectorIndexExcludePatterns` rule set the loader enforces) → persist → apply. `enabled=false` first runs the desktop hook (an epochal invalidation of any in-flight background ONNX init, so its late factory wiring cannot resurrect the registry), then strips the `semantic_search` tool and the RAG closures from the builder (`SetVectorSearchEnabled` — the closures are stashed, and because every per-session registry clone shares the embedded sp4rk registry, live sessions lose the tool too), parks the per-root registry (`VectorRoots.Disable`: managers shut down, embedder released, factory dropped; every routing path — the tool, RAG hints, user-facing search — fails fast with `errVectorDisabled`, and `FactoryReady` reports false so project switches defer their vector setup for the re-enable drain), and emits a `state: "disabled"` snapshot. `enabled=true` re-registers the tool from the stash and relaunches the desktop background ONNX init (a fresh embedder + factory + ready channel under a new epoch; its success path drains the deferred project setup). A boot with indexing off registers the closures then flips the builder off (populating the stash for a later enable) and skips the ONNX load entirely. A policy-only save while enabled (exclude patterns, submodules, ignore-file respect) releases the live managers and rebuilds the focus root — the desktop manager factory snapshots the LIVE config under `configMu` on every build, so the rebuilt manager carries the new policy and its next incremental pass evicts newly excluded files; a save resolving to the same policy releases nothing
- All ONNX Runtime touches under a GPU provider execute on the single locked thread (sp4rk `ortRunner`, `runtime.LockOSThread`): environment init, session-options build, session creation, fast-path and batch inference, and teardown — a per-OS-thread cuBLAS context (~1 GiB VRAM each) makes any unguarded ORT touch from another thread exhaust VRAM
- Every externally fetched build-time artifact (ONNX Runtime library, the OpenVINO EP wheel and its extracted plugin library, embedding model, tokenizer) is SHA256-verified fail-closed against Makefile-pinned digests before installation, and the verification covers installed, cached, and downloaded copies alike; the OpenVINO flavor and the CUDA flavor are mutually exclusive in both directions — each fetch target refuses to lay its stack over the other's install
- Write-path and structural RPCs (`WriteFile`, `ListDirectory`) reject paths outside the workspace (directory-traversal containment); read-path RPCs (`ReadFile`, `GetFileIcon`, `GetFileDiff`) accept any absolute path so the viewer can display any file the agent cites — this is a display affordance that does not relax the agent's `read_file` tool containment. `ReadFileAsDataURL` is the exception among read RPCs: it retains workspace containment because image embedding runs during markdown auto-render (no explicit user action) and must not let a document read arbitrary files into the webview DOM
- Every git invocation flows through `exec.CommandContext`; git errors propagate to the caller (no silent fallback)
- Missing `git` binary blocks the CODE-mode project switch: detected lazily via `exec.LookPath` in `SwitchProject`, it emits a dismissable `runtime_error` toast (`error_code: git_not_found`) and rejects the switch; CHAT / No-Project mode never invokes git and never requires it
- ONNX embedder loading runs asynchronously after EventBackendReady; it never blocks the critical startup path
- Vector search RPCs block via `Service.WaitReady` until the index is ready: a search issued while indexing is in progress waits, surfacing a "waiting for index readiness" error only if the request context is cancelled first. When no target root resolves — no Git-panel focus root for the user-facing RPCs, no workspace root in the executor context for the agent-side closures, or a root that is neither a registered project checkout nor one of its managed trees — the registry answers with the `errVectorNoTarget` "vector search not available" error
- **A publication is a promise the open can keep.** `PublishCorpus` writes only when every leg an open reads is present — a live corpus lexical leg, and chunk records that are verified or re-embedded in the same pass — and any open that finds a leg missing treats the corpus as unpublished, resets exactly that snapshot's legs and rebuilds it from source, cache-spared
- **An empty index is never published.** A clean empty walk reports `ErrCorpusNoIndexableFiles` with an actionable reason; an empty result caused by skipped entries reports `ErrCorpusWalkIncomplete` naming them; neither writes the §3 table or the manifest, and both map to no-store repair because rebuilding cannot change what the tree contains
- **Attach self-heals exactly one step.** A proven store defect quarantines exactly the store its failing stage names and retries once; a transient fault quarantines nothing and leaves the publication byte-identical; an unrepairable defect ends after that one retry and binds no other snapshot's or era's data
- **Quarantine is selective.** The corpus and overlay scopes are disjoint, and neither removes content-addressed `chunks/` records or `embedding_cache/` entries — shared derived work is never charged to one store's damage
- **Walk errors below the root are skipped gaps.** A deleted or unreadable subtree is recorded and the walk continues; only an unreadable root fails the pass, and each pass logs at most one aggregated WARN naming the skipped count, the first path and the cause
- **Hygiene never reaps under a live build.** The orphan-chunk sweep and count-zero eviction are suppressed while any build lease is live (and re-sampled before eviction); the ledger reports the skip, and budget eviction leaves unreaped records on disk and accounted
- **Every non-ready vector status explains itself.** `unavailable` always carries a non-empty `last_error` and an `error_kind`; `loading` and `restarting` are non-failure windows that stay `loading`; `disabled` carries no cause because the switch is the explanation; a healthy status omits the pair and clears any stale reason
- **Pass liveness is bounded and observable, and it never disturbs a healthy pass.** File reads run under the 30-second per-stage watchdog with a per-pass 50-skip budget whose exhaustion aborts the pass explicitly (`ErrReadSkipBudgetExhausted`) instead of stacking wedged reader goroutines; a pass silent for the full 5-minute threshold logs its evidence once and stays visible as the `stalled` sub-status until progress resolves it; a wedged embedder is confirmed by the heartbeat verdict and restarted once per wedge (CPU provider after repeated restart failures, requested vs. effective kept honest); a busy lexical gate refuses within `DefaultGateWait` and rides the ADR-120 repair rung. The watchdogs themselves never interrupt work — only the read budget's refusal and the lock gate's repair-rung classification change a pass's outcome
- **Registry identity is physical.** Registry keys are symlink-resolved, so every spelling of one existing root shares one manager; duplicate project records are resolved by a total order (checkout over managed tree, exact spelling over resolved-only, freshest activity, project ID) with a WARN naming the candidates; a foreign root stays `no_target`
- **A terminal `unavailable` has an explicit repair path.** Reindex on a view-model index with no live collection re-attaches the snapshot view and rebuilds an unopenable corpus once, cache-spared; legacy mode no-ops; no branch switch or project reopen is required or substituted
- No Project: git operations and vector indexing are skipped (deactivated at the FrontendAPI layer). File watching is scoped to the active session's workspace directory (`__no_project__/<sessionID>/workspace/`); when no session exists yet, the watcher is torn down and creation deferred until the first session activates (no project-base-directory fallback).
- No Project: git status and diff always return empty (no git process spawned)
- No Project: vector search never returns results (indexer is never started, semantic_search tool is disabled anyway)

## Extension Points

- **Custom ignore patterns**: add entries to the project's `.gitignore` (or `.aiignore` for AI-specific ignores) to exclude files/directories from tree and index. `.aiignore` is the recommended channel for files git tracks but the agent/indexer should not waste context on. Recommended `.aiignore` recipe:
  ```
  go.sum
  package-lock.json
  *.lock
  ```
  Hidden directories (entries starting with `.`) are always excluded regardless of ignore files. See [ADR-016](../decisions/016-aiignore.md) for the full rationale and the ripgrep nested-`.aiignore` limitation.
- **Alternative embedding model**: replace ONNX Runtime with a different model by implementing the embedding interface
- **Vector store backend**: replace chromem-go with an alternative vector database by implementing the service interface
- **Git monitor hooks**: add custom callbacks on branch change detected by `GitMonitor`
- **Additional file attributes**: extend `FileNode` with custom fields and populate them in `ListDirectory()`
