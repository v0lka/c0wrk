# Web Access (Browser Sidecar)

## Purpose

Serve the existing c0wrk frontend to a local browser from the running desktop app: an HTTP(S) + WebSocket sidecar re-exposes the backend RPC surface (by reflection over `*backend.FrontendAPI`) and the backend event stream (via a web-agnostic tap in `(*App).emit`), so the same UI bundle works in the Wails webview and in a browser tab. The transport is plain HTTP by default; the `web_access.tls` subsection turns on sidecar-terminated TLS ([ADR-102](../decisions/102-web-access-tls.md)). The sidecar is mounted sideways from `desktop` and is designed to be removable without touching `backend`/`core` ([ADR-101](../decisions/101-browser-web-access.md)). The browser holds full control of the app by design — the default loopback bind plus the generated persistent credential is the default mitigation; a non-loopback bind is the operator's warned decision, never a gate (same ADR, decision 12). The sidecar additionally mounts only while the master experimental gate is open: availability is the conjunction `experimental.enabled && web_access.enabled`, and a mid-session flip of EITHER switch mounts or stops the sidecar live, without an app restart ([ADR-101](../decisions/101-browser-web-access.md)).

## Key Files

Dependency contract: **stdlib + `backend/config` only** — enforced by `nodeps_test.go` (`TestPackageImportHygiene`), which bans `desktop` and Wails imports in every file of the package, tests included.

Modeled on `initChatGPTAuth`: fail-soft and loud — a failed mount logs at Error and the desktop app continues; the persisted switch stays on and the next launch retries.
- `desktop/startup.go` - the call sites: `initWebAccess` right after `emitBackendReady`; `stopWebAccess` in `Shutdown` after `stopEmbeddedLLM` (a quit never hangs on a stateless listener).
- `desktop/webaccess_inbound.go` - the inbound bridge: `webWSInboundDispatcher(log)` (mounted as `Options.WSInbound` from `startWebAccessLocked`) decodes the `{name,args}` frames an authenticated tab sends and resolves the whitelisted frontend→backend HITL events through exactly the `desktop/event_handlers.go` methods the Wails listeners use; every other frame drops at Debug.
- `desktop/app.go` - the seams: `eventTap` (atomic pointer consumed by `(*App).emit`), the `webAccess`/`webAccessMu`/`webAccessStatic` fields, `startWebAccessLocked`/`stopWebAccessLocked`, `applyExperimentalWebAccess` (the experimental-gate live-follow hook — gate opened over an enabled section → mount, gate closed → bounded stop, every other combination a no-op; invoked by the backend strictly after a successful `experimental.enabled` persist, [ADR-101](../decisions/101-browser-web-access.md)), `logWebAccessReady` (logs the URL with the token masked), and the control RPCs `GetWebAccessInfo`/`SetWebAccessEnabled`/`SetWebAccessConnection`/`SetWebAccessToken`/`RegenerateWebAccessToken`/`SetWebAccessTLS`/`GenerateWebAccessCertificate` plus the `SetWebAccessStaticFS` startup handover — all methods on `*App`, never on `FrontendAPI`. `SetWebAccessTLS` is the TLS pin writer ([ADR-102](../decisions/102-web-access-tls.md), decision 1): it trims both paths — never derived (decision 4 as amended: the UI authors both pair paths explicitly) — refuses an enabled subsection with empty paths through `config.ValidateWebAccessTLS`, and refuses to commit an unloadable pair: the pair is loaded BEFORE the no-op check or any persist and refused with the commit check's own two-bucket error split (a key that does not match its certificate is refused as a mismatch — "does not match" — every other load failure as unreadable — the interactive boundary of the ADR-102 usability rule; deliberately NOT the `cert_status` vocabulary: `classifyWebAccessCert` reserves `mismatch` for SAN non-coverage of the pinned bind and reports this same key-mismatch pair as `unreadable`, since its load precedes the coverage check), so a broken pair is met at the commit that introduces it and nothing is written; a request matching the current subsection is a no-op once the pair has loaded, and a since-deleted file fails that no-op too. Then it persists + hot-restarts + rolls back like every pin writer, and deliberately consults neither `web_access.enabled` nor the experimental gate. `SetWebAccessEnabled` preflights the TLS pair fail-closed before enabling ([ADR-102](../decisions/102-web-access-tls.md)): a flip onto a configured-but-unusable TLS is refused with the load failure — nothing is mutated or persisted, the sidecar stays down, and a persisted-on switch above a silently-down listener is never produced. `GenerateWebAccessCertificate` writes the fixed app-owned pair (`config.WebAccessCertPath`/`WebAccessKeyPath` — `~/.c0wrk/web-access.crt`/`.key`) for the CURRENTLY pinned bind, persists the pair's paths (never flipping `tls.enabled`, never touching operator-authored paths) BEFORE the config save, and hot-restarts even when the paths did not change — the key material on disk was replaced; it also works while the sidecar is stopped. `classifyWebAccessCert` computes the info payload's `cert_status`/`cert_detail` pair — deterministic check order unreadable → mismatch → expired → ok, empty when no cert path is configured (decision 5). `startWebAccessLocked` mints the credential when the section carries an empty token: generated once, persisted through the same immediate config save every settings change uses (a failed persist aborts the start), then the sidecar mounts. `SetWebAccessConnection` is the connection pin writer: it persists `web_access.bind`/`port` — never the token — with the toggle's rollback discipline (empty bind = the `127.0.0.1` default; the no-op check compares both) and hot-restarts a running sidecar onto the new connection, restoring the previous pin (and the running sidecar on it) when the new one cannot serve (`desktop/webaccess_connection_test.go`). `SetWebAccessToken` persists an operator-typed credential (trimmed, bounds-checked by `config.ValidateWebAccessToken`, no-op on the unchanged value) and `RegenerateWebAccessToken` rotates it — both through the same persist + hot-restart + rollback discipline, serialized by `webAccessMu`. The info's browser URL goes through `webAccessBrowserURL` — a wildcard bind renders as `localhost` (no browser opens `0.0.0.0`), a specific IP passes through as-is.

- `backend/frontend_api_attachment.go` - `AttachFileContent` — the single additive backend edit: a byte-upload attachment method (`data []byte` travels base64 over both bridges), name sanitized to a bare base name, capped by the backend's raw-buffer limit (32 MiB). Survives sidecar removal.
- `frontend/src/api/runtime.ts` - the transport shim shared by both clients: synchronous Wails detection, `GET /api/transport` probe for the web transport (its `authenticated` field lands in the module's web-session state), the RPC proxy over `POST /api/rpc/<Method>`, the WebSocket event router (batch envelopes and single events fan out through the same registry as the Wails path), and the login-gating seam — `webAuthRequired()` (probe answer) plus `onWebAuthRequired()` (a live signal fired when any RPC answers 401, i.e. the app restarted under an already-open tab). `clipboardSetText` stays WRITE-ONLY on the web transport: `navigator.clipboard.writeText` first, degraded to the legacy hidden-textarea `document.execCommand('copy')` when the async Clipboard API is missing (non-secure origin, older browser) or refuses the write; both legs honor the boolean contract of the Wails `ClipboardSetText` call they replace — an honest verdict (`true` only on a confirmed write), every failure resolved to `false` with a warn log, never a throw, so callers own the failure UX off the return value alone. There is no read direction: `PasteFromClipboard` is denylisted (the host clipboard is never exposed to the browser — see [Invariants](#invariants)), browser-side pasting rides native `paste` events (the editor's paste extension inserts plain text itself; the async attachment handler reads only the event's own `DataTransfer`), and the shim adds no `navigator.clipboard.readText` fallback to compensate. Survives sidecar removal as the seam a future headless build rides.
  - `frontend/src/lib/armWhenRuntimeReady.ts` - the shared readiness gate every app-global DOM trigger (window focus, tab visibility) arms through: the desktop attaches synchronously (`isWailsReady()` — the bridge exists before any bundle code), a web tab attaches once the transport probe resolves `'web'`, and the transportless `'none'` environment (plain dev server, vitest, SSR) never arms — the RPCs there are guaranteed no-ops. Deliberately NOT `backend:ready`: that event is a desktop one-shot — `emitBackendReady` fires once during startup (`desktop/startup.go`, right before `initWebAccess` mounts the sidecar) and is never replayed — so a tab that loads later subscribes after the fact and would stay permanently disarmed; waiting on it would leave the web focus/visibility repair dead. Attaching on `'web'` is unconditionally safe: the login gate (`WebAccessGate`) keeps unauthenticated tabs behind the token form, so the app root — where these triggers mount — only ever mounts for an authenticated tab, and a mid-session 401 swaps the app for the gate, whose cleanup detaches. `useShallowResync` and `useGitFocusRefresh` (git auto-fetch's window-focus trigger) are its consumers; each disposer detaches once when armed, cancels a pending probe when not, and is safe to call twice.
- `frontend/src/api/webAccess.ts`, `frontend/src/components/settings/WebAccessSettings.tsx`, `frontend/src/components/settings/WebAccessTLSSettings.tsx` - the Settings → General block: `parseWebAccessInfo` boundary validator (fail-open read → "unavailable" state), the optimistic toggle with rollback + authoritative re-read, and two self-committing fields of one design (no apply button — each commits on Enter or focus loss, like the UI Scale control). The address field is ONE URL-style input (`parseWebAccessAddress`: strict local pattern — IPv4 octets bounded 0-255 in the regex, bracketed IPv6, `localhost`, port 1–65535; the scheme is display-only — `http://`/`https://` are accepted and stripped (the transport itself is the TLS switch, [ADR-102](../decisions/102-web-access-tls.md)), any other scheme refused) feeding `SetWebAccessConnection` — an invalid value is refused locally and never reaches the backend. The token field sits under it: a monospace password input seeded with the live credential (the raw value is masked until revealed; copy on demand), accepting an operator-typed value validated by `parseWebAccessToken` (trimmed, 8–256 characters, mirrored on the backend by `config.ValidateWebAccessToken`) feeding `SetWebAccessToken` — an emptied field always reverts (emptiness means GENERATED, never a save) — plus the Regenerate button (rotation through `RegenerateWebAccessToken`). The TLS block (`WebAccessTLSSettings.tsx`) rides the same doctrine ([ADR-102](../decisions/102-web-access-tls.md)): an optimistic HTTPS toggle with rollback + authoritative re-read, two self-committing path fields — cert and key, one design: each seeds from the live info payload and commits the FULL pair (its edited value plus the persisted counterpart; either field may point at one combined PEM — a single document carrying certificate and key is a valid pair), a backend refusal ("unreadable"/"does not match") lands in the error row with the draft preserved, and the post-Generate re-read re-seeds BOTH fields; plus a busy Generate button, and the backend's `cert_detail` rendered verbatim as the warning row. `webAccessLogin(token)` posts the credential to `POST /api/login` directly (a pre-session REST call, not an RPC) and translates 401/429/transport failures into operator-actionable messages.
- `frontend/index.html`, `frontend/public/favicon.png` - the SPA favicon: the browser tab's identity (the Wails webview never shows one). The sidecar's static FS serves the same embedded tree the Wails asset server does, so the icon rides for free.
- `frontend/src/components/settings/SettingsModal.tsx` (Web Access + Tabs blocks), `frontend/src/api/notifications.ts`, `frontend/src/lib/systemNotifications.ts` - the web-mode UI adaptations: in the web transport the modal hides the Web Access block (the control RPCs are unreachable from a tab — the section could only ever render "unavailable") and the Tabs block (see the invariant below); on the desktop the Web Access block renders only while the master experimental gate is open — the compound guard `experimentalEnabled && !isWebTransport()` sits around the border wrapper (the Session Statistics precedent), reads `useExperimentalStore` reactively, so flipping the switch in Settings → Experimental hides/reveals the block without a reload and the `border-t pt-4` wrapper disappears with it ([ADR-101](../decisions/101-browser-web-access.md)); `api/notifications.ts` branches every entry point to the browser Notification API — the boot init reads the permission (a prompt must ride a gesture), the Settings toggle-on click and the Test button request it, a banner's click focuses the tab and replays `notification_clicked` LOCALLY through `runtime.emitLocalEvent`, so the downstream `isNotificationClickedData` guard and `useNotificationClicks` navigation are byte-identical to the desktop's Go-owned round-trip; `lib/systemNotifications.ts`'s availability guard accepts either transport. Without a Service Worker, browser banners require the tab to stay alive — the recorded stage-1 limitation.
- `frontend/src/components/webaccess/WebAccessGate.tsx` - the SPA login gate mounted above `<App />` in `main.tsx`: holds the app on a probe spinner until the transport resolves (the late-join boot barrier — see Invariants), renders children untouched for the wails/none transports and for an authenticated web tab; replaces the app with a token form when the probe reports no session or a mid-session 401 fires; a successful login reloads the page (through `lib/reload.ts`, the mock seam) so every store, the probe and the websocket boot authenticated. Percentage sizing only — zoom-safe under the UI Scale.
- `desktop/webaccess_extra.go` - the App-level extra surface: `webExtraSurface`, the MINIMAL adapter passed as `Options.ExtraDispatch` — currently exactly one method, `GetPendingActions` (the HITL reconciliation sweep a session switch fires; it reads app state that never moved to `FrontendAPI`). Never a passthrough to the App: every adapter method widens the browser attack surface and is pinned by `desktop/webaccess_extra_test.go` (exact method set, d.ts presence, control-RPC unreachability) and the sidecar surface contract test.
- `desktop/webaccess_test.go`, `internal/webaccess/contract_test.go` - the lifecycle/isolation tests (mount, bounded stop, hot restart, control-RPC unreachability over the real authenticated handler) and the surface-contract test (denylist ↔ dispatch-target correspondence, upload-limit sizing).

type Options struct {
    Config        config.WebAccessConfig          // resolved web_access section; New refuses a disabled section (ErrDisabled), an invalid bind, or — with tls.enabled — an unreadable cert/key pair (fail-closed: a listener configured as encrypted never downgrades to plaintext)

    WSInbound     func(c *WSConn, data []byte)    // the whitelisted HITL bridge — desktop/webaccess_inbound.go at mount; nil discards
}

type Server struct{ /* ... */ }

HTTP surface (all JSON, all same-origin; dynamic responses carry `Cache-Control: no-store`):

| Route | Auth | Behavior |
| ----- | ---- | -------- |
| `GET /api/transport` | none | Bootstrap answer the SPA shell probes first: `{transport:"web", ws:"/ws", authenticated:true}` WITH a session cookie, the minimal `{transport:"web"}` without one (no `/ws` disclosure, no session-presence oracle before login — the shim defaults the socket path to `/ws`) |
| `POST /api/login` | none (rate limited: 10 attempts/min per IP, `Retry-After` on 429) | Token in the POST body → `HttpOnly` `SameSite=Strict` session cookie (`Secure` rides the transport — set exactly when the sidecar terminates TLS, [ADR-102](../decisions/102-web-access-tls.md)). 400 malformed · 401 wrong token · 429 limited |
| `POST /api/rpc/{method}` | session cookie | Positional JSON array args → JSON result, or `{error}` envelope with a non-200 status |
| `GET /ws` | session cookie + exact same-origin `Origin` | RFC6455 upgrade; one `{name,args}` frame per event |
| `GET /` | none | Static SPA through the injected CSP middleware |

## Flow

Two clients, one backend, one emit funnel:

```
                         ┌─────────────────────────────────────────────────────────┐
   backend/core events ──► (*App).emit  ──► wailsRuntime.EventsEmit ──► webview    │
                         │      │            (batched flush = c0wrk:events:batch)   │
                         │      └─► eventTap (atomic, nil-safe) ──► hub ──WS──► browser
                         └─────────────────────────────────────────────────────────┘

 webview : window.go.desktop.App.M(args) ──────────────► direct Go call (Wails IPC)
 browser : POST /api/rpc/M  [cookie] ──► reflection dispatcher ──► *backend.FrontendAPI method
 browser : GET /  ──► [CSP middleware] ──► static FS (frontend/dist) ──► same SPA bundle
 browser : GET /ws ──► [cookie + Origin check] ──► per-client outbox ──► one frame per event
 browser : WS text {name,args} ──► WSInbound whitelist ──► shared HITL handlers (webview answers ride Wails events)
```

1. **Mount** — startup (`initWebAccess`, after `emitBackendReady`) or `SetWebAccessEnabled(true)` — whose flip preflights the TLS pair fail-closed, [ADR-102](../decisions/102-web-access-tls.md) — builds `Options` from the live `FrontendAPI`, the SPA tree `main.go` handed over, `CSPMiddleware()`, the resolved config section, and the inbound HITL dispatcher — after minting the credential when the section carries an empty token (generated once, persisted through the immediate config save; a failed persist aborts the start); `New` validates (enabled, valid bind, port range, non-nil dispatch target — and, with `tls.enabled`, a readable cert/key pair: fail-closed, a listener configured as encrypted never downgrades to plaintext) and mints the separate per-launch session secret; `Start` binds and publishes the handle, then the tap — in that order, so `GetWebAccessInfo` already sees `Running` once events can flow.
2. **Detection** — the webview resolves `'wails'` synchronously; a browser page probes `GET /api/transport` and resolves `'web'` (or `'none'` when no sidecar serves the origin — plain dev server, vitest, SSR). The probe is an async round trip, and the gate HOLDS the app on a splash spinner until it settles: a late-joining tab that mounted the app into an unresolved transport would fire its mount-time RPCs at `getApp()` while the shim still reads `'pending'` — the throw kills `App.tsx`'s one-shot startup safety nets and the tab strands on an empty splash forever. The event socket connects only from an `authenticated:true` answer (a pre-auth tab holds no cookie; login always reloads the page, so the fresh probe reconnects). Settling `'web'` also applies the web-mode workspace adaptations BEFORE the app mounts — the gate forces `uiStore.tabsEnabled` off (the browser owns the tabs; the tab layer degenerates to its documented single-tab special case and every reader — bar, hotkeys, notification-click routing — agrees because they all read the store) and `setWindowTitle` mirrors the title into `document.title` from then on.
3. **Login** — the SPA shell's `WebAccessGate` asks the operator for the token (the form appears when `GET /api/transport` answered `authenticated:false`, or live when an RPC answers 401 under an already-open tab); `POST /api/login` exchanges it for the session cookie and the page reloads, so every store, the probe and the websocket boot authenticated. Rejected attempts log only a SHA-256 digest of the presented secret.
4. **RPC** — every call dispatches by reflection over the exported `FrontendAPI` method surface (the same surface the Wails binding generator consumes), falling back to the extra surface's minimal App-level adapter (`desktop/webaccess_extra.go` — currently `GetPendingActions`) when the primary target has no such method: denylisted → 403 with the reason (the denylist governs the union), unknown → 404, wrong arg count → 400, variadic → 501 (fail-closed; no such method exists today), a panicking method → 500 envelope, a non-nil trailing `error` → 500 envelope. Bodies are capped at 1 MiB (48 MiB for `AttachFileContent`, whose base64 payload must fit the backend's own 32 MiB raw cap).
5. **Events** — backend events already funnel through `(*App).emit`; the tap marshals one `{name,args}` envelope per emit call (once, before fan-out) and enqueues it on every live client's bounded outbox (1024 frames). The fan-out never blocks the desktop event goroutine; a client that cannot keep up is dropped with a Warn (it reconnects with backoff — 500 ms doubling to 30 s). The desktop layer's own batching is upstream of `emit`, so a coalesced flush arrives as its `c0wrk:events:batch` envelope frame and the shim unwraps it through the same path the webview uses; the sidecar itself adds no batching and reshapes nothing. Inbound frames ride the same envelope in reverse: the mount wires `Options.WSInbound` to `webWSInboundDispatcher`, whose whitelist resolves exactly the seven frontend→backend HITL events (`tool_confirm_response`, `tool_judge_request`, `ask_user_response`, `step_limit_response`, `plan_approval_response`, `goal_proposal_response`, `goal_suggestion_response`) through the shared handlers — the desktop event listeners and the web bridge are two transports over one authorization decision. Everything else is dropped at Debug and the connection survives.
6. **Stop** — app `Shutdown` (`stopWebAccess`, ~3 s budget, after `stopEmbeddedLLM`) or `SetWebAccessEnabled(false)` clears the handle and the tap first, then stops the server: graceful `Shutdown` within the deadline, then a force-close that reclaims hijacked WebSocket connections. Idempotent; a quit is never blocked by the sidecar.

## Multi-surface consistency

The same UI bundle can be open on several surfaces at once — the Wails webview plus any number of authenticated browser tabs. The backend treats them symmetrically; convergence rests on the shared emit funnel plus a small event set, never on per-surface push logic:

- **One emit funnel delivers to every surface.** Each backend event is dispatched once through `(*App).emit` (Flow step 5): the Wails runtime fans it out to the webview while the event tap enqueues the same envelope on every connected tab's outbox. No event is addressed to a single surface and no surface holds state the others cannot reach — every surface sees the same stream, and any surface can act through the same RPC surface (a mutation issued from a tab emits the same events back to all surfaces, including the one that caused them). Inbound HITL answers keep the shared handlers' first-responder-wins semantics, so two surfaces racing one action converge instead of double-applying.
- **List events converge the surrounding UI.** Mutations carry no per-surface bookkeeping: every list-affecting session mutation emits the global `sessions:changed` (no payload; [event-catalog.md](../contracts/event-catalog.md)), whose debounced re-reads — `useSessionLoader` via `ListSessions`, `useActiveSessionsRefresh` via one coalesced `ListAllSessions` — refresh each surface's sidebar and cross-project snapshot, including a tab whose RPC arrived over the websocket. The same holds per session: `message_received` goes to every surface watching the session — the sender dedups the echo against its optimistic copy (`useChatEvents`' `shouldAddReceivedUserMessage`), every other surface renders the user card from the event, so a message typed on one surface is visible on all of them without a session switch.
- **HITL answers are broadcast, not local.** Resolving a pending prompt (tool confirmation, ask-user, step limit, plan review, goal proposal/suggestion) emits one session-scoped `hitl_resolved` through the same funnel as the prompt itself ([event-catalog.md](../contracts/event-catalog.md)), so every surface retires its open card immediately — a second browser tab watching the same session does not keep a dead confirmation card hanging while the task it gated resumes in front of it. The payload carries the EFFECTIVE (first-responder-wins) decision, so a surface whose optimistic answer lost the race converges on the outcome that actually drove the agent, and a stale click on an already-settled card is a no-op (the card handler re-reads the settled metadata before writing). On every surface the handler also re-queries `GetPendingActions` for a session still carrying a pending-override bit in `activeSessionsStore`, so the live-sessions indicator settles with the cards instead of waiting for a reconcile. The focus/visibility resync below remains the backstop only for a push that never arrived: its `GetPendingActions` sweep settles the same state eventually, and every sweep pass self-heals a stale override bit, so the badge converges even when the event is lost.
- **A shallow resync repairs silent transport gaps.** Delivery is per-connection: a dropped socket (or a backgrounded tab whose browser throttles the websocket) loses deltas silently — the deltas stop, not the state. `useShallowResync` (mounted app-wide; its focus/visibility triggers arm through the shared `armWhenRuntimeReady` gate — the desktop attaches synchronously at mount, a web tab attaches when the transport probe resolves `'web'`, `'none'` never arms; see the file entry above for why `backend:ready` cannot be the web signal) re-reads the three pieces the chat UI is built from through the exact loaders a session switch uses — `reloadSessionHistory` (idempotent merge into the chat store), the active project's session list, and the cross-project snapshot plus the pending-HITL sweep — on WS re-connect (`onWSReconnected`, fired by the shim when the socket re-opens after a failure; the desktop transport has no websocket, so focus/visibility covers it), window focus and tab-visible, behind a debounce + min-interval so a trigger burst collapses into one run. Convergence is eventual by construction: after any reconnect or focus, a surface is one shallow reload away from the truth with no manual session switch.

## Invariants

- **Sidecar boundary** — everything web-specific lives only in `internal/webaccess` and the frontend shim (`frontend/src/api/runtime.ts` web branches, `frontend/src/api/webAccess.ts`, `frontend/src/components/webaccess/WebAccessGate.tsx`, `WebAccessSettings.tsx`). `internal/webaccess` imports only the Go stdlib and `backend/config` (never `desktop`, never Wails — guarded by `TestPackageImportHygiene`); `desktop` is its only importer; `backend` and `core` never reference it.
- **One emit path** — every backend-facing event flows through `(*App).emit` exactly once; the tap observes the same dispatch the webview gets. The tap never alters, filters, blocks, or fails the Wails emit; a panic inside it is recovered and logged ("desktop dispatch unaffected"). Event producers know nothing about transports.
- **Validity is gated; exposure is the operator's warned decision** — the bind accepts any valid IP literal or `localhost` (default `127.0.0.1`), and every fail-soft/fail-closed gate keys on validity only: the loader resets an invalid section (unparseable bind, bind missing while enabled, out-of-range port) to the safe default (sidecar off) with a visible warning, `Save` refuses to persist one, and `New` rejects it with the same messages. A valid non-loopback bind survives the whole pipeline — it saves as-is and `New` warns again at sidecar start — while the Settings UI renders its network-exposure banner from the same `IsLoopbackBind` classification the warnings use ([ADR-101](../decisions/101-browser-web-access.md), decision 12). The LOAD exposure warning is scoped to the plain-HTTP combination ([ADR-102](../decisions/102-web-access-tls.md)): a TLS-encrypted non-loopback bind loads warning-free, its exposure staying surfaced by the section banner and the start log. An UNUSABLE TLS is a class of its own ([ADR-102](../decisions/102-web-access-tls.md)): it turns the whole section off at load with one warning — a requested TLS is never downgraded to plain HTTP, so no listener is left to expose.
- **The transport is plain HTTP by default and TLS only through `web_access.tls` — and a broken TLS never downgrades to plaintext** — the subsection's `enabled` is the only switch (the address field's scheme is display-only), the sidecar terminates TLS itself with `MinVersion` pinned to 1.2, and `New` fails closed on an enabled-but-unreadable pair — and, since [ADR-102](../decisions/102-web-access-tls.md), the load path reads the pair too: an unusable subsection (empty paths or an unloadable pair) turns the whole section OFF with a warning, so a listener the operator configured as encrypted is never silently served as plaintext, in any path ([ADR-102](../decisions/102-web-access-tls.md), decision 2). The session cookie carries `Secure` exactly when the sidecar terminates TLS — on plain HTTP the cookie keeps its pre-ADR-102 shape and the HTTP behavior is byte-identical (decision 6). The same-origin WS check, the rate limiter, the denylist and the exposure classification stand unchanged on both transports; the one transport-keyed exception is the load warning's plain-HTTP scope ([ADR-102](../decisions/102-web-access-tls.md)).
- **Certificate fit for the pinned bind is a computed, visible property** — whenever `tls_cert` is configured, `GetWebAccessInfo` classifies the pair the same way the sidecar loads it (unreadable → mismatch → expired → ok, deterministic order) and the Settings block renders the detail as a warning row; changing the bind after the pair was generated is the canonical mismatch trigger, and regenerating the app-owned pair is the fix ([ADR-102](../decisions/102-web-access-tls.md), decision 5). The notification-banner corollary still keys on the origin's security context: the Web Notification API is a secure-context-gated platform feature, so a non-loopback **plain-HTTP** bind leaves the page an insecure origin where browsers never grant permission — regardless of any site setting — while the loopback default keeps banners available, and TLS serving lifts the page to an https origin, the platform's secure context (see [system-notifications.md](frontend/system-notifications.md), Web-transport permission contract).
- **Default off** — an absent section, or `enabled: false`, starts nothing; the app behaves exactly as before the feature existed.
- **Availability is the conjunction of two switches, both live-followed** — the sidecar mounts only while `experimental.enabled` AND `web_access.enabled` are on, and the conjunction is enforced OUTSIDE the section: the startup mount and the desktop hook decide it, the Settings render guard mirrors it, and the section, the loader and the sidecar package stay gate-free. The master switch applies through a persist-then-hook seam: `UpdateExperimentalFeatures` persists first, then invokes the `OnExperimentalChanged` hook (`applyExperimentalWebAccess`) synchronously on the toggle's goroutine under `webAccessMu` — the hook fires ONLY after a successful persist (the lifecycle follows persisted operator intent; a rejected disk write starts and stops nothing), mounts when the gate opens over an enabled section, stops (bounded by `webAccessStopBudget`) when it closes, and no-ops every other combination. The section's own switch (`SetWebAccessEnabled`) is unchanged. A closed gate skips quietly at Debug — an intentionally-off feature is not a failure ([ADR-101](../decisions/101-browser-web-access.md)).
- **Denylist is the only surface reduction** — the web-dispatchable surface is exactly the exported `FrontendAPI` methods minus `deniedMethods`: `EmitSessionEvent` (a web client must consume events, never forge them into the trusted bus) and `PasteFromClipboard` (OS-wide clipboard exfiltration). Entries are web-transport hazards only, each with its reason inline; ordinary business policy stays in the methods it belongs to. The ONE surface addition runs the other direction: the extra surface (`Options.ExtraDispatch`) is a desktop-owned, explicitly pinned adapter for App-level methods the mirrored UI needs (today only `GetPendingActions`) — the denylist governs the union, and the adapter is never a passthrough to the App.
- **Production CSP per-directive contract** (`desktop/csp.go`) — `default-src 'none'` deny-all base; `script-src 'self'` (bundle + Wails runtime/IPC scripts served same-origin; no remote/inline scripts); `style-src 'self' 'unsafe-inline'` (link stylesheets + injected style elements/attributes: Tailwind utilities, theme injection, CodeMirror/xterm inline styling); `img-src 'self' data: https: http:` — bundled assets, `data:` URIs from the markdown image pipeline, and external http/https images the markdown and paper renderers pass through verbatim (`markdownImageResolve.ts` `EXTERNAL_SRC_RE`, `paperHtmlSanitize.ts`); images are passive content granting no script/connect rights, so the exfiltration channel closed by `connect-src 'self'` stays closed; `font-src 'self' data:` (Nerd Fonts, `data:`-embedded); `connect-src 'self'` only (the desktop IPC transport); `worker`/`frame`/`object`/`base-uri`/`form-action`/`frame-ancestors` all `'none'` (no workers/iframes/plugins, `<base>` hijack, form navigation, or embedding).
- **The web SPA boots only after the transport probe settles** — the login gate holds the app on a probe spinner while the shim's transport is unresolved (`'pending'`) and mounts it only into `'wails'` (synchronous — the window never waits), an authenticated `'web'`, or `'none'`. This is load-bearing, not cosmetic: `getApp()` throws while the transport is unresolved, and every mount-time RPC that beats the async probe dies with it — `App.tsx`'s RPC safety net (the one-shot splash → main transition) has no retry, so a tab that mounted early strands on an empty splash forever. Pinned by the gate and shim tests (a mid-probe mount must render the spinner, never the app).
- **The web-mode UI adaptations are forced, not optional** — in the web transport the workspace tab bar is OFF (`WebAccessGate` flips `uiStore.tabsEnabled` to false before the app mounts; a browser tab lives in the browser's own tab strip), the window title lands in `document.title` (`runtime.setWindowTitle`), the modal's Web Access and Tabs blocks are hidden (a tab can neither control the sidecar nor re-enable the tab bar mid-session), and notification banners come from the browser Notification API (permission is a browser-site grant requested from the Settings toggle/Test gestures; a banner click replays `notification_clicked` locally through `runtime.emitLocalEvent` — the same guard and navigation path as the desktop's Go-owned callback, never a second routing entry point). Desktop behavior is byte-identical: every branch keys off `isWebTransport()`, which is false on `'wails'`/`'none'`.
- **The token never travels in a URL and never lands in logs** — login is POST-body only; requests authenticate by the `HttpOnly` `SameSite=Strict` session cookie, which carries a separate per-launch session secret (stealing a cookie reveals no durable secret); secrets are compared as fixed-size digests in constant time; rejected logins log only a `sha256:<prefix>(len=N)` digest; the ready log masks the token ("(hidden — see Settings → Web Access)"); `AuthToken()` is the token's only exit from the package.
- **The credential is generated by default; its runtime writers are the two dedicated token RPCs** — an empty `web_access.token` is minted at the first sidecar start (`webaccess.GenerateToken`, crypto/rand 32 bytes → 64 hex) and persisted through the same immediate config save every settings change uses; the credential is stable across restarts from that moment. `SetWebAccessConnection` never writes the token; the credential changes only through `SetWebAccessToken` (an operator-typed value, trimmed and bounds-checked by `config.ValidateWebAccessToken` — 8–256 characters, the empty value rejected so a cleared field can never overwrite a live credential) and `RegenerateWebAccessToken` (mint + persist + hot-restart) — both under the same rollback discipline (a failed persist keeps the old credential, a failed restart restores it on disk and live), serialized by `webAccessMu` so the writers can never interleave. The interactive bounds do NOT gate a hand-edited config.yaml: a static token shorter than 16 characters is honored but warned at sidecar start — tightening the rule must never lock an operator out of their own config. The mint is part of starting: a persist failure aborts the start loudly — a credential that would silently vanish on the next restart must never serve.
- **Control RPCs are unreachable from the web** — `GetWebAccessInfo`/`SetWebAccessEnabled` are methods on `desktop.App`, and the reflection dispatcher sees the `FrontendAPI` surface plus the extra surface's explicitly pinned adapter method set — never the App itself — so a browser tab can neither read the credential state nor flip the switch that feeds it. Pinned by tests over the sidecar's real authenticated handler and by `TestWebExtraSurfaceIsTheOnlyAppSliceOverTheWeb`.
- **The inbound event bridge is a whitelist, never a forge path** — an authenticated tab holds webview trust (the session cookie is the boundary), so it may resolve HITL actions; but only through the fixed bridge: `webWSInboundDispatcher` resolves exactly the seven frontend→backend HITL events via the same `desktop/event_handlers.go` handlers the Wails listeners use, drops every other name at Debug (network input must not write unbounded log lines), and `EmitSessionEvent` stays denylisted — arbitrary events still cannot be forged into the trusted bus. Two clients racing one action inherit the handlers' first-responder-wins semantics; a judge flood is self-bounded (the handler acts only on a live `pendingConfirmations` entry). Pinned by dispatch, wire, and hot-restart tests.
- **The feature stays additive** — deleting the sidecar package, its mount, and (optionally) the config section and Settings block restores the pre-feature app (see [Removal Path](#removal-path)); the zero-backend-edit rule holds with the single recorded exception of the additive `AttachFileContent` method.
- **Panics never cross the boundary** — every HTTP handler and goroutine is recovered; a panic in the web layer or in a dispatched method becomes a 500 envelope (or a closed connection), never an app crash.

## Configuration

```yaml
web_access:
  enabled: false   # the section's own switch; mounts only while experimental.enabled is ALSO on (ADR-101) — false (or an absent section) starts nothing
  bind: "127.0.0.1"  # any valid IP literal (loopback, wildcard, specific interface) or "localhost"; non-loopback = network-exposed
  port: 0          # 0 = pick a free port at every start
  token: ""        # empty = minted once at the first start and persisted; a hand-edited static token is honored (warned under 16 chars)
  tls:             # the HTTPS switch (ADR-102) — the protocol is never parsed out of the address field
    enabled: false # false = plain HTTP, byte-identical to pre-ADR-102
    cert: ""       # PEM certificate path; the app-owned pair is ~/.c0wrk/web-access.crt (+ .key), written by the Generate control
    key: ""        # PEM key path; authored explicitly next to cert (either field may point at one combined PEM); every commit validates the pair before persisting
```

The section is **externally gated** ([ADR-101](../decisions/101-browser-web-access.md)): `enabled: true` alone mounts nothing — the sidecar additionally requires the master `experimental.enabled` switch, and a mid-session flip of either switch mounts or stops the sidecar live (persist-then-hook seam on the master side, the toggle's own hot start/stop on the section side). Upgrade behavior is intentional: a config that opted in before the gate keeps its `web_access.enabled: true` across the upgrade but stays unmounted until the master switch is turned on. The gate lives in the mount points and the Settings render guard — this section stays pure data, and everything below (validity, exposure, credential) is unchanged by it.

Load is **fail-soft on validity** (the `shell_exec` precedent): an enabled section with an invalid value — an unparseable bind, a bind missing while enabled, an out-of-range port — produces a visible load warning and is reset to the canonical default state (disabled, loopback, auto port, empty token); a broken section never keeps the app from starting and never leaves an unusable listener configured. Save is **fail-closed on the same invalid values**: such a section is never persisted. A VALID non-loopback bind over PLAIN HTTP is refused BY DEFAULT (the security-review fix round, amending ADR-101 decision 12's warn-only model for exactly this shape): without the explicit `web_access.allow_insecure_lan` opt-in the section loads DISABLED with one warning naming both ways out, the save gate refuses to persist it, `SetWebAccessEnabled(true)` / a re-bind onto it / the TLS-off flip are all refused with the same message, and the sidecar mount (`New`) fail-closes on it — the token-over-plaintext combination is an accepted risk the operator must name, never a state a missed warning can drift into. With the opt-in in place the section is the operator's explicit decision: it is saved as-is, `New` warns once more at sidecar start (naming the accepted-risk flag), and the Settings block shows the network-exposure banner while the section is enabled and non-loopback. The CONFIG-LOAD exposure warning — the only exposure signal that reaches the top "Configuration warning" banner through `config_errors` — is scoped to the plain-HTTP combination, `bind not loopback AND tls.enabled false` (evaluated after the fail-soft resets and only for a SURVIVING enabled section, so an unusable TLS never reaches this gate — its section is disabled first and there is no listener to expose), while a TLS-encrypted non-loopback bind loads warning-free. The warning is LIVE, not a launch-frozen snapshot ([ADR-102](../decisions/102-web-access-tls.md)): the three transport-affecting control RPCs (enable, connection, TLS) recompute the section's `web_access*` entries in `config_errors` from the section's CURRENT state through the pure `config.WebAccessLoadWarnings` — the same text source the load tail delegates to, so the two can never drift — and the Settings banner re-reads the channel after each successful write; an HTTP→HTTPS flip drops the warning, the reverse flip, a re-bind onto a LAN address, or re-enabling the section restores it, and disabling clears it (a disabled section warns nothing — no listener, nothing to expose). The token RPCs and certificate Generate cannot move the warning state and stay out; the recompute is state-only (an unusable TLS is unreachable at runtime — the interactive writers preflight it fail-closed), the refresh is surgical (every non-`web_access` load warning survives; it is never a clear-all), and it runs strictly OUTSIDE `webAccessMu` — the lock-order rule that keeps the ADR-101 hook's `configMu`→`webAccessMu` order acyclic. So plain HTTP keeps three chances to see the consequence — the LIVE config-load warning, the section banner, and the start log; TLS keeps the two that are not the config-error channel — and neither is a gate ([ADR-101](../decisions/101-browser-web-access.md), decision 12, [ADR-102](../decisions/102-web-access-tls.md)). The bind and port ARE operator-pinnable — either by editing this file or through the Settings → Web Access address field, whose one URL-style input (the scheme is display-only — `http://`/`https://` accepted and stripped, strict local validation — an invalid value never reaches the backend, commit on Enter or focus loss) feeds `SetWebAccessConnection(bind, port)`, which persists with the toggle's rollback discipline (empty bind = the `127.0.0.1` default) and hot-restarts a running sidecar onto the new connection (a pin that cannot serve is rolled back and the previous one restored). The token is NOT part of that call: an empty value mints the credential at the first start (persisted immediately — stable across restarts from then on), the Settings token field under the address authors a custom one through `SetWebAccessToken` (trimmed, 8–256 characters, commit on Enter or focus loss; an emptied field reverts), and `RegenerateWebAccessToken` rotates it — all through the same persist + hot-restart + rollback discipline; a hand-edited static token shorter than 16 characters draws a visible Warn when the sidecar starts. The security-relevant constants — the validity rule itself, the loopback DEFAULT, the generated-credential DEFAULT, the token BOUNDS, the `HttpOnly`/`SameSite=Strict` cookie (with `Secure` riding the TLS switch), the TLS 1.3 floor (raised from the original 1.2 of ADR-102 decision 6 in the security-review fix round), the WS same-origin check — are **not** operator-configurable beyond what these RPCs accept: they are the feature's floor, not tunables ([ADR-101](../decisions/101-browser-web-access.md), decision 2). The `tls:` subsection ([ADR-102](../decisions/102-web-access-tls.md)) has ONE usability rule: an UNUSABLE subsection — `enabled` with an empty cert or key path, or a pair that fails to load from disk (the config layer READS and parses the pair here, the deliberate ADR-102 reversal of the never-reads-the-files doctrine) — turns the WHOLE section off at load with one visible warning naming the reason (`web_access.tls unusable (the sidecar stays disabled — a configured TLS is never downgraded to plain HTTP; fix the certificate pair or turn tls off, then enable web_access again): <reason>`): a requested TLS is never downgraded to plain HTTP, so no listener is the only safe state. The connection values and the subsection itself are preserved as authored (a disabled section is inert — the persisted shape stays valid; the operator fixes the pair and flips the switch back on, re-typing nothing), the save gate stays structure-only (filesystem state never bricks an unrelated settings save), and the interactive boundaries fail closed on the same predicate — `SetWebAccessTLS` refuses to commit an unloadable pair, and `SetWebAccessEnabled(true)` preflights it before enabling, so the toggle never produces a persisted-on switch above a silently-down sidecar. The sidecar mount keeps its fail-closed backstop (`New` refuses a pair it cannot load) for the one race the load path cannot see — files vanishing between load and mount; a running sidecar keeps serving from its in-memory certificate, and a hot-restart that cannot reload the pair simply fails closed. The Generate control (`GenerateWebAccessCertificate`) writes the fixed app-owned pair for the currently pinned bind — a self-signed ECDSA P-256 leaf, ServerAuth, 825-day validity, SANs covering the bind's browser-facing host; key 0600, cert 0644, atomic publication — then persists the pair's paths and hot-restarts a running sidecar; both paths are authored explicitly through the Settings block — two self-committing fields, each committing the full pair, which `SetWebAccessTLS` pre-loads before persisting (an unreadable or mismatched pair is refused at the commit), and both fields may point at ONE combined PEM (a single document carrying certificate and key is a valid pair); a layout beyond what two explicit paths express is authored by editing this file directly. The cookie's `Secure` flag is the transport's, not a tunable: set exactly when the sidecar terminates TLS, omitted on plain HTTP — the HTTP behavior stays byte-identical to pre-ADR-102, a host-local eavesdropper remains the loopback default's residual concern, and a non-loopback plain-HTTP bind remains the warned exposure TLS exists to close.

## Removal Path

The feature is designed to be deleted. To abandon the sidecar (headless exposure is a separate, future decision — the [ADR-101](../decisions/101-browser-web-access.md) stage-2 path is additive, not this):

1. **Delete `internal/webaccess/`** — the entire package, tests included. Nothing outside it (besides the mount) imports it.
2. **Delete the desktop mount** — `initWebAccess`/`stopWebAccess` in `desktop/startup_phases.go` and their call sites in `desktop/startup.go`; `startWebAccessLocked`/`stopWebAccessLocked`/`logWebAccessReady`; the `webAccess`/`webAccessMu`/`webAccessStatic` fields; the control RPCs `GetWebAccessInfo`/`SetWebAccessEnabled`/`SetWebAccessConnection`/`SetWebAccessToken`/`RegenerateWebAccessToken`/`SetWebAccessTLS`/`GenerateWebAccessCertificate` and the `SetWebAccessStaticFS` handover; the `eventTap` field + `setEventTap` (added for this feature — `emit` reverts to dispatching straight to Wails); `desktop/webaccess_inbound.go` + `desktop/webaccess_inbound_test.go` (the inbound bridge and its wire tests); `desktop/webaccess_extra.go` + `desktop/webaccess_extra_test.go` (the extra surface adapter and its pins — `GetPendingActions` stays usable by the webview, which reaches it through the Wails binding); `desktop/webaccess_test.go` + `desktop/webaccess_connection_test.go` + `desktop/webaccess_tls_test.go`; `desktop/webaccess_experimental_test.go` (the gate tests); `applyExperimentalWebAccess` and the `cfg.OnExperimentalChanged = a.applyExperimentalWebAccess` wiring line in `buildFrontendAPI`; the backend hook plumbing (`onExperimentalChanged`/`runExperimentalChangedHook` in `backend/frontend_api.go` + `backend/frontend_api_config.go`, plus the `OnExperimentalChanged` field on `FrontendAPIConfig` and the `cfg.OnExperimentalChanged = a.applyExperimentalWebAccess` line in `buildFrontendAPI` — `UpdateExperimentalFeatures` reverts to a pure config+router toggle); the `SetWebAccessStaticFS(fs.Sub(assets, "frontend/dist"))` line in `main.go`.
3. **Delete the config section** — `backend/config/web_access.go` (struct, `IsValidWebAccessBind`/`ValidateWebAccessBind`/`IsLoopbackBind`, load normalization, save validation) and the `web_access:` block from `config.example.yaml`. A leftover `web_access:` section in an existing user `config.yaml` is inert: the loader unmarshals non-strictly, so the unknown key is ignored and dropped by the next save.
4. **Delete the frontend surfaces** — `frontend/src/api/webAccess.ts`, `frontend/src/components/settings/WebAccessSettings.tsx`, `frontend/src/components/settings/WebAccessTLSSettings.tsx` (and their tests, plus the `webAccess` barrel export in `frontend/src/api/index.ts`); the `experimentalEnabled &&` Web Access render guard in `frontend/src/components/settings/SettingsModal.tsx` reverts to the plain `!isWebTransport()` ADR-101 rule.
5. **Remove the SECURITY.md attack-surface entry** for the built-in web server.

**What stays** (deliberately):

- `frontend/src/api/runtime.ts` — the transport shim is the abstraction seam a future headless build rides; with the sidecar gone its web probe simply resolves `'none'` and the Wails paths take over. Do not rip the `'web'` branches out as part of a removal cleanup unless the headless direction is also abandoned.
- `frontend/src/api/notifications.ts`'s web branches and the gate's `tabsEnabled` force-off — inert with the sidecar gone (`isWebTransport()` never true), same seam-preservation reasoning as `runtime.ts`.
- `AttachFileContent` (`backend/frontend_api_attachment.go`) — additive, desktop-useful, and the recorded exception to zero backend edits; it survives removal.
- The desktop event batching infrastructure — upstream of the sidecar and independent of it.

## Extension Points

- **Trust-store integration** — the seam ADR-102 deliberately left closed ([Alternatives](../decisions/102-web-access-tls.md)): the generated self-signed pair draws the browser's one-time warning screen, and mkcert-style local-CA installation stays a future, separately reviewed decision; operator-trusted certificates need no code — point `tls.cert`/`tls.key` at the PEM files.
- **Additional transports over the same event tap** — the tap is web-agnostic (`func(name string, args []interface{})`); a headless build would consume it through the surviving `runtime.ts` shim or a new consumer.
- **New backend RPCs appear to the browser automatically** — reflection dispatch needs no registration; new methods become web-callable the moment they become webview-callable. The surface-contract test is the place to note a new upload-sized method (raise its body cap in `uploadBodyMethods` if it carries bulk payloads) or a new web-transport hazard (denylist entry with its reason).
- **Inbound WS events beyond the HITL seven** — the bridge (`webWSInboundDispatcher`) resolves exactly the seven frontend→backend HITL events; a future feature that legitimately needs more UI→backend events over the web extends that whitelist with its own authorization reasoning and tests, never by reopening a generic forge path (`EmitSessionEvent` stays denied).
