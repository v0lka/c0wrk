# Contract: Desktop <-> Frontend

## Boundary Rule

Frontend communicates with Go exclusively through its transport bridge — no direct Go imports. Two channels: RPC (request/response) and Events (push notifications). There are two transports for the same bundle:

- **Wails IPC** (the desktop webview) — the primary, always-on channel: generated bindings over `*backend.FrontendAPI` for RPC, Wails events for push.
- **Web sidecar** (opt-in, `web_access.enabled`) — a browser tab served by the loopback web-access sidecar ([ADR-101](../decisions/101-browser-web-access.md), [../domains/web-access.md](../domains/web-access.md)): the same `FrontendAPI` surface dispatched by reflection over `POST /api/rpc/<Method>`, the same event stream bridged over the `/ws` WebSocket as `{name,args}` frames — and the same frames accepted inbound through a fixed whitelist (`desktop/webaccess_inbound.go`): exactly the seven frontend→backend HITL events resolve, through the same desktop handlers the Wails listeners use; every other inbound frame drops.

Sidecar control RPCs (`GetWebAccessInfo` and the `SetWebAccess*` / `RegenerateWebAccessToken` / `GenerateWebAccessCertificate` mutators) live on `desktop.App`, deliberately OFF the reflection-dispatched `FrontendAPI` surface, so a browser tab can neither read the credential state nor flip the switch that feeds it.

## RPC Surface

All methods on `*desktop.App` (promoted from `*backend.FrontendAPI`) are callable from frontend via `window.go.desktop.App.<MethodName>()`.

**Convention**: Methods that can fail return `(T, error)` in Go. Read-only getters that cannot fail return `T` only (e.g., `GetConfig`, `GetSecuritySettings`, `GetMCPStatus`, `GetMCPServers`, `GetToolList`, `GetVectorIndexStatus`, `GetCapabilityModes`, `GetNotificationBannerTimeout`, `ListSkills`, `GetSessionTokens`, `HasDefaultModel`). The "Returns" column shows the actual signature; Wails surfaces `error` as a rejected Promise in TypeScript.

### Sidebar Surface Gates (`backend/frontend_api_packgates.go`)

The Settings → General toggles under Prompt Suggestions ([ADR-115](../decisions/115-sidebar-pack-gates-reconcile-and-serialization.md)): each gate decides whether its sidebar tab (Research / Specs in the workspace panel) renders AND whether the surface's globally-seeded skill/agent pack stays on disk. > **Path-containment boundary**: read-path RPCs (`ReadFile`, `GetFileIcon`, `GetFileDiff`) resolve via `resolveReadablePath` and are **not** workspace-contained — the file viewer must display any path the agent surfaces in chat. Read-path resolution is lexical and GOOS-independent ([ADR-095](../decisions/095-chat-file-reference-path-semantics.md)): `ReadFile`, `GetFileIcon`, `ReadImageAsDataURL`, and `GetFileDiff` strip the trailing line anchor, then recognize absolute paths in every dialect via `core.IsAbsolutePath` (POSIX `/`, drive `^[A-Za-z]:[\\/]`, UNC `^[\\/]{2}`) and return them verbatim (drive/UNC included — never CWD-joined, never rooted into `/C:\…`; the legacy rooted `/C:/x/f.md` spelling is un-rooted when the remainder is a Windows-dialect absolute path), while relative inputs keep the historical `filepath.Abs` against the process CWD. `ReadFileAsDataURL` is the exception: it resolves via `resolveWorkspacePath` and **retains** containment, because image embedding runs during markdown auto-render (no explicit user action) and must not let a malicious document exfiltrate arbitrary files into the webview DOM. Its image-tab counterpart `ReadImageAsDataURL` deliberately does the **opposite** — it resolves via `resolveReadablePath` and is **not** contained, because the viewer must render an image the agent surfaced anywhere, and it only ever fires on an explicit user action (opening an image tab), so it does not widen the auto-render surface. Structural/write RPCs (`WriteFile`, `ListDirectory`) resolve via `resolveWorkspacePath` and **retain** containment (reject paths outside the active project workspace). This is a UI-display affordance only and does **not** affect the agent's tool surface: the `read_file` agent tool enforces its own session-root containment independently (see [../architecture/security-model.md](../architecture/security-model.md)).

`PaperDTO` carries the card's identity (`id`/`slug`/`title`/`authors`/`year`/`venue`/`identifiers`), four string-enum axes — `mode` (`skim`/`deep`/`survey`/`review`/`implement`/`teach`), `reading` (`full`/`selective`/`skip`; the reading DECISION, distinct from the soundness verdict), `verdict` (`accepted`/`rejected`/`uncertain`; the soundness judgement, appraisal-wins), `confidence` (`low`/`medium`/`high`) — the `research_ids`/`anchors`/`claims`/`red_flags`/`uncertainties` collections, and the resolution fields `dir`/`card_path`/`pinned`/`linked_research`. The frontend boundary (`normalizePaper` in `frontend/src/api/papers.ts`) mirrors the enum vocabularies exactly and folds an out-of-set value to `""`.

The study-paper skill additionally authors a `flashcards.md` deck per paper (a card table plus an append-only review log). `core/papers` parses/renders it (`ParseFlashcards`/`RenderFlashcards`) and appends self-grades in place (`ApplyReview` + `RecordCardReview`, atomic and containment-checked); the paper workspace's Flashcards section renders it as an interactive active-recall review (`frontend/src/components/papers/FlashcardsReview.tsx`), whose interval schedule (`frontend/src/lib/spacedRepetition.ts`) mirrors `core/papers`.

Multi-paper comparisons are a second global sibling of the research root — `<research-root>/comparisons/<slug>.md`, one artifact per comparison set, written by the study-paper Compare intent from its `comparison-matrix` template (path helpers `config.ComparisonDirName` / `config.ComparisonsPathIn` / `config.ComparisonsPath`). Comparisons have no dedicated RPC: the frontend reads them through the workspace file RPCs (`ListDirectory`/`ReadFile`) under the same research root. The Papers panel's multi-select ("Compare selected", enabled at ≥2 papers) dispatches the skill with that artifact path; the paper workspace's Compare section renders every comparison that names the paper (`frontend/src/components/papers/CompareMatrix.tsx`).

`RunPaperLiterature` (in `backend/frontend_api_papers_literature.go`) runs the study-paper `literature.py` helper — the seeded, stdlib-only Python 3 graph builder that looks up a paper's predecessors / citing works / contradiction candidates (OpenAlex + Crossref + arXiv + Semantic Scholar) — and writes `<paper-dir>/literature.json` (`papers.LiteratureFileName`; helper OUTPUT, not part of `PaperArtifacts`). The written file is the SOLE read source for the panel: the frontend reads `literature.json` through the workspace file RPCs (`ListDirectory` + `ReadFile`) and never fetches on render — a lookup runs only on an explicit user action (the panel's Refresh control), so merely opening a paper never issues a network request. The helper write is ATOMIC (`write_atomic`: stage in a sibling temp file, `fsync`, then `os.replace`), so a reader never observes a partially written file, and the payload carries a `generated_at` UTC timestamp the panel renders as a "generated <date>" staleness hint (an older file stays old — the panel never silently re-runs). It resolves the seed from the card's identifiers (DOI → arXiv → any id → title) and runs the helper through c0wrk's managed Python (`toolmanager.VenvPythonPath(config.ToolsDir(agentDir))`) off the seeded script at `<SkillsDir>/study-paper/scripts/literature.py`; the whole run serializes on the per-research-root mutation mutex shared with `SetPaperPinned` / `RecordFlashcardReview`, so a lookup cannot interleave with a pin/flashcard write. Every non-success outcome is an EXPLICIT status, never an opaque failure: the helper's exit codes map to `offline` (2), `unresolved` (1), `rate_limited` (3), `error` (anything else, incl. a timeout); a missing managed Python, a missing seeded script, or a card with no resolvable seed yield `no_python` / `no_script` / `no_seed` (the panel turns `no_python` into an actionable affordance that names the tool-manager install path and offers a retry, rather than a bare message). Only a transport-level problem — an unknown paper or a containment violation — is a Go `error`. A `90s` wall clock bounds the whole helper invocation (the helper owns its own per-request HTTP timeout); the helper's stderr tail is truncated to 600 runes into `Message`, and `Path`/`Content` describe the written `literature.json` (empty when nothing was written).

`FetchPaperOriginal` (in `backend/frontend_api_papers_source.go`) fetches a paper's original arXiv HTML rendition and localizes it into `<paper-dir>/paper.html` (`papers.OriginalHTMLFileName`) plus `<paper-dir>/assets/` (`papers.OriginalAssetsDirName`) via `core/papers.FetchOriginalHTML` — the native `arxiv.org/html/<id>` rendition first, the `ar5iv` mirror as fallback, with the endpoint hosts forming a hard redirect/image allowlist, streaming byte caps (8 MiB document, 2 MiB per image, ≤200 images), `script`/`style`/`iframe` stripping, and `img src` rewritten to `assets/<name>` resolved against the final document URL. The arXiv id is normalized from the card's identifiers (`papers.NormalizeArxivID`); a card with no usable id yields `no_arxiv` without touching the network or disk. Like `RunPaperLiterature`, the RPC mirrors the explicit-status contract: every non-success outcome is a STATUS (`ok` | `offline` | `no_arxiv` | `not_found` | `error`) — `offline` when no endpoint was reachable at the network level, `not_found` when every reachable endpoint answered 404/410, `error` for anything else (unexpected status, oversized document, containment violation, filesystem failure) — and only a transport-level problem (unknown paper, containment violation, or a concurrent research-root change) is a Go `error`. Concurrency mirrors `RunPaperLiterature`: the paper resolves under a SHORT hold of the per-research-root mutation mutex (re-loading the row so a concurrent root move is rejected with `errResearchRootChanged`), the mutex is RELEASED before the network-bound fetch runs (its per-request timeouts — 60s document, 20s image — bound the work; holding the row mutex would head-of-line-block every pin/flashcard/research mutation), and concurrent runs targeting the SAME paper serialize on the shared per-paper-directory guard (`paperRunMuKey`). The write is atomic (staging dir inside the paper dir, assets swapped, `paper.html` renamed last as the commit point) and containment-checked in `core/papers`; any failure leaves prior content byte-for-byte intact. No event is emitted synchronously — the write lands inside the watched library, so the file watcher emits `papers:changed` and the caller's resolved promise is its refresh signal. `PaperOriginalDTO` carries only `status` and `url` (the URL that actually produced the document, after redirects; empty unless the fetch succeeded). The frontend boundary (`normalizePaperOriginalResult` in `frontend/src/api/papers.ts`) mirrors the status vocabulary exactly and folds an unknown or missing status to `error`, so the explicit-status contract can never regress into a silent success at the boundary.

### Specs (`backend/frontend_api_specs.go`)

The Specs sidebar panel's single read RPC over a project's `specs/` tree (ADR-106; recomposed by [ADR-108](../decisions/108-specs-panel-usability-redesign.md), simplified to the single sidebar surface by [ADR-109](../decisions/109-specs-panel-simplification.md)). The specs root is `<workspace>/specs` (`config.ProjectSpecsPath`) of the workspace the ACTIVE SESSION resolves to — a session worktree when one resolves, the project checkout as fallback ([ADR-116](../decisions/116-specs-root-follows-active-session.md), ADR-099's protocol) — and is read-only for the application: the parser never creates or writes anything under it. The tree is parsed by `core/specs.ParseSpecsRoot` into files (grouped by section), the `INDEX.md` task→spec navigation table, ADR metadata, and the deterministic tier-1 integrity findings; a MISSING or non-directory root parses to the neutral `present=false` state, and an existing EMPTY or PARTIAL tree parses `present=true` with whatever content is readable — never an error in either case. Every DTO collection and the counts histogram are non-nil on the wire (empty `[]`/`{}`, never `null`), and the frontend boundary (`frontend/src/api/specs.ts`) re-validates the outer shape, drops malformed entries per-entry, and recomputes the counts from the normalized collections. The tier-1 findings are VALUE data behind the stable shape — nine categories as of [ADR-109](../decisions/109-specs-panel-simplification.md) — and a finding's `kind` travels as an open string: the boundary passes an unknown kind through (typed into the union, rendered with a generic label) instead of dropping the finding. Each wire `adrs` element is an `ADRMetaDTO` — the parsed `specs.ADRMeta` embedded verbatim plus an optional `date` (ISO `YYYY-MM-DD`, the file's add date; `omitempty` when unknown). The date enrichment ([ADR-108](../decisions/108-specs-panel-usability-redesign.md)) is fail-soft: ONE bounded `git log --diff-filter=A --name-only --format=%as -- specs/decisions` call (the shared `gitCmdTimeout` ceiling, skipped for No Project / an unparseable root / zero ADRs) maps each file to its git add date in the boundary workspace the root was derived from — the parsed tree's own HEAD, never the checkout's ([ADR-116](../decisions/116-specs-root-follows-active-session.md)); a non-git workspace, a missing git binary, an unborn HEAD, or any spawn/run error leaves every date absent while the RPC still succeeds (Debug-only logging). The specs file format is unchanged — dates are derived from git history, never written into the records. There is no dedicated `specs:*` event — the panel refreshes on mount, on an active-session switch, on `workspace:tree_changed` scoped to `specs/` paths, and on the header's manual refresh button (a repeated `GetSpecsStatus` through the same fetch funnel — the manual gesture introduces neither a new RPC nor an event); every mutating gesture dispatches a `spec-*` skill into the chat (`specsActions.ts`; the header's findings badge dispatches ONE aggregate `spec-update` task and each finding card's fix badge ONE per-finding `spec-update` task, both prompts quoting their findings verbatim through the shared `findingLine`, [ADR-109](../decisions/109-specs-panel-simplification.md)), never an RPC. See [../domains/specs.md](../domains/specs.md) for the full subsystem (the seeded skill pack, the panel, and the invariants).

Idempotent and single-instance; refused while ANY embedded operation is in flight (an install or a removal), and actionable when nothing is installed. The idle budget starts only once the load completes |
| `UnloadEmbeddedLLM` | — | error | Stop the process, returning its RAM/VRAM; the bytes stay on disk, so the state afterwards is `installed`. Refused while an install or removal holds the subsystem-wide operation gate — the same `embeddedBusyOperation` read `LoadEmbeddedLLM` and the probe do, kept uniform even though nothing can be resident while a holder runs. Blocking and idempotent — unloading a model that is not resident is not an error — and bounded for the same gate-acquisition reason `RemoveEmbeddedLLM` is: the 30 s budget covers only the wait for the single-instance gate, after which the stop derives its own budget on either path — `stopTimeout + killWait` once the gate is held, or the no-gate force path's 16 s when the budget expired with a child still live — so an unload during a cold load finishes in ≤ 46 s with the model stopped instead of hanging. The TRANSLATED "a load is still in progress" error — the one `embeddedBoundedStopErr` produces, and it fires only on `errors.Is(err, context.DeadlineExceeded)` — is returned only when no child had spawned yet, the one case where there is nothing to kill and the gate timeout is the whole truth; that scoping is about this one translation, not about every error this RPC can return. A stop that did not take is an error of its own on BOTH the gated and the force path (`terminate`'s "did not exit within … of being killed"), reported instead of claiming the memory was released, which keeps the state honest at `error` and the run handle attached |
| `SetEmbeddedLLMAutoUnload` | enabled, minutes | error | Persist `embedded_llm.auto_unload` and apply it to the supervisor immediately (re-armed against the existing activity stamp while loaded, so enabling the timer on — or shortening it below — the time already idle unloads the model at once rather than granting a fresh budget; disarmed when off). `minutes` outside **1..`embeddedllm.MaxAutoUnloadMinutes`** (525600) is refused without touching the config — the ceiling is the minutes→nanoseconds overflow guard, above which the multiply wraps and an "effectively never" value inverts into "unload immediately". The setting is an operator preference, not install state: it survives a removal |
| `GetEmbeddedLLMTuning` | — | (EmbeddedLLMTuningDTO, error) | Read the operator's persisted memory-plan overrides field for field — the FOURTEEN UI-exposed knobs of `embedded_llm.tuning` (`devices` and `split_mode` included, [ADR-107](../decisions/107-operator-selected-offload-devices.md); `devices` is null-or-array, an empty array and null both read as unset); the two checkpoint-policy keys `ctx_checkpoints`/`cache_idle_slots` are deliberately YAML-only end to end (no DTO field, no `SetEmbeddedLLMTuning` spelling, no `reset` key — observable only through `config.yaml` and the launch command line, see [../domains/embedded-llm.md](../domains/embedded-llm.md)); every field nullable, nil = *unset — the planner decides*. The resolved OUTCOME of these knobs is `GetEmbeddedLLMStatus`'s `plan`, not this DTO. Returns an error in exactly one case — before startup there is no config to read, and the fail-soft alternative (an all-nil DTO) is indistinguishable from "the operator overrode nothing", which an editor would then wipe on Save; a getter that cannot read the truth must not fabricate one. Performs no network I/O, no hardware probe, no translation. Does not require an install |
| `SetEmbeddedLLMTuning` | req: EmbeddedLLMTuningRequest | error | PARTIAL update of `embedded_llm.tuning`, mirroring `UpdateModelProfile`'s contract: a nil field keeps the stored value, a present field replaces its knob verbatim (an explicit `auto` spelling included — it is a real value, not a synonym for unset), and a knob named in `reset` is cleared back to unset (the only encoding that covers the fourteen UI-exposed knobs uniformly; an unknown key or a knob both reset and set in one request is refused without a write). Validation is the same `ToTuning` translation `config.validate()` runs on load, so "the RPC accepted it" and "the next config load accepts it" are the same statement. A no-op patch writes NOTHING (no config.yaml rewrite, no `config:updated`, no router rebuild). A failed persist rolls the in-memory state back through the shared save-or-rollback tail, and the write ends on the same tail as `SetEmbeddedLLMAutoUnload`: saveMu → configMu → atomic save-or-rollback → `config:updated` → judge/router rebuild → one `embedded_llm:state` snapshot. **The resident model is NOT restarted — that is the decision, not an omission**: every tuning knob is a launch flag, so a change takes effect on the NEXT load, and restarting a multi-minute weight load because an operator moved a slider would be a denial of service with no confirmation behind it. Instead `GetEmbeddedLLMStatus.reload_required` reports whether the running process predates the stored tuning (fingerprinted over the translated planner vocabulary, so equivalent respellings do not raise a spurious flag), and `UnloadEmbeddedLLM` + `LoadEmbeddedLLM` is the explicit apply-now path. Tuning is an operator setting, not install state: it survives a removal and does not require an install |
| `ProbeEmbeddedLLMDevices` | — | (EmbeddedLLMDevicesDTO, error) | On-demand re-measurement of THIS machine's accelerator memory: the device inventory (always an array, never null — an empty one is a real "no accelerator" answer), `unified`, `host_ram_gib`, both budgets and `probed_at`. Exists because the topology in `EmbeddedLLMStatus` is the RECORDED snapshot the plan was made from, and a snapshot goes stale (a GPU appears, a driver updates, another process takes the memory); the load-time re-probe is fail-soft and invisible, so an operator diagnosing a plan needs a way to ask directly. The one embedded-LLM read that is allowed to be slow and to fail, hence the error: core's `ProbeDevices` is fail-soft by contract (a load must not fail because a driver query wedged) and this RPC converts exactly that silence into the actionable failure it is here. The frontend consumes it through the Settings device-memory surface: `frontend/src/api/embeddedTuning.ts` wraps the probe as `probeEmbeddedLLMDevices()`, `frontend/src/stores/embeddedLLMSync.ts` drives it through the shared single-writer `refreshEmbeddedLLMDevices('auto' | 'manual')` — the auto re-probe fires on `embedded_llm:state` transitions and is skipped on the mtplx engine (a busy-gate refusal only logs; the next transition re-probes), while the manual re-measure is the only path that paints the refusal — and `frontend/src/components/settings/embedded/EmbeddedLLMDeviceMemory.tsx` probes on mount (auto) and through its re-measure button (manual). Requires an installed runtime (the probe asks the provisioned binary, the only source that agrees with the runtime's own allocation decisions), refused while ANY embedded operation is in flight, bounded by the probe timeout. Persists NOTHING and re-plans nothing: the measurement is returned and discarded, so a support bundle still describes the decision the plan was made from |

> **`embedded_llm.tuning` is not in `ConfigResponse` and is not a whole-section write.** The memory-plan override surface (see [../domains/embedded-llm.md](../domains/embedded-llm.md#configuration)) reaches the UI through its own RPC pair — `GetEmbeddedLLMTuning`/`SetEmbeddedLLMTuning` — rather than through the sanitized config view, exactly like `auto_unload` reaches it through `SetEmbeddedLLMAutoUnload`. The setter is a PARTIAL patch (nil keeps the stored value) with a `reset` list for the third state (*unset*), NOT a whole-sub-struct replacement: the section's pointers exist because *unset* and *explicit auto* are different persisted values, and a bool/int DTO cannot express the difference. The effective, resolved launch shape these knobs produce is read from `GetEmbeddedLLMStatus`'s `plan` — the tuning DTO is the override, never the outcome. A tuning write never restarts a resident model; it sets `reload_required` instead (see the `SetEmbeddedLLMTuning` row). Editing `config.yaml` by hand remains supported and is validated on load with a message naming the offending key.

The lifecycle half of this subsystem is NOT on the RPC surface: `FrontendAPILifecycle.InitEmbeddedLLM` (the startup manifest restore, called from the startup phase body in `backend/startup_phases.go` — no download, no probe, no load) and `FrontendAPILifecycle.StopEmbeddedLLM` (the Shutdown stop). Methods on `FrontendAPILifecycle` are never bound by Wails.

## Event Protocol

See [event-catalog.md](event-catalog.md) for complete event reference.

### Direction

- **Backend -> Frontend**: lifecycle events during task execution — [event-catalog.md](event-catalog.md) is the authoritative list of both the session-scoped and the global names
- **Frontend -> Backend**: the seven HITL events (`tool_confirm_response`, `tool_judge_request`, `ask_user_response`, `step_limit_response`, `plan_approval_response`, `goal_proposal_response`, `goal_suggestion_response`) — the same closed set the web transport's inbound whitelist resolves ([event-catalog.md](event-catalog.md#frontend-to-backend-events))

### Naming Convention

- Session-scoped: `session:${sessionId}:${eventType}`
- Global: bare event name (e.g., `backend:ready`)

## Data Flow Across Boundary

```
┌──────────────────┐                    ┌──────────────────┐
│   Desktop App    │                    │  Backend (Go)    │
│  (TypeScript)    │                    │                  │
│                  │   Wails Binding    │                  │
│  Wails API calls ├────────────────────►  App struct      │
│  (async Go fn)   │                    │  (methods)       │
│                  │                    │                  │
│  Event handlers  │◄───────────────────┤  EventsEmit()    │
│  (Go events)     │   Wails Events     │                  │
│                  │                    │                  │
│  state → store   │                    │  persistence     │
│  update (Zustand)│                    │  (SQLite)        │
└──────────────────┘                    └──────────────────┘
```

- **Synchronous**: Wails RPC method calls from frontend are async (TypeScript `Promise`) but the Go handler may block
- **Asynchronous**: real-time event stream is push-only; frontend listens with `EventsOn` and publishes to stores
- **Project switch state flow**:
  1. Frontend snapshots source project UI state (`open_tabs`, `active_file`, `saved_session_id`) and calls `SaveProjectSwitchState`/`SaveProjectUIState` (best-effort)
  2. Frontend calls `SwitchProject(id)`
  3. Backend persists/normalizes source project state, switches active project context, and records the destination project id as `last_active_project_id` in `app_state` (best-effort; exposed via `GetLastActiveProjectID` for restart restore)
  4. Backend resolves destination session fallback deterministically, skipping archived sessions at every step: saved session if valid (and not archived) for destination project → latest non-archived project session by activity (`ListSessionsByProject`) → backend creates a new project-scoped session via `SessionManager.CreateSession(projectID, workspacePath)` when no sessions exist
  5. Frontend calls `GetProjectSwitchState`/`GetProjectUIState`, restores file tabs/active file, refreshes session list, and activates the resolved session. When only the session selection changes inside an already-active project, the frontend calls `SaveProjectActiveSession` so the write cannot clobber viewer-owned tab state
- **Session creation flow (eager, ADR-091)**: in a CODE project the New Session gesture eagerly creates a plain LOCAL session (the CHAT contract — the row exists from the click onward; nothing is provisioned). While the active session is FRESH — its transcript confirmed empty (the message index exists and is empty; an absent index means "history not loaded", an unknown state) and no task running — the toolbar's `SessionWorkspaceSelector` is the interactive workspace choice (`local` default, or `branch…` → the BranchPicker's pick mode: the working tree's own branch is blocked since a worktree needs a free branch, a remote-tracking row whose local twin is that branch is blocked the same way, remote-tracking rows are selectable pick targets — picking `origin/x` records a create-branch choice, local `x` from `origin/x`, which send-time provisioning follows with git DWIM semantics: an existing local `x` is reused, a missing one is created from the remote ref; the create form refuses an existing local name, whose DWIM reuse would silently ignore the chosen base). The choice lives in the transient `sessionWorkspaceStore` (per session, never persisted); the session-selector's per-branch "+" gesture creates the session eagerly and presets its choice. The session's FIRST send consumes the choice: `SendMessage(..., workspace)` provisions (or adopts, ADR-082) the managed worktree, persists the binding inside the atomic fresh window and evicts the in-memory session so the task starts in the tree; a failure rejects the send before any state is touched and keeps the choice for a retry. Past the fresh window the binding is immutable — the frontend renders it read-only (`SessionInfo.workspace_binding`). CHAT (No Project) creates eagerly the same way; the no-active-session fallbacks (send/attachment/paste/terminal) auto-create a plain local session.
- **Startup**: backend exposes RPC methods after `Startup()` completes; frontend waits for `backend:ready` event. Vector search methods may return empty results until background ONNX init completes (~1-2s after startup).
- **Teardown**: `Shutdown()` triggers backend cleanup; frontend stops polling and unregisters event listeners. **Close guard**: before any teardown can start, the Wails `OnBeforeClose` hook (`App.ShouldPreventClose`, `desktop/exit_guard.go`) intercepts a quit while sessions have live work (running task or in-flight manual compaction — paused/unfinished tasks are persisted and don't count), shows the window, and emits `app:exit_requested` (each session: `{id, name, compacting, hung}` — `hung` is true only when a **Stop** request has gone unanswered past the backend threshold, rendered as "not responding"; a cooperative pause never sets it); the frontend confirmation modal (`ExitConfirmDialog`) answers via `ConfirmExit`, which arms the exit-confirmed bypass and re-issues the quit so `OnBeforeClose` lets it through into the normal `Shutdown` sequence. Every quit path (window close button, OS quit menu/Cmd+Q, `runtime.Quit` — including the updater's quit) funnels through this single hook on all platforms, which is why the bypass flag is mandatory: without it the confirmed `Quit` would be intercepted again. The updater's quit is deliberately not exempt: `ApplyUpdate`'s graceful quit is intercepted like any other while sessions have live work (the user gets a second confirmation), and the payload's `update_pending` flag makes the modal present restart context — the desktop layer arms the marker when the quit is issued and it self-expires with `core/updater.StagedUpdaterShutdownWait` (plus a small slack), so a cancelled-then-retried quit after the staged updater's window degrades to a plain quit context. A payload that fails frontend validation opens the generic list-less modal variant (with the drop reported via `reportDroppedEvent`) — the quit is already prevented, so an unanswered dialog would leave the app unclosable

## Error Propagation

- **RPC errors**: Go methods return `error`; Wails serializes as `Error` thrown in the TypeScript `Promise` rejection
- **Event errors**: there is no dedicated "event error" channel; failed event emissions are logged and dropped. User-visible execution errors flow through the global `runtime_error` event and the session-scoped `error` event (see [event-catalog.md](event-catalog.md))
- **Startup failures**: if backend `Startup()` panics, Wails shows a native error dialog; if startup completes but services fail, `GetConfig()` still returns a `ConfigResponse` (no error) with `Loaded: false` plus a `ConfigErrors` list, which the frontend uses to display a "Backend unavailable" banner
- **Streaming failures**: streaming uses Wails `EventsEmit` (not SSE); if a task errors mid-stream, `assistant_done` may not fire, so the partial text stays in `chatStore.streamingText` until the terminal handler for `error` / `task_complete` / `task_cancelled` discards it via `clearStreamingText(sessionId)`
- **Panic recovery**: Wails runtime catches Go panics and returns them as RPC errors; c0wrk guards its own asynchronous paths per site rather than through a middleware — `SafeGo` for the startup phases (`backend/startup_phases.go`), `(*App).invokeEventTap` for the web-access event tap (`desktop/app.go`), `runJudgeEvaluation` for the judge goroutine (`backend/judge.go`), `dispatchSafely` for the notification click callback (`desktop/notifications_linux.go`), and the background vector-init / update-check / embedded-install paths
- **Fallback**: a method invoked before its subsystem is wired returns that subsystem's own `… not initialized` error (`session manager not initialized`, `config not initialized`, `project subsystem not initialized`, `application not initialized`, `session store not initialized`, `project store not initialized`, `project manager not initialized`, `terminal manager not initialized`, `review store not initialized`, `orchestrator not initialized`)
- **Vector not ready**: vector search methods invoked before embedder initialization completes return empty results with no error (graceful degradation)

## Type Mapping

Go structs are auto-generated as TypeScript interfaces at:

- `frontend/wailsjs/go/desktop/App.js` — method stubs
- `frontend/wailsjs/go/desktop/App.d.ts` — type declarations

Frontend wraps these in `frontend/src/api/` modules (never imports wailsjs directly from components).

The generated tree also carries `frontend/wailsjs/runtime/` (the Wails event/window shim, re-created by every `wails build`/`wails dev`). Its content never changes, so it is **untracked** (see `.gitignore`); only the `frontend/wailsjs/go/` bindings above are committed — they are the Go ↔ TS contract.

## Wails Binding Regeneration

Bindings are regenerated by:

- `wails build` (production)
- `wails dev` (development with hot-reload)

Adding/removing/renaming a method on `desktop.App` or `backend.FrontendAPI` requires regeneration. Methods on `*FrontendAPILifecycle` (reached through `FrontendAPI.Lifecycle()`) are deliberately NOT bound, which is where the embedded-LLM startup/shutdown hooks live.

## Breaking Change Checklist

- Adding a method to FrontendAPI -> run `wails build` to regenerate bindings -> update `frontend/src/api/` wrapper
- Changing method signature -> regenerate bindings -> update frontend callers
- Changing `ProjectUIStateRequest`/`ProjectUIStateResponse` fields or renaming `SaveProjectUIState` / `GetProjectUIState` aliases -> regenerate bindings -> update `frontend/src/api/projects.ts` RPC probing and `frontend/src/types/guards.ts` shape validators
- Adding new event type -> add Go emitter method -> add TS type + type guard -> add handler in relevant hook
- Changing an `EmbeddedLLMStatus` field or an `embedded_llm:*` payload -> regenerate bindings -> update `frontend/src/types/events.ts` (`EmbeddedLLMStateData` / `EmbeddedLLMInstallProgressData` + their guards) and the event-catalog rows; the state payload structs are hand-written on the frontend (only RPC signatures generate Wails models), so a renamed Go JSON tag silently breaks the UI without a compile error anywhere
- Changing a `SpecsStatusDTO`/`ADRMetaDTO` field (the § Specs shapes) -> update `frontend/src/api/specs.ts` boundary guards + `frontend/src/types/models.ts`, then the panel consumers; the contract is additive-only — a NEW optional field (e.g. ADR-108's `adrs[].date`) must degrade gracefully when absent, and a rename/removal breaks the hand-written guards with no compile error
- Adding an `EmbeddedLLMStatus` field (topology, plan, `reload_required`) or an embedded-LLM tuning DTO/method -> regenerate bindings -> additions must be ADDITIVE only: the hand-written guard `isEmbeddedLLMStatus` (`frontend/src/api/embedded.ts`) checks the presence and typeof of the fields it knows, so a newer backend degrades gracefully and an older payload still validates — renaming or retyping an existing field is the break, appending one is not. Tuning DTO fields must stay nullable (nil = *unset*, a different value from an explicit `auto`), and a tuning editor must send the three-state encoding (`SetEmbeddedLLMTuning`: nil keeps, present replaces, `reset` clears) rather than a whole-section write
- Renaming event -> update both Go emitter AND all frontend subscribers
- Adding a `FrontendAPI` method makes it web-callable automatically (the sidecar dispatches by reflection — no registration step). Before shipping it to the web surface: if it carries a bulk upload payload, size its body cap in `uploadBodyMethods` (`internal/webaccess/dispatch.go` — precedent: `AttachFileContent` → 48 MiB against the backend's own 32 MiB raw cap; the default cap is 1 MiB); if it is a web-transport hazard, add a `deniedMethods` entry with its web-specific reason. Both are pinned by the surface-contract test
- Adding a desktop-only control RPC -> declare it on `*desktop.App`, never on `*backend.FrontendAPI`, when a browser tab must not reach it (the web reflection surface is exactly the FrontendAPI method set); verify with the `desktop/webaccess_test.go` isolation tests
- Changing `WebAccessInfo` fields, a web-access control RPC, or the `web_access` config section -> regenerate bindings -> update `frontend/src/api/webAccess.ts` (the `parseWebAccessInfo` guard rejects the whole read on a core-field violation — the section renders "unavailable" rather than guessing — while the pin fields and the TLS fields tolerate a legacy payload by defaulting to the unconfigured/plain-HTTP shape) and `WebAccessSettings.tsx`; keep payload changes additive for the same hand-written-guard reasons as `EmbeddedLLMStatus`
