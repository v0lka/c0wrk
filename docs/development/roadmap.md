# c0wrk: Долгосрочный роадмап развития

## Текущее состояние (базовая линия, июнь 2026)

c0wrk — десктопный AI coding-агент продакшн-уровня с многослойной архитектурой (desktop → backend → core → sdk), трёхфазной оркестрацией (маршрутизация → планирование → выполнение с рефлексией), 5 LLM-провайдерами (Anthropic, OpenAI, Gemini, LM Studio, OpenAI Responses API), 20+ встроенными инструментами, MCP-шлюзом с поддержкой stdio и HTTP-транспорта, ONNX-based векторным хранилищем с гибридным поиском (вектор + BM25, Reciprocal Rank Fusion, bleve-lexical-индекс), 4 стратегиями управления контекстом (sliding window, summarization, hierarchical, tool output pruning), полноценным PTY-терминалом, DAG-based параллельным выполнением с субагентами-горутинами и развитым React 19-фронтендом с 25+ типами событий и 12 Zustand-хранилищами.

Агентный цикл содержит 5+ circuit breaker'ов, оверлеи промптов под семейства моделей и профили агентов-специалистов (researcher, coder, tester, executor). Реализовано: персистентность фактов в SQLite (уровень задачи), автоматическая инъекция RAG-хинтов перед маршрутизацией/планированием, кэширование промптов для Anthropic (CacheBreak + ephemeral cache control), адаптивный выбор стратегии компактизации по домену, многоуровневая система безопасности (политики инструментов, LLM-судья, regex-блоклист, indirect prompt injection defense через XML-boundary wrapping), skill-система с multi-source discovery и инъекцией в системный промпт, FileCoherenceTracker для детекции кросс-сессионных конфликтов, proxy-поддержка с кастомными CA-сертификатами, model registry с 5-уровневым разрешением (user override → built-in → HuggingFace → LM Studio → heuristic), конфигурируемые reasoning effort по семействам моделей, два режима выполнения (normal/advanced) с UI-тогглом, Plan Review с feedback-driven репланированием (ApprovePlan/RejectPlan), DAG carry-forward при репланировании (сохранение выполненных шагов), StepOutputStore для кросс-шагового доступа к результатам.

Анализ ниже структурирован в виде **треков** (параллельных направлений работ). Внутри каждого трека элементы расположены в рекомендуемом порядке реализации. Для каждого элемента указан текущий статус реализации и планируемый результат.

## Трек 1: Персистентная память и граф знаний

**Текущее состояние**: Факты персистентны на уровне задачи (таблица `task_facts` в SQLite, `PersistentBlackboard.StoreFact()` сохраняет, `RestoreBlackboard()` восстанавливает). Однако нет кросс-сессионного/кросс-проектного поиска фактов, нет базы знаний на уровне проекта, нет понимания архитектуры через граф.

### 1.1 Расширение области видимости фактов до уровня проекта

> **Статус**: частично — персистентность фактов работает, но только в рамках задачи (`task_id`), без project-wide поиска.

- **Исследование**: Оценить FTS5 виртуальную таблицу для полнотекстового поиска по фактам. Бенчмарк FTS5 на типичных объёмах (1K-10K фактов на проект). Оценить миграцию с текущей схемы `task_facts` (JSON-блоб) на нормализованную таблицу с отдельными записями.
- **Реализация**: Расширить таблицу `task_facts` или создать нормализованную `project_facts` (`id, project_id, session_id, task_id, keywords, content, author, created_at`). Добавить `SearchProjectFacts()` для поиска по всем задачам/сессиям в пределах одного проекта. Автоматически инжектировать релевантные факты из предыдущих сессий при старте новой задачи.

### 1.2 Проектная база знаний (структурированные заметки)

> **Статус**: частично — `AGENTS.md` автоматически инжектируется в системный промпт через `core/systemprompt.go`. Однако собственного механизма structured note-taking с чтением/записью/поиском у агента нет.

- **Исследование**: Изучить паттерн «structured note-taking» от Anthropic (агенты ведут `CLAUDE.md`-подобные файлы). Оценить, использовать файловую систему (markdown-файлы) или записи в БД.
- **Реализация**: Добавить инструмент `project_notes` (чтение/запись/поиск по markdown-заметкам, привязанным к проекту, в `~/.c0wrk/projects/{id}/notes/`). Автоматически инжектировать релевантные заметки в системный промпт оркестратора через семантический поиск. Агент пишет ADR (Architecture Decision Records), архитектурные решения, изученные паттерны.

### 1.3 Интеграция графа знаний

> **Статус**: отсутствует — нет tree-sitter, нет AST-based анализа, нет графовых запросов в кодовой базе.

- **Исследование**: Оценить легковесные встроенные графовые хранилища (например, Cayley или таблица отношений в SQLite). Профилировать компромисс графовых запросов vs. плоский FTS5.
- **Реализация**: Построить модуль `CodeGraph`, индексирующий: функция → вызовы, тип → реализации, файл → импорты, модуль → зависимости. Заполнять из AST через tree-sitter (Go, TS, Python первоначально). Предоставить инструмент `query_codebase_graph` для запросов агента типа «что вызывает функцию X?» или «что зависит от модуля Y?».

### 1.4 Кросс-проектное обучение

> **Статус**: отсутствует — факты привязаны к `task_id`, таблица `global_insights` не существует.

- **Исследование**: Какие знания переносятся между проектами? Изучить паттерны: стратегии восстановления после ошибок, паттерны использования инструментов, типичные архитектурные решения.
- **Реализация**: Добавить таблицу `global_insights` (не привязанную к проекту). Агент сохраняет обобщаемые выводы. На новом проекте инжектировать top-N релевантных инсайтов в системный промпт.

### 1.5 Подгрузка файлов в Blackboard

> **Статус**: отсутствует — Blackboard хранит факты через `StoreFact`/`SearchFacts`, но не предоставляет механизма загрузки содержимого файлов для кросс-шагового доступа.

- **Исследование**: Оценить объём данных, целесообразный для хранения в Blackboard (целые файлы vs. фрагменты vs. только метаданные). Профилировать влияние на потребление памяти при загрузке крупных файлов. Сравнить с подходом Cursor (context window включает открытые файлы) и Augment (lazy file resolution).
- **Реализация**: Добавить механизм `LoadFileIntoBlackboard()`, позволяющий агенту загружать содержимое файлов в Blackboard для кросс-шагового доступа. Поддержка ленивой загрузки (содержимое считывается при обращении, а не при добавлении). Инъекция загруженных файлов в контекст executor'а при выполнении шагов, с дедупликацией относительно файлов, уже присутствующих в контексте из tool-вызовов.

## Трек 2: Мультиагентная оркестрация

**Текущее состояние**: DAG-based параллельное выполнение уже реализовано (`FindReadySteps()` + `RunSubAgentsParallel()` с горутинами на каждый независимый шаг). Профили агентов-специалистов определены (`AgentProfile` с ролями researcher/coder/tester/executor, role-specific system prompt suffixes и tool pruning defaults) и планировщик инструктирован назначать их. FileCoherenceTracker отслеживает кросс-сессионные конфликты через сигнатуры файлов. DAG carry-forward при репланировании сохраняет успешно выполненные шаги (`BuildCarryForward()`). StepOutputStore обеспечивает кросс-шаговый доступ к результатам инструментов. Однако нет агента-верификатора (Reflector анализирует сбои, но не проверяет соответствие требованиям), нет дебатов/консенсуса.

### 2.1 Улучшение параллельного выполнения: обнаружение конфликтов и изоляция

> **Статус**: частично — параллельный запуск горутин работает, `FileCoherenceTracker` отслеживает кросс-сессионные конфликты через сигнатуры файлов. Отсутствует: внутришаговое обнаружение конфликтов при записи в один файл из двух параллельных шагов, стратегия разрешения конфликтов.

- **Исследование**: Изучить модель оптимистичной конкурентности Cursor (параллельные чтения, отклонение устаревших записей). Оценить git worktree vs. изоляция в памяти. Профилировать реальную частоту конфликтов в типичных DAG-планах.
- **Реализация**: Добавить обнаружение конфликтов на уровне файлов при завершении шага (два шага модифицируют один файл → промпт на разрешение конфликта или автоматический merge). Рассмотреть git-worktree изоляцию для шагов высокой сложности.

### 2.2 Углубление профилей агентов-специалистов

> **Статус**: частично — `AgentProfile` тип определён в `core/stepconfig.go`, role suffixes и tool pruning defaults настроены, планировщик инструктирован назначать профили. Complexity передаётся от Router через `complexityForStep()` (читает `ComplexityFromContext`, fallback на 3). Однако: профили опциональны и не всегда назначаются; Router не выводит рекомендацию профиля; отсутствуют профили `reviewer` и `documenter`.

- **Исследование**: Собрать метрики реальных сессий: как часто планировщик назначает профили? Улучшается ли результат с профилями vs. без? Какие роли нужны дополнительно (reviewer, documenter)?
- **Реализация**: Расширить Router для рекомендации профилей на основе домена и сложности. Добавить профили `reviewer` и `documenter`. Сделать назначение профилей обязательным для сложности >= 3.

### 2.3 Агент-верификатор (post-execution verification)

> **Статус**: частично — `ToolJudge` существует для безопасности (auto-approve vs. confirm мутирующих операций), `Reflector` анализирует сбои выполнения (root cause, suggested action). Однако: ни один из них не проверяет соответствие результатов исходным требованиям, не запускает компиляцию/тесты, не оценивает полноту.

- **Исследование**: Изучить отдельную модель-судью Cursor и «verification lattice» от Anthropic (детерминистический → семантический → безопасность → агентный → человеческий).
- **Реализация**: После каждого выполнения DAG запускать агент `verifier`, который ревьюит изменения относительно исходного запроса. Проверки: код компилируется, тесты проходят, требования выполнены, нет регрессий. Отчёт передаётся как рефлексия для повтора при обнаружении проблем.

### 2.4 Режим дебатов для сложных решений

> **Статус**: отсутствует — Router возвращает одно решение, Planner генерирует один план, Orchestrator выполняет один план.

- **Исследование**: Оценить эффективность мульти-предложений с выбором (подход Augment «exploit non-determinism»). Бенчмарк: превосходит ли запуск 3 параллельных реализаций с выбором однопроходное выполнение?
- **Реализация**: Для задач сложности 4-5 планировщик генерирует 2-3 альтернативных подхода. Каждый выполняется изолированно (git worktree или в памяти). Агент-верификатор выбирает лучший результат. Стоимость: 3x вычислений только для задач максимальной сложности.

### 2.5 Режим исследования с гипотезами

> **Статус**: отсутствует — агент выполняет задачи последовательно (route → plan → execute), нет режима итеративного исследования с формированием и проверкой гипотез.

- **Исследование**: Изучить паттерны research-агентов (итеративный поиск → гипотеза → верификация → уточнение). Оценить интеграцию с текущим циклом Router → Planner → Executor. Сопоставить с подходом ReAct и Tree-of-Thought. Проанализировать, как гипотезы представлены в существующих фреймворках (LangGraph, AutoGen) и какие типы верификации применимы (детерминистические: тесты/линт, семантические: LLM-judge).
- **Реализация**: Добавить режим `research`, в котором агент формулирует гипотезы, проверяет их через инструменты (поиск, чтение файлов, запуск кода), уточняет или отбрасывает на основе результатов. Хранить гипотезы в Blackboard со статусами (proposed/confirmed/refuted). Интегрировать с Треком 1 (персистентные гипотезы как тип фактов) и Треком 4 (адаптивная стратегия компактизации для исследований с большим контекстом).

## Трек 3: Конвейер автоматической верификации

**Текущее состояние**: Агент может запускать тесты/линтер через `bash_exec`, но только если явно проинструктирован (в промпте или пользователем). Нет автоматического запуска верификации после изменений кода. Нет автоопределения build/test/lint команд проекта. Нет генерации тестов. Нет обнаружения регрессий.

### 3.1 Детерминистические гейты верификации

> **Статус**: отсутствует — нет `ProjectDetector`, нет автоопределения команд, нет автоматического post-modification конвейера.

- **Исследование**: Проанализировать типичные структуры проектов для автоопределения команд сборки/линтинга/тестирования (Makefile, package.json, Cargo.toml, pyproject.toml). Сопоставить со стандартными гейтами.
- **Реализация**: Добавить `ProjectDetector` в `backend/`, обнаруживающий доступные команды верификации при открытии проекта. Сохранять в конфигурации проекта. После каждой модификации кода агентом автоматически запускать конвейер: `lint → typecheck → test`. Если любой гейт падает, инжектировать результат в контекст агента как tool_result и дать ему возможность самокоррекции.

### 3.2 Целевая генерация тестов

> **Статус**: отсутствует.

- **Исследование**: Изучить R-MCTS подходы для генерации тестов (статья ExACT). Оценить извлечение сигнатур функций через tree-sitter для скаффолдинга тестов.
- **Реализация**: Добавить инструмент `generate_tests`, который: (1) извлекает сигнатуры функций через tree-sitter, (2) генерирует тест-кейсы с помощью LLM с контекстом функции + существующими паттернами тестов, (3) запускает тесты, (4) итерирует при неудачах. Фокус первоначально на Go (table-driven) и TypeScript (vitest/jest).

### 3.3 Обнаружение регрессий

> **Статус**: отсутствует.

- **Исследование**: Оценить стратегии обнаружения регрессий: snapshot-тестирование, сравнение golden-файлов, регрессия бенчмарков (пороги p95 латентности).
- **Реализация**: До и после изменений агента фиксировать: результаты тестов, показатели бенчмарков, размер бинарника, покрытие типами. Вычислять diff и сообщать о регрессиях. Блокировать `finish`, если обнаружена регрессия без явного override от пользователя.

### 3.4 Интеграция сканирования безопасности

> **Статус**: отсутствует.

- **Исследование**: Оценить встраиваемые SAST-инструменты (правила semgrep, gosec для Go, eslint-plugin-security для TS). Сравнить подход MCP-сервера vs. встроенный инструмент.
- **Реализация**: Добавить инструмент `security_scan` (запускает сконфигурированный сканер на рабочем пространстве). Интегрировать в конвейер верификации. Агент получает результаты сканирования и обязан устранить находки high/critical до завершения.

## Трек 4: Развитие контекстной инженерии

**Текущее состояние**: Реализовано:

- **Tool output pruning** (`toolOutputPruning`): конфигурируемый механизм очистки старых tool-результатов с заменой на placeholder-текст, защитой определённых инструментов (`store_fact`, `search_facts`), порогом активации (50% заполнения контекста), настройкой `keepLastN: 3`.
- **Адаптивный выбор стратегии**: `applyCompactionStrategy()` в `core/router.go` выбирает стратегию по домену и сложности (code → sliding_window, research → summarization, mixed с complexity >= 4 → hierarchical). Complexity передаётся от Router через `complexityForStep()` (читает `ComplexityFromContext`, fallback на 3).
- **Auto-RAG**: `injectVectorSearchHints()` в `core/orchestrator.go` автоматически запускает семантический поиск перед маршрутизацией/планированием, инжектируя top-5 релевантных файлов как секцию «Relevant Project Files» в системный промпт.
- **Prompt caching**: `CacheBreakMarker` инфраструктура в `sdk/prompt/builder.go`, Anthropic provider применяет `CacheControl{Type: Ephemeral}` ко всем стабильным частям системного промпта.

### 4.1 Эволюция tool output pruning до полноценной стратегии clearing

> **Статус**: частично — `toolOutputPruning` работает (placeholder текст, protected tools, keepLastN, threshold). Отличие от целевого состояния: текущая реализация работает как прунинг старых результатов, а не как хирургическая замена с сохранением `tool_use` записей для переиспользования.

- **Исследование**: Измерить эффективность текущего pruning: сколько токенов экономится, как часто агент повторно запрашивает очищенные данные? Сравнить текущий подход (полное удаление tool_result) с подходом Anthropic (сохранение tool_use + placeholder в tool_result).
- **Реализация**: Рефакторить pruning для сохранения `tool_use` записей (агент видит, что он запрашивал, но не видит результат). Добавить интеллектуальный placeholder с указанием типа очищенных данных («файл X был прочитан, результат очищен — перечитайте при необходимости»). Добавить метрики: процент повторных запросов после очистки.

### 4.2 Доработка адаптивного выбора стратегии

> **Статус**: частично — `applyCompactionStrategy()` выбирает по домену, complexity передаётся от Router (не захардкожена). Нет динамической адаптации к runtime-характеристикам задачи.

- **Исследование**: Профилировать, какая стратегия компактизации лучше работает для каких типов задач. Собрать метрики из реальных сессий: соотношение tool-вызовов, средний размер tool-результатов, частота переиспользования ранних результатов.
- **Реализация**: Добавить `CompactionAnalyzer`, который может переключать стратегию на лету при обнаружении паттернов (например, много мелких tool-вызовов → tool_result_clearing, мало больших → hierarchical).

### 4.3 Углубление RAG-инъекции

> **Статус**: частично — `injectVectorSearchHints()` инжектирует top-5 файловых путей с аннотацией перед маршрутизацией. Планировщик имеет доступ к `semantic_search` как инструменту Tier 1. Однако: инжектируются только пути файлов, а не фрагменты кода; инжекция происходит только перед routing, не перед каждым ходом executor'а; нет дедупликации с уже прочитанными файлами.

- **Исследование**: Бенчмарк влияния на quality: инъекция путей vs. инъекция фрагментов кода. Оценить overhead дополнительного семантического поиска перед каждым ходом executor'а.
- **Реализация**: Расширить `injectVectorSearchHints()` для инъекции фрагментов кода (первые N строк релевантных чанков), а не только путей. Добавить опциональную инъекцию перед ходами executor'а для задач высокой сложности. Дедуплицировать относительно файлов, уже присутствующих в контексте из tool-вызовов.

> **Статус**: частично — Reflector умеет анализировать acceptance criteria (упоминается в промпте), но критерии берутся из описания шагов плана, а не из внешней спецификации.

- **Исследование**: Изучить, как критерии приёмки могут быть автоматически верифицированы (некоторые тестируемы, некоторые требуют суждения LLM).
- **Реализация**: После выполнения агент-верификатор проверяет каждое требование спецификации относительно фактических изменений. Детерминистические проверки (тесты проходят, линт чист) + семантические проверки (LLM ревьюит, выполнено ли требование). Отчёт: требование-по-требованию pass/fail.

## Трек 10: Усиление безопасности и governance (OWASP ASI Top 10)

**Текущее состояние**: Модель безопасности включает: 3-уровневые политики инструментов (`always_allow` / `always_deny` / `user_confirm`), LLM-based `ToolJudge` для автоматической оценки безопасности мутирующих операций с кэшем вердиктов, regex-блоклист для bash_exec, indirect prompt injection defense (`WrapUntrustedContent` с XML boundary в `sdk/security/wrap.go`). 5+ circuit breaker'ов (repeat, truncation, parse-error, fruitless, same-tool-loop) предотвращают runaway loops. Проведён аудит соответствия [OWASP Top 10 for Agentic Applications](https://genai.owasp.org) (ASI, 2026): **средневзвешенное покрытие ≈41%**. Нижеперечисленные работы нацелены на закрытие целесообразных пробелов с учётом single-agent desktop-архитектуры проекта. В скобках указаны соответствующие разделы OWASP ASI.

### 10.1 Песочница выполнения

> **Статус**: отсутствует — только regex blacklist + timeout, без контейнеризации или process isolation.

- **Исследование**: Оценить варианты песочницы: Docker-контейнеры, macOS sandbox-exec, nsjail. Профилировать влияние на производительность vs. прирост безопасности.
- **Реализация**: Добавить опциональный sandbox-режим для bash_exec: команды выполняются в изолированном контейнере/песочнице с примонтированным рабочим пространством (read-only или ограниченная запись). Исходящий сетевой трафик заблокирован по умолчанию. Включение через секцию security в config.yaml.

### 10.2 Полноценный аудит-трейл

> **Статус**: отсутствует — логирование через slog (in-process), без персистентного аудит-лога.

- **Исследование**: Спроектировать схему аудита: какие события логировать (все tool-вызовы, все LLM-запросы, все решения пользователя), политика хранения, формат экспорта.
- **Реализация**: Добавить SQLite-таблицу `audit_log`, фиксирующую каждый tool-вызов (tool, args, result_hash, policy_decision, user_verdict, timestamp). Добавить API `export_audit` для compliance-ревью. UI: просмотрщик аудит-лога в настройках.

### 10.3 Policy-as-Code

> **Статус**: отсутствует — текущая политика: enum (3 уровня) + regex blacklist. Нет OPA, Cedar или аналогов.

- **Исследование**: Изучить OPA (Open Policy Agent) и Cedar для оценки политик. Оценить: встроить движок политик или использовать простой rule engine.
- **Реализация**: Заменить текущий regex-based блоклист на движок policy-as-code. Политики определяют: какие инструменты могут обращаться к каким путям, какие сетевые назначения разрешены, какие модификации файлов допустимы. Политики коммитятся в репозиторий как `.c0wrk/policies/`.

### 10.4 Обнаружение секретов

> **Статус**: отсутствует — write_file и edit_file не сканируют содержимое на секреты.

- **Исследование**: Оценить встраиваемые сканеры секретов (правила gitleaks, паттерны trufflehog). Изучить: должен ли агент отказываться коммитить файлы с секретами?
- **Реализация**: Добавить pre-write сканирование секретов: перед `write_file` или `edit_file` сканировать контент на API-ключи, токены, пароли. При обнаружении — предупредить пользователя и потребовать явный override. Интегрировать с аудит-трейлом.

### 10.5 Гардрейлы на базе детекторов dunetrace

> **Статус**: отсутствует — текущая безопасность основана на статических политиках (enum + regex blacklist + LLM-судья), нет динамических детекторов аномалий в поведении агента.

- **Исследование**: Изучить фреймворк [dunetrace](https://github.com/dunetrace/dunetrace) и его детекторы (prompt injection, tool misuse, data exfiltration, jailbreak и др.). Оценить совместимость с текущим конвейером выполнения агента. Профилировать overhead добавления runtime-детекции к каждому tool-вызову. Сравнить с существующим `ToolJudge`: пересечение и дополнение.
- **Реализация**: Интегрировать детекторы dunetrace как гардрейлы в цикл выполнения агента. Каждый tool-вызов проходит через детекторы перед выполнением. При срабатывании — блокировка вызова, логирование инцидента, уведомление пользователя. Конфигурируемые пороги чувствительности через секцию `security:` в config.yaml. Интеграция с аудит-трейлом (10.2).

### 10.6 Egress control и network sandboxing (ASI02, ASI05)

> **Статус**: отсутствует — bash_exec и web_fetch не имеют ограничений исходящего сетевого трафика, что позволяет агенту эксфильтровать данные через DNS/HTTP при компрометации.

- **Исследование**: Оценить механизмы egress filtering на macOS (pf firewall, network extension, sandbox-exec network deny). Профилировать легитимные сетевые паттерны агента для построения минимального allowlist.
- **Реализация**: Внедрить egress allowlist для bash_exec (deny all, allow только явно указанные домены/порты). Добавить секцию `security.egress_control` в config.yaml с конфигурацией разрешённых назначений для каждого инструмента. Сетевая изоляция активируется атомарно с песочницей (10.1). Интегрировать с детекторами dunetrace (10.5) для обнаружения попыток обхода.

### 10.7 Supply chain pinning и integrity verification (ASI04)

> **Статус**: отсутствует — промпты вкомпилированы через `go:embed`, но нет content hash pinning; конфигурация MCP-серверов не верифицируется криптографически; нет kill switch для скомпрометированных инструментов.

- **Исследование**: Оценить встраивание контрольных сумм (SHA-256) для промптов и конфигураций в бинарник на этапе сборки. Изучить подходы к emergency revocation (мгновенное отключение инструментов без перезапуска).
- **Реализация**: Добавить `content_hash` для каждого встроенного промпта, проверяемый при старте. Верифицировать хеши конфигураций MCP-серверов при подключении (pin по command+args+transport). Добавить API `RevokeMCPTool(serverName, toolName)` — kill switch на уровне Gateway для экстренного отключения инструментов без перезапуска агента.

### 10.8 Memory & context integrity guardrails (ASI06)

> **Статус**: отсутствует — blackboard и векторный индекс не валидируют контент перед записью; нет предотвращения «bootstrap poisoning» (повторное засасывание собственных выводов агента в доверенную память); нет expiration/TTL для unverified memory entries.

- **Исследование**: Оценить lightweight scanning контента перед сохранением в Blackboard (injection pattern detection, structural validation). Изучить механизмы TTL-based expiration для векторных чанков.
- **Реализация**: Добавить `ValidateMemoryWrite()` — проверка контента перед `StoreFact` и векторной индексацией на наличие prompt injection-паттернов и структурную валидность. Внедрить механизм предотвращения self-reingestion: помечать собственные outputs агента и исключать их из автоматической индексации. Добавить `memory_ttl` в конфигурацию для автоматической экспирации unverified векторных чанков.

### 10.9 Kill-switch и blast-radius guardrails (ASI08, ASI10)

> **Статус**: частично — 5+ circuit breaker'ов предотвращают runaway loops (repeat, truncation, parse-error, fruitless, same-tool-loop), step limit (max_react_steps=50) и retry cap (2) ограничивают масштаб. Отсутствует: явный kill-switch для принудительной остановки executor'а, quotas на количество tool-вызовов за сессию, механизм quarantine подозрительных agent-компонентов.

- **Исследование**: Спроектировать kill-switch, интегрированный с текущим circuit breaker — общий механизм принудительной остановки, доступный и пользователю (кнопка в UI), и внутренним детекторам. Оценить пороги для per-session quotas (tool calls, network bytes, file modifications).
- **Реализация**: Добавить `SessionKillSwitch` в `Orchestrator` — атомарный флаг, вызывающий немедленное завершение всех горутин шага и предотвращающий запуск новых. Внедрить квоты: `max_tool_calls_per_session`, `max_file_modifications`, `max_network_bytes`. При превышении — уведомление пользователя с опцией override. Пользовательская кнопка «Force Stop» в UI, интегрированная с kill-switch.

### 10.10 Human-agent trust safeguards (ASI09)

> **Статус**: отсутствует — нет confidence cues в UI (low-certainty индикаторов), нет plan-divergence detection (сравнение plan vs. actual), нет визуальных гардрейлов для risk-aware interaction.

- **Исследование**: Изучить подходы к confidence calibration в agentic UI (цветовое кодирование уверенности, явные предупреждения о потенциально опасных действиях). Спроектировать divergence detection на основе сравнения изначального плана с фактическими шагами.
- **Реализация**: Внедрить `PlanDivergenceDetector` в конвейер Reflector'а: перед каждым шагом сравнивать запланированные действия с фактическими, алертить при отклонении. Добавить confidence cues в frontend: маркировка low-certainty ответов (визуальный индикатор «⚠️ Low confidence»), цветовое кодирование риска для pending confirmations. Интегрировать с ToolJudge reasoning для отображения обоснования вердикта.

### 10.11 Goal intent validation (ASI01)

> **Статус**: отсутствует — нет сверки intent агента с изначальным запросом пользователя перед выполнением goal-changing действий.

- **Исследование**: Оценить lightweight intent validation: сравнение embedding текущей цели с embedding изначального запроса пользователя + сравнение routing domain до и после. Изучить пороги расхождения для алертинга.
- **Реализация**: Добавить `ValidateGoalIntent()` в `Orchestrator.HandleMessage()`: перед выполнением плана вычислять similarity между исходным запросом и текущим routing domain. При падении similarity ниже порога — запрашивать подтверждение пользователя. Интегрировать с kill-switch (10.9) для автоматической блокировки при критическом расхождении.

### 10.12 MCP transport security hardening (ASI04, ASI07)

> **Статус**: отсутствует — MCP HTTP transport не использует mTLS, нет message integrity verification, нет typo-squatting detection для имён MCP-инструментов.

- **Исследование**: Оценить внедрение mTLS для MCP HTTP-транспорта (сертификаты клиента и сервера). Изучить HMAC-based integrity для MCP stdio-транспорта.
- **Реализация**: Добавить опциональный mTLS для MCP HTTP-серверов через секцию `mcp.servers.<name>.tls` в config.yaml. Внедрить `ToolNameValidator` — проверка имён MCP-инструментов на typo-squatting (Levenshtein distance между registered names, алерт при подозрительной близости). Интегрировать с kill switch (10.7) для блокировки подозрительных инструментов.

### 10.13 Behavioral drift detection (ASI08, ASI10)

> **Статус**: отсутствует — circuit breaker детектирует повторы и fruitless calls, но нет долгосрочного мониторинга дрейфа поведения агента (постепенное изменение паттернов tool usage, token consumption, success rate).

- **Исследование**: Определить baseline-метрики поведения агента (распределение tool-вызовов, средний tokens/step, частота retry) и пороги для алертинга. Изучить lightweight anomaly detection (статистические методы — Z-score, moving average).
- **Реализация**: Добавить `BehavioralBaseline` в `SessionManager`: персистентное хранение агрегированных метрик по проекту (скользящее среднее tool calls/task, token efficiency, step success rate). `DriftDetector` сравнивает текущую сессию с baseline и алертит при значимых отклонениях. Интегрировать с аудит-трейлом (10.2).

### 10.14 Content provenance & audit trail hardening (ASI06, ASI08, ASI09)

> **Статус**: отсутствует — нет source attribution для данных в контексте (какой инструмент и когда произвёл содержимое), нет tamper-evident logging.

- **Исследование**: Спроектировать схему provenance metadata для tool results (source tool, timestamp, content hash). Оценить overhead хранения HMAC-подписей для audit log.
- **Реализация**: Добавить `ProvenanceMetadata` к каждому `ToolResult` (tool_name, invocation_id, timestamp, content_sha256). Инжектировать provenance в контекстное окно вместе с контентом. Добавить HMAC-подписи для записей `audit_log` (10.2) с ключом, привязанным к сессии — обеспечение non-repudiation для аудит-трейла.

Адаптировать tree-sitter grammar для Python. Расширить `generate_tests` (3.2) для поддержки pytest/unittest. Добавить `ProjectDetector` (3.1) для Python-проектов.

- **Реализация**: Добавить `LanguageDetector` в `ProjectDetector` (3.1), определяющий основной язык/фреймворк проекта. Генерировать языково-специфичный `AGENTS.md` с командами сборки/тестирования/линта. Адаптировать профили инструментов под язык (например, для Rust — cargo-команды, для Python — pip/poetry/pytest).

# c0wrk: Долгосрочный роадмап развития

## Текущее состояние (базовая линия, июнь 2026)

c0wrk — десктопный AI coding-агент продакшн-уровня с многослойной архитектурой (desktop → backend → core → sdk), трёхфазной оркестрацией (маршрутизация → планирование → выполнение с рефлексией), 5 LLM-провайдерами (Anthropic, OpenAI, Gemini, LM Studio, OpenAI Responses API), 20+ встроенными инструментами, MCP-шлюзом с поддержкой stdio и HTTP-транспорта, ONNX-based векторным хранилищем с гибридным поиском (вектор + BM25, Reciprocal Rank Fusion, bleve-lexical-индекс), 4 стратегиями управления контекстом (sliding window, summarization, hierarchical, tool output pruning), полноценным PTY-терминалом, DAG-based параллельным выполнением с субагентами-горутинами и развитым React 19-фронтендом с 25+ типами событий и 12 Zustand-хранилищами.

Агентный цикл содержит 5+ circuit breaker'ов, оверлеи промптов под семейства моделей и профили агентов-специалистов (researcher, coder, tester, executor). Реализовано: персистентность фактов в SQLite (уровень задачи), автоматическая инъекция RAG-хинтов перед маршрутизацией/планированием, кэширование промптов для Anthropic (CacheBreak + ephemeral cache control), адаптивный выбор стратегии компактизации по домену, многоуровневая система безопасности (политики инструментов, LLM-судья, regex-блоклист, indirect prompt injection defense через XML-boundary wrapping), skill-система с multi-source discovery и инъекцией в системный промпт, FileCoherenceTracker для детекции кросс-сессионных конфликтов, proxy-поддержка с кастомными CA-сертификатами, model registry с 5-уровневым разрешением (user override → built-in → HuggingFace → LM Studio → heuristic), конфигурируемые reasoning effort по семействам моделей, два режима выполнения (normal/advanced) с UI-тогглом.

Анализ ниже структурирован в виде **треков** (параллельных направлений работ). Внутри каждого трека элементы расположены в рекомендуемом порядке реализации. Для каждого элемента указан текущий статус реализации, исследовательский компонент и результат реализации.

## Трек 1: Персистентная память и граф знаний

**Текущее состояние**: Факты персистентны на уровне задачи (таблица `task_facts` в SQLite, `PersistentBlackboard.StoreFact()` сохраняет, `RestoreBlackboard()` восстанавливает). ### 1.1 Расширение области видимости фактов до уровня проекта

> **Статус**: частично реализовано — персистентность фактов работает, но только в рамках задачи (`task_id`), без project-wide поиска.

- **Исследование**: Оценить FTS5 виртуальную таблицу для полнотекстового поиска по фактам. Бенчмарк FTS5 на типичных объёмах (1K-10K фактов на проект). Оценить миграцию с текущей схемы `task_facts` (JSON-блоб) на нормализованную таблицу с отдельными записями.
- **Реализация**: Расширить таблицу `task_facts` или создать нормализованную `project_facts` (`id, project_id, session_id, task_id, keywords, content, author, created_at`). Добавить `SearchProjectFacts()` для поиска по всем задачам/сессиям в пределах одного проекта. Автоматически инжектировать релевантные факты из предыдущих сессий при старте новой задачи.

### 1.2 Проектная база знаний (структурированные заметки)

Автоматически инжектировать релевантные заметки в системный промпт оркестратора через семантический поиск. Агент пишет ADR (Architecture Decision Records), архитектурные решения, изученные паттерны.

## Трек 2: Мультиагентная оркестрация

**Текущее состояние**: DAG-based параллельное выполнение уже реализовано (`FindReadySteps()` + `RunSubAgentsParallel()` с горутинами на каждый независимый шаг). Профили агентов-специалистов определены (`AgentProfile` с ролями researcher/coder/tester/executor, role-specific system prompt suffixes и tool pruning defaults) и планировщик инструктирован назначать их. FileCoherenceTracker отслеживает кросс-сессионные конфликты через сигнатуры файлов. Однако нет агента-верификатора (Reflector анализирует сбои, но не проверяет соответствие требованиям), нет дебатов/консенсуса.

### 2.1 Улучшение параллельного выполнения: обнаружение конфликтов и изоляция

> **Статус**: частично реализовано — параллельный запуск горутин работает, `FileCoherenceTracker` отслеживает кросс-сессионные конфликты через сигнатуры файлов. Отсутствует: внутришаговое обнаружение конфликтов при записи в один файл из двух параллельных шагов, стратегия разрешения конфликтов.

- **Исследование**: Изучить модель оптимистичной конкурентности Cursor (параллельные чтения, отклонение устаревших записей). Оценить git worktree vs. изоляция в памяти. Профилировать реальную частоту конфликтов в типичных DAG-планах.
- **Реализация**: Добавить обнаружение конфликтов на уровне файлов при завершении шага (два шага модифицируют один файл → промпт на разрешение конфликта или автоматический merge). Рассмотреть git-worktree изоляцию для шагов высокой сложности.

### 2.2 Углубление профилей агентов-специалистов

> **Статус**: частично реализовано — `AgentProfile` тип определён в `core/types.go`, role suffixes и tool pruning defaults настроены в `core/stepconfig.go`, планировщик инструктирован в `core/planner.go` (строка 73: «Assign specialized profiles when it adds clear value»). Однако: профили опциональны и не всегда назначаются; Router не выводит рекомендацию профиля; сложность в `applyCompactionStrategy` захардкожена на 3.

- **Исследование**: Собрать метрики реальных сессий: как часто планировщик назначает профили? Улучшается ли результат с профилями vs. без? Какие роли нужны дополнительно (reviewer, documenter)?
- **Реализация**: Расширить Router для рекомендации профилей на основе домена и сложности. Добавить профили `reviewer` и `documenter`. Передавать реальную сложность (от Router) в `applyCompactionStrategy()` вместо захардкоженной 3. Сделать назначение профилей обязательным для сложности >= 3.

### 2.3 Агент-верификатор (post-execution verification)

> **Статус**: частично реализовано — `ToolJudge` существует для безопасности (auto-approve vs. confirm мутирующих операций), `Reflector` анализирует сбои выполнения (root cause, suggested action). Однако: ни один из них не проверяет соответствие результатов исходным требованиям, не запускает компиляцию/тесты, не оценивает полноту.

- **Исследование**: Изучить отдельную модель-судью Cursor и «verification lattice» от Anthropic (детерминистический → семантический → безопасность → агентный → человеческий).
- **Реализация**: После каждого выполнения DAG запускать агент `verifier`, который ревьюит изменения относительно исходного запроса. Проверки: код компилируется, тесты проходят, требования выполнены, нет регрессий. Отчёт передаётся как рефлексия для повтора при обнаружении проблем.

### 2.4 Режим дебатов для сложных решений

> **Статус**: отсутствует — Router возвращает одно решение, Planner генерирует один план, Orchestrator выполняет один план.

- **Исследование**: Оценить эффективность мульти-предложений с выбором (подход Augment «exploit non-determinism»). Бенчмарк: превосходит ли запуск 3 параллельных реализаций с выбором однопроходное выполнение?
- **Реализация**: Для задач сложности 4-5 планировщик генерирует 2-3 альтернативных подхода. Каждый выполняется изолированно (git worktree или в памяти). Агент-верификатор выбирает лучший результат. Стоимость: 3x вычислений только для задач максимальной сложности.

### 2.5 Режим исследования с гипотезами

> **Статус**: отсутствует — агент выполняет задачи последовательно (route → plan → execute), нет режима итеративного исследования с формированием и проверкой гипотез.

- **Исследование**: Изучить паттерны research-агентов (итеративный поиск → гипотеза → верификация → уточнение). Оценить интеграцию с текущим циклом Router → Planner → Executor. Сопоставить с подходом ReAct и Tree-of-Thought. Проанализировать, как гипотезы представлены в существующих фреймворках (LangGraph, AutoGen) и какие типы верификации применимы (детерминистические: тесты/линт, семантические: LLM-judge).
- **Реализация**: Добавить режим `research`, в котором агент формулирует гипотезы, проверяет их через инструменты (поиск, чтение файлов, запуск кода), уточняет или отбрасывает на основе результатов. Хранить гипотезы в Blackboard со статусами (proposed/confirmed/refuted). Интегрировать с Треком 1 (персистентные гипотезы как тип фактов) и Треком 4 (адаптивная стратегия компактизации для исследований с большим контекстом).

## Трек 4: Развитие контекстной инженерии

**Текущее состояние**: Реализовано больше, чем предполагалось изначально:

- **Tool output pruning** (`toolOutputPruning`): конфигурируемый механизм очистки старых tool-результатов с заменой на placeholder-текст, защитой определённых инструментов (`store_fact`, `search_facts`), порогом активации (50% заполнения контекста), настройкой `keepLastN: 3`.
- **Адаптивный выбор стратегии**: `applyCompactionStrategy()` в `core/router.go` выбирает стратегию по домену и сложности (code → sliding_window, research → summarization, mixed с complexity >= 4 → hierarchical). Однако complexity захардкожена на 3 при применении к шагам.
- **Auto-RAG**: `injectVectorSearchHints()` в `core/orchestrator.go` автоматически запускает семантический поиск перед маршрутизацией/планированием, инжектируя top-5 релевантных файлов как секцию «Relevant Project Files» в системный промпт.
- **Prompt caching**: `CacheBreakMarker` инфраструктура в `sdk/prompt/builder.go`, Anthropic provider применяет `CacheControl{Type: Ephemeral}` ко всем стабильным частям системного промпта.

### 4.1 Эволюция tool output pruning до полноценной стратегии clearing

> **Статус**: частично реализовано — `toolOutputPruning` работает (placeholder текст, protected tools, keepLastN, threshold). Отличие от целевого состояния: текущая реализация работает как прунинг старых результатов, а не как хирургическая замена с сохранением `tool_use` записей для переиспользования.

- **Исследование**: Измерить эффективность текущего pruning: сколько токенов экономится, как часто агент повторно запрашивает очищенные данные? Сравнить текущий подход (полное удаление tool_result) с подходом Anthropic (сохранение tool_use + placeholder в tool_result).
- **Реализация**: Рефакторить pruning для сохранения `tool_use` записей (агент видит, что он запрашивал, но не видит результат). Добавить интеллектуальный placeholder с указанием типа очищенных данных («файл X был прочитан, результат очищен — перечитайте при необходимости»). Добавить метрики: процент повторных запросов после очистки.

### 4.2 Доработка адаптивного выбора стратегии

> **Статус**: частично реализовано — `applyCompactionStrategy()` выбирает по домену, но complexity захардкожена на 3 при конфигурации шагов. Нет динамической адаптации к runtime-характеристикам задачи.

- **Исследование**: Профилировать, какая стратегия компактизации лучше работает для каких типов задач. Собрать метрики из реальных сессий: соотношение tool-вызовов, средний размер tool-результатов, частота переиспользования ранних результатов.
- **Реализация**: Передавать реальную сложность от Router в `coreStepConfigurator` вместо захардкоженной 3. Добавить `CompactionAnalyzer`, который может переключать стратегию на лету при обнаружении паттернов (например, много мелких tool-вызовов → tool_result_clearing, мало больших → hierarchical).

### 4.3 Углубление RAG-инъекции

> **Статус**: частично реализовано — `injectVectorSearchHints()` инжектирует top-5 файловых путей с аннотацией перед маршрутизацией. Планировщик имеет доступ к `semantic_search` как инструменту Tier 1. Однако: инжектируются только пути файлов, а не фрагменты кода; инжекция происходит только перед routing, не перед каждым ходом executor'а; нет дедупликации с уже прочитанными файлами.

- **Исследование**: Бенчмарк влияния на quality: инъекция путей vs. инъекция фрагментов кода. Оценить overhead дополнительного семантического поиска перед каждым ходом executor'а.
- **Реализация**: Расширить `injectVectorSearchHints()` для инъекции фрагментов кода (первые N строк релевантных чанков), а не только путей. Добавить опциональную инъекцию перед ходами executor'а для задач высокой сложности. Дедуплицировать относительно файлов, уже присутствующих в контексте из tool-вызовов.

### 4.4 Расширение prompt caching на другие провайдеры

> **Статус**: частично реализовано — CacheBreakMarker инфраструктура работает, Anthropic provider применяет ephemeral cache control к стабильным частям. Не реализовано для Gemini, OpenAI.

- **Исследование**: Профилировать процент попаданий в кэш для Anthropic. Изучить механизмы кэширования Gemini (context caching API) и OpenAI (server-side automatic caching). Измерить экономию стоимости.
- **Реализация**: Адаптировать CacheBreak для Gemini provider (context caching API). Для OpenAI-compatible провайдеров оценить, даёт ли стабильность порядка системных секций неявное кэширование. Добавить метрику `cache_hit_rate` в сессионную статистику.

## Трек 10: Усиление безопасности и governance (OWASP ASI Top 10)

Проведён аудит соответствия [OWASP Top 10 for Agentic Applications](https://genai.owasp.org) (ASI, 2026): **средневзвешенное покрытие ≈41%**. Нижеперечисленные работы нацелены на закрытие целесообразных пробелов с учётом single-agent desktop-архитектуры проекта. В скобках указаны соответствующие разделы OWASP ASI.

### 10.1 Песочница выполнения

> **Статус**: отсутствует — только regex blacklist + timeout, без контейнеризации или process isolation.

- **Исследование**: Оценить варианты песочницы: Docker-контейнеры, macOS sandbox-exec, nsjail. Профилировать влияние на производительность vs. прирост безопасности.
- **Реализация**: Добавить опциональный sandbox-режим для bash_exec: команды выполняются в изолированном контейнере/песочнице с примонтированным рабочим пространством (read-only или ограниченная запись). Исходящий сетевой трафик заблокирован по умолчанию. Включение через секцию security в config.yaml.

### 10.8 Memory & context integrity guardrails (ASI06)

> **Статус**: отсутствует — blackboard и векторный индекс не валидируют контент перед записью; нет предотвращения «bootstrap poisoning» (повторное засасывание собственных выводов агента в доверенную память); нет expiration/TTL для unverified memory entries.

Отсутствует: явный kill-switch для принудительной остановки executor'а, quotas на количество tool-вызовов за сессию, механизм quarantine подозрительных agent-компонентов.

- **Исследование**: Спроектировать kill-switch, интегрированный с текущим circuit breaker — общий механизм принудительной остановки, доступный и пользователю (кнопка в UI), и внутренним детекторам. Оценить пороги для per-session quotas (tool calls, network bytes, file modifications).
- **Реализация**: Добавить `SessionKillSwitch` в `Orchestrator` — атомарный флаг, вызывающий немедленное завершение всех горутин шага и предотвращающий запуск новых. Внедрить квоты: `max_tool_calls_per_session`, `max_file_modifications`, `max_network_bytes`. При превышении — уведомление пользователя с опцией override. Пользовательская кнопка «Force Stop» в UI, интегрированная с kill-switch.

### 10.10 Human-agent trust safeguards (ASI09)

> **Статус**: отсутствует — нет confidence cues в UI (low-certainty индикаторов), нет plan-divergence detection (сравнение plan vs. actual), нет визуальных гардрейлов для risk-aware interaction.

- **Исследование**: Изучить подходы к confidence calibration в agentic UI (цветовое кодирование уверенности, явные предупреждения о потенциально опасных действиях). Спроектировать divergence detection на основе сравнения изначального плана с фактическими шагами.
- **Реализация**: Внедрить `PlanDivergenceDetector` в конвейер Reflector'а: перед каждым шагом сравнивать запланированные действия с фактическими, алертить при отклонении. Добавить confidence cues в frontend: маркировка low-certainty ответов (визуальный индикатор «⚠️ Low confidence»), цветовое кодирование риска для pending confirmations. Интегрировать с ToolJudge reasoning для отображения обоснования вердикта.

### 10.11 Goal intent validation (ASI01)

> **Статус**: отсутствует — нет сверки intent агента с изначальным запросом пользователя перед выполнением goal-changing действий.

- **Исследование**: Оценить lightweight intent validation: сравнение embedding текущей цели с embedding изначального запроса пользователя + сравнение routing domain до и после. Изучить пороги расхождения для алертинга.
- **Реализация**: Добавить `ValidateGoalIntent()` в `Orchestrator.HandleMessage()`: перед выполнением плана вычислять similarity между исходным запросом и текущим routing domain. При падении similarity ниже порога — запрашивать подтверждение пользователя. Интегрировать с kill-switch (10.9) для автоматической блокировки при критическом расхождении.

### 10.12 MCP transport security hardening (ASI04, ASI07)

> **Статус**: отсутствует — MCP HTTP transport не использует mTLS, нет message integrity verification, нет typo-squatting detection для имён MCP-инструментов.

- **Исследование**: Оценить внедрение mTLS для MCP HTTP-транспорта (сертификаты клиента и сервера). Изучить HMAC-based integrity для MCP stdio-транспорта.
- **Реализация**: Добавить опциональный mTLS для MCP HTTP-серверов через секцию `mcp.servers.<name>.tls` в config.yaml. Внедрить `ToolNameValidator` — проверка имён MCP-инструментов на typo-squatting (Levenshtein distance между registered names, алерт при подозрительной близости). Интегрировать с kill switch (10.7) для блокировки подозрительных инструментов.

### 10.13 Behavioral drift detection (ASI08, ASI10)

> **Статус**: отсутствует — circuit breaker детектирует повторы и fruitless calls, но нет долгосрочного мониторинга дрейфа поведения агента (постепенное изменение паттернов tool usage, token consumption, success rate).

- **Исследование**: Определить baseline-метрики поведения агента (распределение tool-вызовов, средний tokens/step, частота retry) и пороги для алертинга. Изучить lightweight anomaly detection (статистические методы — Z-score, moving average).
- **Реализация**: Добавить `BehavioralBaseline` в `SessionManager`: персистентное хранение агрегированных метрик по проекту (скользящее среднее tool calls/task, token efficiency, step success rate). `DriftDetector` сравнивает текущую сессию с baseline и алертит при значимых отклонениях. Интегрировать с аудит-трейлом (10.2).

### 10.14 Content provenance & audit trail hardening (ASI06, ASI08, ASI09)

> **Статус**: отсутствует — нет source attribution для данных в контексте (какой инструмент и когда произвёл содержимое), нет tamper-evident logging.

- **Исследование**: Спроектировать схему provenance metadata для tool results (source tool, timestamp, content hash). Оценить overhead хранения HMAC-подписей для audit log.
- **Реализация**: Добавить `ProvenanceMetadata` к каждому `ToolResult` (tool_name, invocation_id, timestamp, content_sha256). Инжектировать provenance в контекстное окно вместе с контентом. Добавить HMAC-подписи для записей `audit_log` (10.2) с ключом, привязанным к сессии — обеспечение non-repudiation для аудит-трейла.
