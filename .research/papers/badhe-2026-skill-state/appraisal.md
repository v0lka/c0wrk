## 3. Method reconstruction

- Pipeline: сборка промпта (`Instructions` + компактный JSON `SkillExecutionState` + `LatestObservation`, App. A.4) → генерация `(R_t, ΔΣ_t, a_t)` (Eq.3 §3.2) → «Validate ΔΣt» (Alg.1 стр.6) → merge `Σ_{t+1} = Σ_t ⊕ ΔΣ_t` с null-deletion (Eq.4 §3.2) → диспатч `a_t` → выброс R_t (§3.2).
- Ключевой механизм, на котором держат заявления: владение схемой и валидацией у детерминированного рантайма, не у модели — «malformed outputs cannot corrupt persistent state Σ_t» [§7].
- Символы: см. note.md §6.
- Допущения — **[Статья]**: Σ_t — sufficient statistic (три названных случая поломки); single-agent; патчи предлагает модель, валидирует рантайм [§7].

## 7. Critical layer

- **Claim → evidence check** (несущее заявление): «O(1) при паритете точности» [§1; §5.2] → асимптотика [Eq.6–7] + бюджет-мэтч контроль [§5.6] → **present** (измерительная часть — weak по конверсии).
- **Red flags (≤3, по убыванию):**
  1. Валидация ΔΣ_t не специфицирована [Alg.1 стр.6; §7] — статья о «runtime architecture» оставляет центральный компонент однострочным; воспроизведение «по статье» невозможно.
  2. Внутренние несогласованности: набор действий и критерий успеха Env 2 различаются между §4.1 и App. B.1; correspondence-email вне списка авторов.
  3. Headline опирается на собственный бенчмарк, чей шум по построению безвреден для мира [App. C] — результат ≥0.97 доказывает устойчивость внимания, не состояния.
- **Uncertainty flags — [Не установлено]:** тела таблиц 1, 2, 4, 5, 6–9, 11; статус рецензирования; инициализация Σ_0; рекурсивность ⊕ (выводится из App. B.3); формальное ограничение \|Σ\|; названия моделей; методика таксономии §5.7; доступность кода/данных.

## 8. Threats to validity & unstated assumptions

- Что дизайн не может показать: устойчивость состояния к шуму, меняющему мир (шум App. C такого не создаёт); поведение на открытых доменах без заранее известной схемы (сами авторы называют это ограничением [§7]); мультиагентные режимы [§7].
- Abstract vs results: «strictly bounded O(1)» [§1] подаётся как свойство метода, но держится на неформальном предположении об ограниченности \|Σ\|, которое нигде не enforced — **[Анализ]**: mild overclaim, закрываемый тривиальной доработкой (byte-cap).
- Correlation→causation: причинность «выброс истории → точность» изолирована Stateful-абляцией и бюджет-мэтчем — **[Анализ]**: здесь статья аккуратна.

## 9. Review verdict

- **Summary:** Архитектурно ясная и в целом честная статья: каркас метода специфицирован достаточно для понимания, ключевые возражения заранее отработаны контролами (Stateful, бюджет-мэтч), негативная группа D/C в дрейфе показана полностью. Главные издержки — невоспроизводимость валидации, несогласованности текста и утраченные тела таблиц в доступной конверсии.
- **Strengths:**
  - Бюджет-мэтч контроль [§5.6] — прямой ответ на «это просто короткий промпт».
  - Честная негативная группа (сценарий D — все рантаймы «No») [§5.4 Table 3/10].
  - Точная постановка границ применимости (sufficient statistic, три случая поломки, single-agent) [§7].
- **Weaknesses:**
  - Валидация, retry-семантика и инициализация Σ_0 не специфицированы [Alg.1; §7].
  - Несогласованности §4.1 ↔ App. B.1.
  - Диагностический бенчмарк собственный; шум безвреден по построению [App. C].
  - Репродукционные данные (таблицы, код) недоступны/утрачены.
- **Red flags:** см. §7.
